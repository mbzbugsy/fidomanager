# M7.0 — macOS packaging foundation (unsigned)

Status: **foundation only**. This milestone produces and structurally validates a real
`Fido Manager.app` (and an unsigned DMG) from source. It is **not** Milestone 7, not a public
alpha, not Developer ID signed, not notarized, not stapled, and not validated on a clean machine
or under quarantine. M7 proper still depends on the M6/reset and hardware-validation gates.

> **Superseded in part by [M7.1](M7.1-static-native-deps.md):** libcrypto and libcbor are now
> private static archives built from pinned source. The bundle no longer has `Contents/Frameworks`,
> the dylib relocation in section 4 was removed, and the deployment floor is macOS 11.0.

Base: `main` at `ed4abec2d832af9595e5110a2413e929df4aa489` (PR #29 / M5 merged). M6 Reset is
untouched.

## 1. Runtime topology (inspected before any change)

| Question | Finding |
| --- | --- |
| How the app locates `fido-worker` | `src-tauri/src/lib.rs` calls `ProcessWorkerLauncher::beside_current_exe()`, which canonicalises `std::env::current_exe()` and joins the `'static` file name `fido-worker` in the **same directory**. Never `PATH`, the environment, or renderer input. The file must be a regular, executable, non-world-writable file (`ResolvedWorkerExecutable::checked`). |
| Development `target/` assumption | None. "Beside the canonical executable" is `target/<profile>/` in development and `Contents/MacOS/` in a bundle. **No Rust change was needed.** |
| Native linkage of the worker | libfido2 1.17.0 is the pinned, patched, **private static** archive (`libfidomanager_fido2_bounded.a`; M3). `libcrypto` (OpenSSL 3) and `libcbor` are linked **dynamically from Homebrew by absolute path** (`/opt/homebrew/opt/openssl@3/lib/libcrypto.3.dylib`, `/opt/homebrew/opt/libcbor/lib/libcbor.0.14.dylib`). The other dependencies are system ones: `libz`, `libiconv`, `libSystem`, CoreFoundation and IOKit. |
| Main app native linkage | Only system frameworks/libraries. The app process never links libfido2, libcrypto or libcbor. |
| What must be in the bundle | Main executable, `fido-worker`, the worker's two non-system dylibs, icon, Info.plist. |
| Mechanism | Tauri `bundle.externalBin` (sidecar) for the worker. This is the documented Tauri way to ship a helper, and it lands in `Contents/MacOS/` with the target-triple suffix removed, exactly where resolution already looks. Bundling the dylibs and rewriting their install names is a post-Tauri preparation step, because Tauri's `macOS.frameworks` only copies files and does not rewrite load commands. |

Caveats found while inspecting:

- `tauri-build` copies `externalBin` into the Cargo profile directory during the app build
  (`target/release/fido-worker`). The packager therefore builds the release worker under
  `--target <host>` (`target/<triple>/release/`), so the verified worker and its link map can
  never be overwritten by that copy.
- The Tauri CLI rewrites `src-tauri/Cargo.toml` dependency syntax during `tauri build`. The
  packager restores the reviewed bytes afterwards, and CI asserts `git diff --exit-code`.
- Tauri embeds the whole config (including `devUrl`) in the binary, so a string search for the
  dev server proves nothing. The production frontend is proven instead by the embedded asset keys
  of every file in `dist/`, which Tauri only embeds for production (`custom-protocol`) builds.

## 2. Bundle layout (produced locally and in CI)

```text
Fido Manager.app/
  Contents/
    Info.plist                       CFBundleIdentifier eu.fidomanager.desktop, version 0.1.0
    MacOS/
      fidomanager-app                CFBundleExecutable (main process, system linkage only)
      fido-worker                    the only worker; 0755; signing id eu.fidomanager.desktop.fido-worker
    Frameworks/
      libcrypto.3.dylib              id/load path @executable_path/../Frameworks/libcrypto.3.dylib
      libcbor.0.14.dylib             id/load path @executable_path/../Frameworks/libcbor.0.14.dylib
    Resources/
      icon.icns                      byte-identical to src-tauri/icons/icon.icns
    _CodeSignature/CodeResources     ad-hoc seal
```

The worker's exact location is `Fido Manager.app/Contents/MacOS/fido-worker`. Nothing else in
the bundle may be named like the worker (no `Resources/fido-worker`, no leftover
`fido-worker-<triple>`), and the checker enforces this.

## 3. Packaged worker resolution and authority

- **Unchanged code path.** The packaged app resolves the worker beside its own canonical
  executable. Renderer input cannot reach the path, arguments (`&'static`) or environment
  (cleared). The renderer gains no filesystem, shell, or process-launch capability: no Tauri
  shell plugin exists, and `externalBin` alone grants the renderer nothing.
- **Boundary checker extended** (`scripts/check-renderer-boundary.mjs`, regression cases in
  `scripts/test-renderer-boundary.mjs`):
  - Only `tauri.conf.json` and `tauri.macos-bundle.conf.json` may exist. Auto-merged platform
    configs such as `tauri.macos.conf.json` are rejected.
  - The overlay may contain only `bundle`, with an exact key set. `externalBin` is exactly the
    staged worker, targets are `["app"]`, updater artifacts are `false`, and `signingIdentity` and
    `entitlements` are `null`. Overriding `app.security`, adding `plugins` (an updater included)
    or `resources`, or adding a second binary all fail.
  - The base config must not set `externalBin`, `resources` or `createUpdaterArtifacts`, and has
    no `plugins`.
  - `src-tauri/src` must contain exactly one `ProcessWorkerLauncher::beside_current_exe()` and no
    `Command::new`, `std::process::Command`, `from_absolute_path` or `with_fixed_args`.
- **Runtime evidence (local, this Mac).** Launching the packaged app with `open` spawned exactly
  `…/Fido Manager.app/Contents/MacOS/fido-worker --authentication` as its child. `lsof` showed the
  live worker mapping `Contents/Frameworks/libcrypto.3.dylib` and `libcbor.0.14.dylib`, not
  Homebrew's, and the main process mapping neither. After a normal Quit, both processes were gone;
  kill/reap semantics are unchanged. Discovery here is passive and read-only.
- **Not yet done (gate):** checking the worker's code signature or designated requirement before
  spawn (for example `anchor apple generic` + Team ID + `eu.fidomanager.desktop.fido-worker`).
  Today authenticity rests on the bundle seal and Gatekeeper at app launch. A per-spawn
  requirement check needs a real Team ID and must land before a signed release.

## 4. Native dependency strategy (decision for M7.0)

Decision: **bundle + relocate, gated as non-distributable.** It was chosen over building pinned
private static OpenSSL/libcbor in this PR, which would have changed the reviewed native pipeline.

- The packager reads the worker's real load commands (`otool -L`). Every non-system dependency
  must match the reviewed allowlist (`libcrypto.3.dylib`, `libcbor.0.N.dylib`) and must itself
  have only system dependencies. Anything else, including any libfido2 dylib, aborts.
- Each dylib is copied into `Contents/Frameworks/`. Its install id and the worker's load command
  are rewritten to `@executable_path/../Frameworks/<name>`. **No `LC_RPATH`, no `@rpath`, no
  `@loader_path`, no `DYLD_*` variables, no `LSEnvironment`.** The checker enforces all of these.
- Origin recorded in `target/macos-package/package-summary.json` (this run):

  | Bundled file | Origin | Origin SHA-256 | Origin minos |
  | --- | --- | --- | --- |
  | `libcrypto.3.dylib` | Homebrew `openssl@3` 3.6.5 bottle, `/opt/homebrew/Cellar/openssl@3/3.6.5/lib/libcrypto.3.dylib` | `31180b62…a6a9a4a` | 26.0 |
  | `libcbor.0.14.dylib` | Homebrew `libcbor` 0.14.0 bottle, `/opt/homebrew/Cellar/libcbor/0.14.0/lib/libcbor.0.14.0.dylib` | `f4506b24…742d23de` | 26.0 |

- `LSMinimumSystemVersion` is set to the newest `minos` of all bundled code (here **26.0**), not
  Tauri's default 10.13. The checker rejects an understated value.

**Release-blocking limitations of this strategy** (why the output is not distributable):

1. **Provenance is unpinned.** The bottles are whatever Homebrew provides on the build host.
   There is no checksum-pinned source, no reproducible build, and no recorded build flags.
2. **Deployment target.** The bottles require macOS 26.0, while the worker and the private libfido2
   target 11.0.
3. **OpenSSL configuration path.** Homebrew's libcrypto has `OPENSSLDIR=/opt/homebrew/etc/openssl@3`
   (user-writable on Homebrew machines), and OpenSSL 3 loads its config by default. A bundled
   worker on a machine with Homebrew could read that config. Hardened Runtime library validation
   would block loading unsigned modules, but the config surface must not exist in a release.
4. Third-party notices for OpenSSL and libcbor are not yet collected into the bundle.

Required follow-up (M7.x, before Developer ID): build libcbor and libcrypto from checksum-pinned
sources as private static archives, like libfido2. Use deployment target 11.0, and configure
OpenSSL with `no-shared no-module no-engine no-dso no-autoload-config` and a non-user-writable
`OPENSSLDIR`. Link them into the worker so the bundle needs no `Frameworks/` at all. The checker's
allowlist then becomes empty.

## 5. Unsigned local build

Prerequisites: Xcode Command Line Tools, Rust 1.98.1, Node 24 and pnpm 10.17.1 on `PATH`, and
`brew install cmake pkg-config openssl@3 libcbor`. Homebrew is a **build-time** prerequisite
only; Homebrew libfido2 is never used.

```sh
pnpm install --frozen-lockfile
python3 scripts/build-libfido2.py fetch
python3 scripts/package-macos.py --dmg
python3 scripts/check-macos-bundle.py "target/macos-package/Fido Manager.app" --frontend-dist dist
python3 scripts/test-macos-bundle-check.py "target/macos-package/Fido Manager.app"
FIDOMANAGER_PACKAGED_WORKER="$PWD/target/macos-package/Fido Manager.app/Contents/MacOS/fido-worker" \
  cargo test -p fido-worker --test packaged_worker --locked -- --ignored
```

`package-macos.py` performs these steps in order:

1. Refuses to run if any signing, notarization or override variable is set (`APPLE_*`,
   `TAURI_SIGNING_*`, `LIBFIDO2_LIB_DIR`).
2. Builds a clean release worker with `--target <host>`.
3. Runs the existing `verify-libfido2-linkage.py` on that **release** worker. This closes the M3
   follow-up: "release packaging must verify the release worker".
4. Stages the worker as `target/macos-package/sidecar/fido-worker-<triple>`.
5. Runs `tauri build --bundles app` with `src-tauri/tauri.macos-bundle.conf.json` and the
   computed minimum macOS version. `beforeBuildCommand` (`pnpm build`) produces the production
   frontend.
6. Asserts the bundled worker is byte-identical to the verified one.
7. Relocates the dylibs.
8. Signs ad-hoc, inside-out.
9. Runs the structural checks, including executing the bundled worker.
10. Optionally builds `FidoManager-<version>-<arch>-UNSIGNED.dmg` with `hdiutil` (an `.app` plus
    an `/Applications` symlink), verifies it, mounts it read-only and re-runs every check on the
    mounted app.

Outputs live under `target/macos-package/` (gitignored). The base `tauri.conf.json` keeps
`bundle.active: false`, so a bare `pnpm tauri build` cannot silently produce a bundle without its
worker.

Local result (macOS 26.5.2 arm64): `.app` **builds**, unsigned `.dmg` **builds** (≈9 MB), and all
checks pass.

## 6. Structural checks (`scripts/check-macos-bundle.py`)

Uses only `plistlib`, `otool`, `nm`, `lipo`, `codesign` and `hdiutil`. It asserts:

- **Info.plist:** identifier `eu.fidomanager.desktop`, name and display name `Fido Manager`,
  version equal to `tauri.conf.json`, executable `fidomanager-app`, `APPL`, icon. No
  `LSEnvironment`, `NSAppTransportSecurity`, or Sparkle/updater keys.
- **Exact tree:** an allowlist of entries and directories. No symlinks, no duplicate or misplaced
  worker. The worker is a regular 0755-style file (owner-executable, not group/world-writable)
  beside `CFBundleExecutable`. The icon is byte-identical to the project icon. The Mach-O set is
  exactly {main, worker, allowlisted dylibs}.
- **Linkage:**
  - Every dependency is either system or `@executable_path/../Frameworks/<bundled file>`.
    Nothing matches `/opt/homebrew`, `/usr/local`, `libfido2`, `@rpath` or `@loader_path`.
  - No `LC_RPATH` or `LC_DYLD_ENVIRONMENT`. One architecture throughout.
  - The main app loads no bundled native code.
  - The worker's system linkage is exactly `libz`, `libiconv`, `libSystem`, CoreFoundation and
    IOKit, so no network framework.
  - Every bundled dylib is actually used.
  - `LSMinimumSystemVersion` is at least the newest `minos` in the bundle.
- **Symbols:** the worker statically defines `fidomanager_libfido2_1_17_0_credman_limit`,
  `fido_init` and `fido_dev_get_puat`, with no unresolved FIDO symbols. The main app and the
  dylibs define or import none.
- **Production frontend:** every `dist/` file is embedded as an asset key in the main binary.
- **Signature shape:**
  - No entitlements at all, with explicit messages for `get-task-allow`,
    `disable-library-validation`, `allow-dyld-environment-variables`,
    `allow-unsigned-executable-memory`, `disable-executable-page-protection` and `allow-jit`.
  - Signing identifiers: `eu.fidomanager.desktop` and `eu.fidomanager.desktop.fido-worker`.
  - Resources sealed (v2), Info.plist bound, and `codesign --verify --strict --deep` passes.
  - Mode `adhoc` asserts no Team ID, not merely linker-signed, and **no** Hardened Runtime.
  - Mode `developer-id` (for the future release job) asserts a Developer ID Application
    authority, one Team ID across all code, a secure timestamp, and Hardened Runtime on both
    executables. This mode is **not yet exercised with a real identity**.
- **Worker execution (dyld proof, no authenticator):** the bundled worker under an empty
  environment exits 64 for a stray argument, 78 for `FIDO_DEBUG`, and 0 on stdin EOF.

`scripts/test-macos-bundle-check.py` mutates 20 isolated copies of the real bundle and requires
each to be rejected for the intended reason. The mutations are:

- duplicate worker, leftover triple-suffixed worker, missing worker
- world-writable, non-executable and symlinked worker
- extra libfido2 dylib, missing dylib
- Homebrew load command, `LC_RPATH`
- unexpected resource
- wrong bundle id or version
- `LSEnvironment`, ATS exception
- understated minimum macOS
- `get-task-allow` entitlement
- ad-hoc Hardened Runtime
- unsigned worker
- library tampered after sealing

It also confirms an ad-hoc bundle is never accepted as Developer ID.

`crates/fido-worker/tests/packaged_worker.rs` is `#[ignore]` by default. With
`FIDOMANAGER_PACKAGED_WORKER` set, it runs the production `ResolvedWorkerExecutable` and
`ProcessWorkerLauncher` against the bundled worker (a path containing a space) through the real
hello handshake and health check, then contain/reap. It refuses any path that isn't
`Fido Manager.app/Contents/MacOS/fido-worker`.

## 7. CI packaging validation

The new `macos-packaging` job in `.github/workflows/ci.yml` runs on `pull_request` and pushes to
`main` with workflow-level `permissions: contents: read`, `persist-credentials: false`, and **no
secrets**. Steps:

1. Pinned Node/pnpm, `pnpm install --frozen-lockfile`, and the renderer boundary check.
2. Build prerequisites **without** Homebrew libfido2, and fetch the pinned libfido2 source.
3. `python3 scripts/package-macos.py --dmg`: release worker, link-map verification, Tauri
   production build, relocation, ad-hoc seal, structural checks, worker execution, DMG build,
   mount, and re-check.
4. Bundle-checker regression tests.
5. Packaged worker handshake and health check.
6. `git diff --exit-code`: packaging must not modify tracked files.

Artifacts are **not uploaded** and nothing is published.

## 8. Signing, Hardened Runtime and notarization design (prepared, not performed)

`scripts/sign-macos-bundle.py <app> --identity <id>` is the single inside-out signing
implementation. It accepts only `-` (ad-hoc) or a `Developer ID Application: … (TEAMID)` / SHA-1
identity, and refuses any other (for example `Apple Development`).

Signing order (inside-out, never `--deep` for signing):

1. `Contents/Frameworks/*.dylib`: `codesign --force --sign ID --timestamp`.
2. Helper executables in `Contents/MacOS/` other than the main one (today only `fido-worker`):
   `--options runtime --timestamp --identifier eu.fidomanager.desktop.fido-worker`.
3. The bundle (main executable, resource seal, Info.plist binding): `--options runtime --timestamp`.
4. `codesign --verify --strict --deep`, then `check-macos-bundle.py --signature developer-id`.

Entitlement policy: **none**, for both the app and the worker. No App Sandbox in this phase; any
future entitlement needs its own review. Local evidence:

- Ad-hoc + Hardened Runtime on the main app, with zero entitlements, launched normally. The
  WKWebView ran the production frontend, which issued `list_authenticators` IPC and caused the
  worker spawn. So no `allow-jit`/`unsigned-executable-memory` entitlement is needed for the app.
- Ad-hoc + Hardened Runtime on the **worker** fails in dyld: library validation rejects the ad-hoc
  bundled dylibs ("mapping process and mapped file (non-platform) have different Team IDs"). This
  is expected and desirable. With Developer ID, all code shares one Team ID and validation passes.
  With static private dependencies (section 4), nothing is loaded from `Frameworks/` at all.
  Hence ad-hoc builds deliberately omit Hardened Runtime, and `disable-library-validation` is
  never used.

Future protected release workflow (not in this PR):

1. A separate workflow triggered from a protected tag/environment with required reviewers. It is
   never `pull_request`, and it has no secrets in PR contexts.
2. Build exactly as here. Developer ID certificate in an ephemeral keychain.
3. `sign-macos-bundle.py --identity "Developer ID Application: …"`.
4. `check-macos-bundle.py --signature developer-id`.
5. Notarize with `notarytool` (App Store Connect API key from protected secrets), then staple the app.
6. Build the DMG, sign the DMG, notarize and staple the DMG.
7. `spctl --assess` / `stapler validate`.
8. Clean-machine and quarantine validation before any publication.

## 11. Exact limitations of this PR

- Ad-hoc signed only. No certificate, no Team ID, no Hardened Runtime in the shipped ad-hoc
  output, no notarization, no stapling. **Not for distribution.**
- Bundles Homebrew-built libcrypto/libcbor (see section 4). Requires macOS 26.0+.
- Clean-machine and quarantine behaviour **not** validated. The local launch was performed on the
  development Mac, which has Homebrew installed.
- Host-native architecture only. No Windows/Linux packaging. No updater, telemetry, networking,
  or provider changes.
- No hardware mutation was performed. The local launch performed passive read-only discovery only.
