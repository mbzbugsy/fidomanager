# M7.2a — macOS worker authenticity and release identity enforcement

Status: **runtime enforcement code only (ADR-017 §12 steps 2–5).** The application can now
authenticate its exact release worker at startup and on every spawn, and fails closed. Nothing in
this slice signs, notarizes, staples, publishes or releases anything. No Apple credential was used,
no Developer ID identity exists yet, and no authenticator was touched (no hardware access, no
mutation, no Reset).

Base: `main` at `4424bcd48dc0ea0d2701b9a24d7c9d55024ddb22` (PR #32, ADR-017 rev 5 and the M7.2
validation plan merged). Design: [ADR-017](../adr/ADR-017-MACOS-RELEASE-SIGNING.md). Validation
plan: [M7.2](M7.2-macos-release-validation-plan.md).

## 3. Security.framework wrapper

One file, `fido-platform/src/macos_code_signing.rs`, declares every foreign function and constant:
`SecStaticCodeCreateWithPath`, `SecStaticCodeCheckValidityWithErrors`,
`SecCodeCopyGuestWithAttributes`, `SecCodeCheckValidity`, `SecCodeCopySigningInformation`,
`SecRequirementCreateWithString`, `SecCodeCopySelf`, `SecCodeCopyStaticCode`, the
`kSecGuestAttributePid` and `kSecCodeInfo*` keys, and the CoreFoundation helpers they need
(`CFRelease`, type IDs, `CFURLCreateFromFileSystemRepresentation`, `CFStringCreateWithBytes`,
`CFStringGetBytes`, `CFData*`, `CFNumber*`, `CFDictionaryCreate`, `CFDictionaryGetValue`).

- **Ownership.** Every Create/Copy result (including out-parameters, adopted even when the call
  fails, and the `CFErrorRef` from `…WithErrors`) goes straight into `Owned`, which calls
  `CFRelease` exactly once on drop. Get-rule values are only read while their owner lives and are
  copied into bounded Rust values (strings ≤ 1 KiB, data ≤ 64 bytes, lossless UTF-8 conversion,
  type-ID checked).
- **Safe surface.** `Requirement` (immutable, `Send + Sync`, compiled once), `StaticCode`
  (`at_path`, `check_validity`, `signing_information`, `secured_info_plist_string`),
  `RunningCode` (`current_process`, `child_process(pid)`, `check_validity`,
  `signing_information`, `static_code`), plain-data `SigningInformation`, and the typed
  `CodeSigningError` (`Unsigned`, `InvalidSignature`, `RequirementNotSatisfied`, `NoSuchCode`,
  `RequirementSyntax`, `MalformedInformation`, `InvalidInput`, `Other(OSStatus)`).
- **No panics across FFI.** No callback is passed to Apple code; no Rust frame can unwind through
  a foreign one.
- **The worker never links it.** The module is compiled only with the `fido-platform` feature
  `macos-code-signing`, which `fido-service` enables and `fido-worker` must not (boundary check).
  A first packaging run without this gate failed the M7.1 link-input check (`Unreviewed system
  link input: …/Security.framework/Security.tbd`): a `#[link]` attribute would have added
  Security.framework to the worker's pinned dynamic dependencies. With the gate, the packaged
  worker's `otool -L` is unchanged (libz, CoreFoundation, IOKit, libiconv, libSystem).
- **Renderer isolation.** Nothing from this module is serializable; `Display` is one generic
  sentence; the OSStatus is kept only in `Debug` for local diagnostics.

Flags: static `kSecCSStrictValidate | kSecCSCheckAllArchitectures | kSecCSRestrictSymlinks |
kSecCSNoNetworkAccess` (`+ kSecCSCheckNestedCode` for the bundle at S3); signing information with
`kSecCSSigningInformation` (static) or `| kSecCSDynamicInformation` (running code).

## 4. OS-version flag policy (ADR-017 §5.2)

`os_version::current()` reads `sysctlbyname("kern.osproductversion")` once per startup. The strict
parser accepts only `major.minor[.patch]` of ASCII digits.

| Version | Dynamic flags |
| --- | --- |
| unparsable, or below 11.0 (incl. `10.16`) | rejected: no launcher |
| 11.0 – 11.2 | `kSecCSDefaultFlags` (0) |
| 11.3 and later | `kSecCSNoNetworkAccess` (`1 << 29`) |

The requirement string and every identity check are built without any OS input, so both paths
use the identical policy (`both_os_flag_paths_use_the_identical_requirement`). No renderer,
environment, argument, config file, `Info.plist` or debug switch participates.

Local evidence for E3 (not a substitute for the clean-machine runs): the macOS 26.5 SDK
`CSCommon.h` states that `kSecCSNoNetworkAccess` "has always been usable for SecStaticCode objects
and is usable with SecCode objects starting with macOS 11.3". On macOS 26.5.2,
`kern.osproductversion` returned `26.5.2` with `SYSTEM_VERSION_COMPAT=1`, also for a binary built
with `-mmacosx-version-min=10.15`. E3 still requires offline runs on 11.0–11.2 and ≥ 11.3.

## 5. Requirements and the Team ID

Publisher requirement (ADR-017 §5.1; Mac App Store branch dropped):

```text
anchor apple generic and identifier "<identifier>" and
certificate 1[field.1.2.840.113635.100.6.2.6] and
certificate leaf[field.1.2.840.113635.100.6.1.13] and
certificate leaf[subject.OU] = "<TEAM_ID>"
```

`WORKER_EXACT_REQ` = publisher requirement for `eu.fidomanager.desktop.fido-worker` `and cdhash
H"<EXPECTED cdhash>"`. The app requirement uses `eu.fidomanager.desktop`. Inputs are validated
constants (identifier charset, Team ID `[A-Z0-9]{10}`, hex cdhash), so no text can be injected.

**Team ID status: not provisioned.** `MACOS_RELEASE_TEAM_ID: Option<&str> = None` in
`worker_authenticity.rs` is the single reviewed constant. No value was invented. Consequences:

- development and M7.1 ad-hoc builds are unaffected;
- a *debug* build of the `macos-release-signing` flavor compiles (so `--all-features` lint and
  tests cover the enforcing code) but release startup fails closed with `TeamIdUnprovisioned`;
- an *optimized* build of the flavor does not compile:
  `error[E0080]: … the macos-release-signing flavor cannot be built optimized until the reviewed
  Team ID is set`.

**Inserting the real Team ID is a release-configuration gate**, to be done in its own reviewed
change once the Developer ID identity exists and E1 has validated the requirement against a real
signed worker.

## 6. Release-worker identity record and RID authentication (ADR-017 §5.8)

Record (`Contents/Resources/release-worker-identity.json`, ≤ 4 KiB, UTF-8 JSON, unknown /
duplicate / missing / mistyped fields rejected):

```json
{
  "schema": "fidomanager.release-worker-identity/1",
  "release": { "version": "X.Y.Z", "source_commit": "<40 lowercase hex>" },
  "worker": {
    "path": "Contents/MacOS/fido-worker",
    "identifier": "eu.fidomanager.desktop.fido-worker",
    "team_id": "<compiled Team ID>",
    "build_id": "X.Y.Z+<source_commit>",
    "file_sha256": "<64 lowercase hex>",
    "slices": [ { "arch": "arm64|x86_64", "cdhash": "<40 hex>", "cdhash_sha256": "<64 hex>" } ]
  }
}
```

S6 requires: exact schema; version = compiled version; commit = compiled commit; path, identifier
and Team ID exact; `build_id = version + "+" + commit`; every digest exact-length lowercase hex;
1–2 slices, supported architectures only, no duplicate architecture, a slice for the running
architecture. Each failure has its own `RecordError` (tests cover each).

Startup (`authenticate_release_worker`, the ordering is in shared code; the macOS environment
supplies the platform steps):

```text
S1  SecCodeCopySelf → SecCodeCheckValidity(dynamic flags by OS, APP_REQ); runtime flag, no entitlements
S2  SecCodeCopyStaticCode(self); its kSecCodeInfoUnique == the running cdhash
S3  SecStaticCodeCheckValidityWithErrors(bundle, strict|all-arch|restrict-symlinks|nested|no-network, APP_REQ)
    RID = kSecCodeInfoPList[FidoManagerReleaseWorkerIdentitySHA256] from that validated object;
    must be a string of exactly 64 lowercase hex characters
S4  open O_RDONLY|O_NOFOLLOW|O_CLOEXEC, fstat regular, size ≤ 4 KiB, read once into BUF (≤ 4 KiB enforced again on bytes read)
S5  SHA-256(BUF) == RID, compared in constant time
S6  parse that same BUF (never re-read)
S7  worker static validation against WORKER_EXACT_REQ + cdhash + file SHA-256 + identity facts
S8  EXPECTED (verifier with compiled requirement and expected identity) kept in memory; BUF dropped
```

Any failure → `WorkerAuthenticity::StartupRejected` → no worker is ever spawned, and the renderer
shows the integrity category. Local stderr records only the `StartupRejection` category.

**A21 (record swap) test hook** — test-only (`#[cfg(test)]` environment in
`release_identity.rs`), using the production single-read primitive on a real file:
`record_swapped_for_the_s4_read_is_rejected_at_s5` (attacker bytes for the S4 read →
`RecordDigestMismatch`, genuine file restored afterwards, still one read) and
`record_swapped_after_s5_cannot_change_expected` (file replaced during S7 → `EXPECTED` from the
authenticated BUF, one read). There is no production hook or switch.

## 7. E16 status (hard release gate — **open**)

The implementation uses the intended mechanism: `kSecCodeInfoPList` from
`SecCodeCopySigningInformation` on the bundle static code that S3 validated. That this returns the
*signed* plist value (not an on-disk edit) on 11.0–11.2 and on ≥ 11.3 is **not** proven by this
slice: it needs a real signed bundle with the on-disk `Info.plist` edited after signing
(validation plan A22). Nothing here claims E16 is solved; the code compiles and fails closed when
the key is missing or malformed. If E16 fails, M7.2 does not ship (ADR-017 §5.8).

## 8. `ChildHello.build_id` (protocol version 9)

`ChildHello` gained `build_id: String` (`deny_unknown_fields`, required; a version-8 hello without
it is malformed). The worker reports the compile-time `fido_platform::build_identity::
WORKER_BUILD_ID` (`<version>+<commit>` in the release flavor, `<version>+development` otherwise).
`ParentHello::validate_reply(reply, spawned_pid, expected_build_id)` checks protocol, generation and
pid first, then the build id (≤ 128 bytes, exact equality, an empty expectation never matches),
returning `HandshakeError::BuildIdMismatch`. The launcher maps that to the terminal
`WorkerIdentityRejected`, never to `HandshakeMismatch`. The expected value is backend-owned
(compiled constant in development, `EXPECTED.build_id` in release); the renderer neither provides
nor sees it. It is a build identity, not a session or runtime id.

## 9. Per-spawn launcher order and PID ownership

Every `launch()` (first start, replacement, breaker probe), nothing cached:

1. latched rejection → `WorkerIdentityRejected` without resolving or spawning;
2. re-resolve `dir(canonical(current_exe()))/fido-worker`; must equal the construction-time
   canonical path; regular, executable, not world-writable; **release**: inside
   `.app/Contents/MacOS`, `lstat` not a symlink, not group-writable, absolute paths refused;
3. static validation (release) — failure: latch, nothing spawned;
4. spawn exactly that path (environment cleared, `'static` args, fd 3 only for `--authentication`);
5. dynamic validation of that child by pid (release): `SecCodeCopyGuestWithAttributes` +
   `SecCodeCheckValidity(WORKER_EXACT_REQ)` + status ⊇ `valid | kill`, identifier, Team ID,
   `runtime`, no entitlements, running cdhash == `EXPECTED`; then `waitid(WNOWAIT)` must show the
   child still running;
6. only then the stdout reader starts and `ParentHello` is written; handshake timeout as before;
7. `ChildHello.build_id` == expected, then the health check.

**PID invariant** (documented on `ProcessWorkerEndpoint::establish`): the endpoint owns the only
`Child`, nothing else waits on it (no global reaper, no concurrent `try_wait`/`wait`), and the only
reaping paths (`terminate`, `has_exited`) cannot run before step 5 finishes. Until reaped, the pid
cannot be reused. The exit check uses `waitid(… WNOHANG | WNOWAIT)`, which does not reap. A child
that exits before or during validation is rejected (`child_exiting_during_validation_is_rejected`;
real-process evidence: `exit_is_observed_without_reaping_the_child`, and the dynamic check of an
exited child fails with `NoSuchCode`/ESRCH).

No ParentHello, PIN, PUAT, request, mutation authority or secret is sent before step 5 passes
(`nothing_is_written_before_dynamic_verification_succeeds`,
`failed_dynamic_verification_sends_nothing_latches_then_contains`).

## 10. `WorkerIdentityRejected`, latch and containment

- `LaunchError::WorkerIdentityRejected { quiescence }` — terminal. The launcher's `IdentityLatch`
  is set **before** `contain()`; `quiescence: Active` carries a failed containment *alongside* the
  rejection, never instead of it (`not_contained_keeps_the_identity_rejection_latched`; the fake
  process records that the latch was already set at every kill).
- The supervisor latches `SupervisorError::WorkerIdentityRejected { quiescence }` (and
  `WorkerExecutableRejected`, ADR-017 §5.7 makes filesystem integrity rejections terminal too)
  before recording the failure, never wraps it as `Launch(..)`, and refuses every later launch for
  the session regardless of backoff, breaker, cooldown or a launcher that would now succeed
  (`identity_rejection_is_terminal_and_never_relaunched`,
  `not_contained_identity_rejection_keeps_the_terminal_latch`). Ordinary launch failures stay
  retryable (`ordinary_launch_failures_are_not_integrity_failures`).
- No fallback exists to `PATH`, another path, the development mode, an unsigned/ad-hoc worker, a
  publisher-only requirement or a weaker flag set.
- Renderer: `DiscoveryPresentation::IntegrityFailure {}` (`{"state":"integrity_failure"}`), shown
  as "Fido Manager could not verify its own components. Reinstall it from the official release.";
  inventories are cleared, Scan now is disabled, and an IPC error cannot turn it back into
  "unavailable". No path, OSStatus, Team ID, cdhash, certificate, requirement, record or build id
  crosses IPC.

## 11. M5 / M6 recovery regressions

**M5 (credential deletion) — proven end to end.**
`identity_rejected_replacement_keeps_unknown_deletion_outcome_journal_and_barrier`
(`fido-worker-fixture/tests/credential_deletion.rs`) runs the production service, endpoint,
runtime and engine for `lost-response`, `crash` and `unknown`: the delete is entered and its
result lost (`OutcomeUnknown`, journal `dispatch_capable`), then the replacement worker reports
another build id. Result: terminal `WorkerIdentityRejected { Quiescent }`; repeated refreshes
launch nothing (exactly one `replacement-started`); the journal bytes are unchanged
(`dispatch_capable`, no resolution); recovery admission stays `Barrier`; the recoverable operation
is still `DeleteCredential`; `reserve()` is refused; the delete is never retried. Unit companion:
`identity_rejected_replacement_never_erases_unknown_deletion_evidence` (also shows the journal
refuses `NotDispatched` and a restart still sees the barrier).

**M6 (Reset) — nearest existing boundary.** M6.0 merged no Reset dispatch, Reset journal
operation or Reset recovery family (ADR-011). What is proven
(`worker_authenticity::tests::m6_reset_boundary`):
`identity_rejection_cannot_admit_reset_or_erase_uncertain_evidence` — with an uncertain durable
`dispatch_capable` incident (`change_pin`, `set_pin`, `delete_credential`) and a worker identity
rejection, a `SensitiveWorkflowKind::Reset` admission is refused with `RecoveryBarrier` and the
record is byte-identical; `uncontained_identity_rejection_never_releases_a_reset_admission` — an
admitted Reset-class workflow cannot be released with the `Active` quiescence carried by a
not-contained rejection. The ADR-017 §12 step 4(c) regression for a real Reset incident remains to
be written when the M6 Reset journal operation lands.

## 12. Release build flavor

`macos-release-signing` (on `fidomanager-app`, `fido-service`, `fido-worker`, `fido-platform`):
compile-time only; never a default feature (boundary check). It:

- runs S1–S8 in `ProcessWorkerLauncher::beside_current_exe()`, the single construction site
  (boundary check: exactly one `release_startup()` call, exactly one `WorkerAuthenticity::Enforced`
  construction file, exactly one Team ID constant);
- compiles `FIDOMANAGER_RELEASE_SOURCE_COMMIT` (read by `fido-platform/build.rs` at **compile
  time only**; malformed → build error; missing in an optimized build → compile error) into the
  build id;
- links the enforcing marker, found by byte search:
  `FIDOMANAGER-RELEASE-ENFORCING-MARKER/1;team=<TEAM>;version=<X.Y.Z>;commit=<40-hex>;end`
  (today `team=UNPROVISIONED`). Verified: present in a debug flavor build of
  `target/debug/fidomanager-app`, absent (0 matches) from the default build;
- never downgrades: on failure the launcher is permanently rejected; on a non-macOS target it is
  rejected too.

Development and M7.1 ad-hoc builds keep `UnsignedDevelopment` (path checks + build-id consistency).
`ci.yml` is unchanged and stays ad-hoc and secret-free.
