# M6.0 H0: non-destructive Option A timing spike

Date: 2026-10-07. Branch: `feature/m6-reset-architecture`, from main `f444caa`.
Architecture: [ADR-011](../adr/ADR-011-FIDO2-RESET.md). Implementation SHA: the exact head
recorded in the Draft PR containing this report.

## Purpose

Decide whether ADR-011 Option A fits the authenticator Reset window:

```text
reconnect → candidate discovery → open/GetInfo validation → durable DispatchCapable
(F_FULLFSYNC) → ExecuteReset
```

H0 measures every host-side part of that path and stops at the point where an `ExecuteReset`
frame would be received. **It never sends Reset, and cannot.**

## Status

- Tooling: implemented and tested on Linux and on macOS (build, link, symbol and link-map checks
  run locally on the measurement Mac; see "Hardware session" below).
- Hardware measurement: **performed** on 2026-10-07 with one YubiKey 5 series key (firmware
  5.7.4), 20 valid samples, no aborts. No Reset, PIN, credential or configuration command was
  sent; the tool only discovered, opened and read GetInfo.
- Verdict (default policy, fixed before measurement): **OPTION A VIABLE** for this model on this
  host. It is evidence for one model and one Mac; see "Limits of this evidence".

## Tool architecture (`crates/fido-h0-timing`)

| Part | Role |
|---|---|
| `macos/insertion.rs` | IOKit first-match notifications for `IOHIDDevice` services on usage page 0xF1D0, on their own run-loop thread. Observes the registry only; opens nothing. This is the insertion clock; absence and cardinality come from the libfido2 manifest. |
| `macos/fido.rs` | The complete libfido2 surface: manifest, open, GetInfo, parsed GetInfo getters, close. |
| `measurement.rs` | The Option A pass, generic over device/clock/journal/executor seams and unit-tested with fakes: poll manifest → exactly one candidate → open → GetInfo → mismatch-only snapshot comparison and record serialization → durable replace → would-dispatch. Cardinality > 1, timeouts, open/GetInfo/durability failures abort the sample before any later step. |
| `durability.rs` | T5 calls `fido_platform::recovery_file::DurableRecoveryFile::replace`, the production journal primitive (temp file, F_FULLFSYNC, rename, directory fsync, F_FULLFSYNC), on a production-shaped record under the session's own scratch directory. The record names a different application, so it can never be loaded as a real incident. |
| `would_dispatch.rs` | The would-dispatch point: a marker frame crosses a Unix socket to a thread that owns no device, is timestamped and discarded. |
| `operator.rs` | Interactive operator mode (below). |
| `decision.rs`, `report.rs`, `stats.rs` | Nearest-rank min/median/p95/max per component and total, per model label; ADR-011 acceptance rule. |
| `session.rs` | The only place H0 writes. Refuses any directory that is not new, empty or an existing H0 session, so it cannot be pointed at the real application data directory. |

Timeline per sample (process monotonic clock):

| Component | From → to |
|---|---|
| T1 | IOKit insertion notification → libfido2 manifest lists exactly one candidate (may be negative if the poll wins the race) |
| T2 | manifest → `fido_dev_open` returned (INIT + internal GetInfo) |
| T3 | open → explicit `fido_dev_get_cbor_info` returned |
| T4 | GetInfo → snapshot compared and DispatchCapable bytes serialized (immediately before the durable write) |
| T5 | production durable replace |
| T6 | durable replace → would-dispatch frame received by the executor stub |
| total | T1 + … + T6 |

Not measured: T0 (power-up → HID service published) and T7 (frame receipt → first HID report);
ADR-011 covers them with explicit allowances.

## Structural proof that H0 cannot send Reset

`tests/no_destructive_capability.rs` runs in both CI jobs (`cargo test --workspace`) and fails if:

1. any source file, the build script or the manifest contains `fido_dev_reset`, `CTAP_CBOR_RESET`,
   `fido_tx`/`fido_rx`, custom I/O or transport hooks, `fido_dev_cancel`, any PIN, credential,
   bio, large-blob or config command, raw HID report I/O (`IOHIDDeviceSetReport`,
   `IOHIDDeviceOpen`, HID manager), dynamic loading, process spawning, or the M6 authority type
   names;
2. any native function outside a closed allowlist is declared, or natives are declared outside
   the two reviewed files; the declared libfido2 set must equal the allowlist exactly;
3. `Cargo.lock` resolves H0's dependencies to anything but `fido-platform`, `libc`, `serde`,
   `serde_json`, or `fido-platform` to anything but `libc` (no production FIDO crate can arrive
   transitively);
4. the built executable's symbol table contains any destructive libfido2 symbol; on macOS it must
   also contain the read-only ones, statically, so the absence is meaningful; off macOS it must
   contain no libfido2 symbol at all. (On macOS the executable imports `IOHIDDeviceSetReport`
   because libfido2's own HID write path uses it for INIT and GetInfo; H0 code cannot call it,
   and only allowlisted libfido2 entry points reach it.);
5. on macOS, the linker map of the tested executable lists libfido2's `reset.c.o`, or does not
   list the pinned private archive's `info.c.o`/`dev.c.o`, or the archive identity is not the
   pinned revision. libfido2 defines `fido_dev_reset` only in `reset.c`, which nothing else
   references, so a static link without that object has no code that emits 0x07.

The checker itself is tested: an injected `fido_dev_reset` declaration is caught. During
development the check was also exercised by adding such a declaration to `macos/fido.rs`; both
source checks failed, and the change was reverted.

There is no `--dry-run`: the binary has no mode with a destructive step. The CLI test asserts
that `--dry-run`, `--execute` and `--force` are rejected as unknown options.

## Hardware operator mode (for the authorized session)

No PIN, no touch, no credential access. The operator only unplugs and plugs in one key.

```sh
cargo build -p fido-h0-timing --locked --release
S="$HOME/fidomanager-h0/$(date +%Y%m%dT%H%M%S)"
target/release/fido-h0-timing durability --session "$S" --samples 200    # no key needed
target/release/fido-h0-timing measure --session "$S" --samples 20        # interactive
target/release/fido-h0-timing report --session "$S"
```

`measure` prints one instruction at a time and waits for the tool to observe it:

1. `H0 ACTION: Unplug the security key.` → waits until neither IOKit nor libfido2 sees a key.
2. (untimed) scratch `Pending` written, insertion clock armed.
3. `H0 ACTION: Plug the security key in. Do not touch it.` → measures one pass.
4. `H0 SAMPLE: n/N measured, total … ms` (or `aborted (reason)`), then back to step 1.

Samples append to `hardware-samples.jsonl`, so an interrupted session resumes. Close browsers
and other FIDO clients first: libfido2 seizes the device and an open failure aborts the sample.

## Data and privacy

Session directory: `h0-session.json` (OS version and build, hardware model, architecture,
scratch filesystem type, pinned libfido2 revision, tool version), `hardware-samples.jsonl`,
`durability-samples.jsonl`, `report.json`, `report.md`, and `journal-scratch/`. Samples record
VID/PID, manufacturer/product strings, AAGUID and firmware version as a model label, plus
timings. No native path, IORegistry ID, serial, user or host name, PIN or credential is stored.
Model labels group results; they are never identity or authority.

  delete or config symbol. The only symbols containing "reset" are the read-only accessors
  `fido_blob_reset`, `fido_cbor_info_reset`, `fido_cbor_info_long_touch_reset` and
  `fido_cbor_info_reset_transports_{len,ptr}`. The release link map does not list `reset.c.o`.
- Isolation: the session directory was new, under `~/fidomanager-h0/`, outside
  `~/Library/Application Support`. `journal-scratch/` existed only inside it and its record names
  application `fidomanager-h0-timing-scratch-v1`. A before/after listing (paths, inode, size,
  mtime, SHA-256) of the real application data directory (`eu.fidomanager.desktop`) was
  identical.

Environment: macOS 26.5.2 (25F84), Mac16,1, aarch64, APFS scratch filesystem, libfido2
`b974e7cf2ee7392134cc12c08b76a068cf250dd8`, tool 0.1.0. Chrome and Safari were running but idle
(no WebAuthn request); no sample was affected (zero open failures).

Procedure: exactly one key connected throughout, confirmed by the libfido2 manifest (the tool
aborts a sample on any count other than 0 or 1; none did). For every sample the log shows
`no security key connected` (manifest count 0) before the plug-in instruction and a single
candidate afterwards, so each sample has an observed 1 → 0 → 1 sequence. The operator only

at a time; at the owner's request samples 6–20 were self-paced (unplug, about 3 s, plug in, about

Excluded: a first measurement session was started while a different authenticator (a non-Yubico

stopped, and is not part of this evidence. The reported session below was started fresh, with its
own durability run, after that key was removed.

## Results

`durability-samples.jsonl`, `report.json`, `report.md`). Generated with
`fido-h0-timing report --session …` and the **default policy** (no options). Milliseconds;
nearest-rank percentiles, every value an observed sample.

Model label (groups samples only; not identity or authority): Yubico "YubiKey FIDO+CCID",
VID 0x1050, PID 0x0406, AAGUID `d7781e5de35346aaafe23ca49f13332a`, firmware 5.7.4 (329476).

|---|---|---|---|---|---|
| T1 insertion → manifest | 20 | 0.572 | 1.501 | 6.460 | 8.324 |
| T2 manifest → open | 20 | 223.564 | 225.080 | 226.146 | 227.805 |
| T3 open → GetInfo | 20 | 15.819 | 15.994 | 16.046 | 16.052 |

- T2 (`fido_dev_open`: CTAPHID INIT plus libfido2's internal GetInfo) dominates at about 225 ms

  7.8 ms); both are small next to the budget.
- An earlier 200-sample durability-only run in the excluded session gave min 5.676, median
  8.731, p95 9.843, max 15.599 ms, consistent with the reported run.

### Limits of this evidence

- One authenticator model, one Mac, one OS build. Other vendors, models, macOS versions and
  slower or busy disks need their own samples before the same conclusion applies to them.
- T0 (power-up → HID publish) and T7 (frame receipt → first HID report) remain allowances, not
  measurements (ADR-011, unresolved decision 4).
- Production discovery cadence must stay within the 100 ms poll allowance (ADR-011, unresolved
  decision 8). H0 polled tightly; production must not regress T1 beyond that allowance.
- Option A viability does not change any authority rule: the 1 → 0 → 1 trace remains
  correlation evidence, not proof that the same physical key was reinserted.
