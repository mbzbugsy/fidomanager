# M7.2 — macOS release validation plan (signed, notarized, stapled)

Status: **plan only**. Nothing here has been run. It needs a real Developer ID identity and a
notarized artifact, and neither exists yet. Design:
[ADR-017](../adr/ADR-017-MACOS-RELEASE-SIGNING.md). Base: main
`d32dcd60fd37cd0bae4702a92447251b709d91dc`, assuming M7.1 (static private dependencies, no
`Contents/Frameworks/`) has merged.

The plan has three parts:

- **A.** Automated checks that run in the protected workflow's `verify` job (no secrets). They gate
  the draft release.
- **B.** A manual clean-machine and quarantine matrix that a maintainer runs on the **draft**
  release's DMG, downloaded through a browser. It gates making the release public (ADR-017 D13).
- **C.** Worker handshake latency evidence against the existing 3 s `handshake_timeout`. This plan
  **does not change the timeout**; it only defines the evidence that would justify revisiting it.

No step mutates an authenticator. Discovery and PIN *verification prompts* are cancelled or use a
non-mutating read; no PIN change, credential deletion or Reset is performed (M6/Reset is out of
scope).

## Part A — automated (verify job, fresh GitHub-hosted macOS VM)

| ID | Check | Pass |
| --- | --- | --- |
| A1 | Recompute the SHA-256 of the DMG and the app zip; compare with the `sign-notarize` outputs | equal |
| A2 | Simulate a download: `xattr -w com.apple.quarantine "0081;$(printf %x $(date +%s));Safari;$(uuidgen)" dmg` | attribute set |
| A3 | `hdiutil verify dmg` | valid |
| A4 | `spctl --assess --type open --context context:primary-signature -vvv dmg` | `accepted`, `source=Notarized Developer ID` |
| A5 | `xcrun stapler validate dmg` | worked |
| A6 | `hdiutil attach -readonly -nobrowse`; `ditto` the app to a temp `Applications` dir (keeps quarantine); detach | copied app carries `com.apple.quarantine` |
| A7 | `spctl --assess --type execute -vvv` on the copied app | `accepted`, `source=Notarized Developer ID`, origin Team ID == expected |
| A8 | `xcrun stapler validate` on the copied app | worked (the app has its own ticket, ADR-017 D9) |
| A9 | `codesign --verify --strict --deep -vvv` on the copied app | exit 0 |
| A10 | `codesign --verify -R='=<worker requirement>'` on `Contents/MacOS/fido-worker`; same for the app requirement | satisfied |
| A11 | `check-macos-bundle.py --signature developer-id --stapled --expected-team-id <constant>` | pass: exact code set, zero entitlements, runtime, timestamp, chain, enforcing marker, exactly one `Contents/CodeResources` ticket |
| A12 | Negative: make an ad-hoc-re-signed copy of the worker; run the verifier's test against it | **rejected** |
| A13 | `packaged_worker` (`--ignored`) with the **enforcing** verifier against the copied app's worker | handshake, health and reap pass; spawn → hello latency recorded |
| A14 | Manifest and SBOM: the digests in `release-manifest.json` and `SHA256SUMS` match the files; the SBOM lists the libfido2, OpenSSL and libcbor versions/digests that match the lock files | match |

A failure in any row fails the job, and `attest` and `publish-draft` do not run.

## Part B — manual clean-machine and quarantine matrix

### Machines

| Machine | Purpose |
| --- | --- |
| **M1** | Apple-silicon Mac on the **oldest supported macOS** (deployment target 11.0, or the oldest a maintainer can provide; record the version). Fresh user account. **No Homebrew, no Xcode, no Command Line Tools**, no previous Fido Manager. |
| **M2** | Apple-silicon Mac on the **current** macOS release, same clean conditions. |
| **M3** (if architecture support exists) | Intel Mac. Only if an x86_64 or universal artifact ships (M7.0 gate 6). |

"Clean" is checked before starting: `ls /opt/homebrew /usr/local/Cellar` gives no such directory,
`xcode-select -p` fails, `which openssl` is only the system one, and there is no
`~/Library/Application Support/eu.fidomanager.desktop`.

Authenticator: one FIDO2 key whose PIN is known. Only discovery, read-only inspection and a
cancelled or read-only PIN prompt are used.

### Steps

Each row records the macOS version, date, the build's tag and DMG SHA-256, the outcome, a
screenshot where noted, and `log show --last 5m --predicate 'subsystem == "com.apple.syspolicy" OR process == "syspolicyd"'`
for the Gatekeeper rows.

| ID | Step | Expected | Evidence |
| --- | --- | --- | --- |
| B1 | Download the DMG from the draft release **with Safari** | the file has `com.apple.quarantine` (`xattr -l`) | xattr output |
| B2 | Verify the SHA-256 against `SHA256SUMS` from the same release page | match | shasum output |
| B3 | Double-click the DMG in Finder | mounts with no Gatekeeper warning beyond the normal one; volume shows the app and an `Applications` link | screenshot |
| B4 | Drag the app to `/Applications`, eject, launch from Finder (first launch) | the standard "downloaded from the Internet" dialog, with Apple's malware-check wording; **no** "unidentified developer" or "cannot be opened" dialog | screenshot |
| B5 | Click Open | main window appears; no TCC prompt (Input Monitoring or other) | screenshot; note any prompt (ADR-017 E7) |
| B6 | Check the process tree: `ps -o pid,ppid,command -ax \| grep -i fido` | exactly one `…/Fido Manager.app/Contents/MacOS/fido-worker --authentication` child of `fidomanager-app` | ps output |
| B7 | `codesign -dvvv <worker pid>` (codesign accepts a pid and then reports the running process) | Developer ID Application, expected Team ID, `runtime`; note whether `kill` appears in the status flags (E4) | output |
| B8 | Insert the authenticator | device discovered; model and capability info shown | screenshot |
| B9 | Start a read-only operation that needs the PIN (credential inspection) | native AppKit sheet appears modally on the main window; cancel it | screenshot |
| B10 | Quit with ⌘Q | app and worker both gone (`ps`) | ps output |
| B11 | Relaunch (second launch) | no Gatekeeper dialog; discovery works | note |
| B12 | **Offline**: turn off Wi-Fi and unplug Ethernet; Quit; relaunch | launches; discovery works; read-only inspection works; nothing waits on the network | note; time to first discovered device |
| B13 | **Offline first launch**: on a second fresh user account (or after `xattr` reset on a fresh copy), with the network **off from before the download was copied in** (bring the DMG over by USB stick, preserving quarantine with `ditto`), install and first-launch | accepted from the **stapled** tickets; no "cannot verify" dialog | screenshot; syspolicy log |
| B14 | **Translocation**: from a fresh download, launch the app **directly from the mounted DMG** (or from `~/Downloads` unmoved) | launches; worker resolves beside the running executable (a translocated `…/AppTranslocation/…` path or the read-only volume); discovery works; quit is clean | `ps` path; repeat once after a normal relaunch, since translocation applies on first launch only |
| B15 | **Tamper, worker**: on a copy in `/tmp`, replace `Contents/MacOS/fido-worker` with an ad-hoc-signed build of the same worker; launch that copy | the app starts (Gatekeeper may refuse the broken seal first, which is also a pass); FIDO functionality disabled with the integrity message; **no worker process stays running**; no fallback | screenshot; ps |
| B16 | **Tamper, wrong identifier**: same as B15, with a worker re-signed (ad-hoc) with a different identifier | same as B15 | same |
| B17 | **Missing worker**: delete the worker in a `/tmp` copy | integrity or launch error; no crash loop (the supervisor treats it as terminal) | screenshot |
| B18 | **Duplicate distribution**: keep `/Applications/Fido Manager.app`, also run a second copy from another folder | the single-instance policy (ADR-012) holds; each copy validates its own sibling worker | note |
| B19 | Second user account on the same Mac launches the already-installed app | works; no extra Gatekeeper prompt beyond macOS's per-user behaviour | note |

B15–B17 are run on copies the maintainer makes deliberately. They are **not** release artifacts
and are deleted afterwards.

### Publication rule

The draft release is made public only when B1–B14 pass on M1 and M2 (and M3 if applicable) and
B15–B17 show fail-closed behaviour. The filled-in matrix is committed as
`docs/validation/M7.2-macos-release-<version>.md`.

## Part C — first-launch Gatekeeper latency vs the 3 s worker handshake

Background: `ProcessWorkerConfig::default().handshake_timeout` is 3 s. It starts **after**
`ParentHello` is written (`process_worker.rs`), so in the ADR-017 design the pre-spawn and
post-spawn signature validation happen **before** that clock starts. Two latencies can still eat
into the window:

1. the worker's own exec when its file is quarantined: does syspolicyd evaluate a nested helper
   separately on first exec (ADR-017 E15)?
2. first-run dyld and page-in costs for a freshly copied binary on a cold disk cache.

### Measurements

| ID | Condition | Measure |
| --- | --- | --- |
| C1 | M1 and M2, first launch after quarantined download, online | spawn → `ChildHello` received; static + dynamic validation time |
| C2 | Same, offline (B13 conditions) | same |
| C3 | Translocated launch (B14) | same |
| C4 | Second and later launches | same (baseline) |
| C5 | Supervisor replacement spawn after `kill -9` of the worker | same |

How to measure: the M7.2 implementation should record, per worker generation, the
validation-duration and handshake-duration milliseconds in the existing local diagnostics. These
are non-sensitive timing integers that never leave the machine (Diagnostics Center, product
roadmap). The A13 test records the same in CI. In addition, `log stream --predicate 'process ==
"syspolicyd"' --style compact` running during C1–C3 shows whether a separate assessment of
`fido-worker` happens.

### Evidence threshold (proposal, for review)

- At least 10 first-launch samples per machine for C1 and C2.
- If the **maximum** spawn → `ChildHello` latency is under 1.5 s (half the timeout) on every
  machine, the 3 s timeout is kept with recorded evidence.
- If any sample is over 1.5 s, or any handshake times out, record it as a finding and open a
  separate reviewed change. The timeout is **not** changed in M7.2.
- In every case, a first-launch handshake timeout must already be self-healing through the ADR-009
  backoff (the next spawn is no longer the first exec). B4/B5 show whether the user notices.

## What is out of scope here

- Windows and Linux packaging.
- Any updater.
- Universal or x86_64 builds, unless they ship.
- Hardware mutation of any kind, and M6/Reset.
