# M7.2 — macOS release validation plan (signed, notarized, stapled)

Status: **plan only**. Nothing here has been run. It needs a real Developer ID identity and a
notarized artifact, and neither exists yet. Design:
[ADR-017](../adr/ADR-017-MACOS-RELEASE-SIGNING.md). Base: main
`15ae91c71f1531b26ce3a1ce7367659018c8455d` (M7.1 static native dependencies merged).

Revision 4 (final independent Astra review) adds:

- checks that the app authenticates the exact record bytes through the secured `Info.plist`
  digest, including a record-swap race (A15, A17, A21, A22);
- the acyclic `SHA256SUMS` and the `D7`-plus-attestation root of trust for publication (A20,
  Part D);
- both dynamic-validation flag paths on macOS 11 (machines M1 and M1b);
- clean-machine rows for the shipped app ZIP (B23–B28);
- the `≥ 1.5 s` latency threshold;
- Part E (N1–N14): hostile-archive, authorization-substitution, eligibility and policy-check
  negatives.

Revision 3 (rebase on merged M7.1) states the expectations as the merged M7.1 bundle and checker
define them (ADR-017 section 1.1): exactly two Mach-O executables, no `Contents/Frameworks/`,
`LSMinimumSystemVersion` and worker `minos` 11.0, a byte-identical
`Contents/Resources/THIRD_PARTY_NOTICES.md`, and static link provenance proven in the `build` job
before anything is signed.

Revision 2 (after an independent red-team review) adds the checks for the exact app ↔ worker
binding (ADR-017 D14), keeps every check that executes candidate code out of the credential-bearing
job (D15), and adds Part D, which verifies the assets that are actually published (D16).

No row in any part runs in the `sign-notarize` job. That job executes no candidate code. Its own
data-only checks are defined in ADR-017 section 4 ("Driver" rows).

The plan has five parts:

- **A.** Automated checks that run in the protected workflow's `verify` job (no secrets). They gate
  the draft release.
- **B.** A manual clean-machine and quarantine matrix that a maintainer runs on the **draft**
  release's DMG, downloaded through a browser. It gates approval of `publish-final` (ADR-017 D13).
- **C.** Worker handshake latency evidence against the existing 3 s `handshake_timeout`. This plan
  **does not change the timeout**; it only defines the evidence that would justify revisiting it.
- **D.** Publication verification: the draft's and then the published release's actual assets are
  downloaded and checked against the authorization record, after that record has been
  authenticated by `D7` and its attestation (ADR-017 7.6).
- **E.** Negative tests at the signing boundary and the publication root, run in the signer
  repository's test suite and in the credential-free rehearsal (ADR-017 §12, step 10).

No step mutates an authenticator. Discovery and PIN *verification prompts* are cancelled or use a
non-mutating read; no PIN change, credential deletion or Reset is performed (M6/Reset is out of
scope).

| A22 | Secured-plist negative (E16): on a copy, edit the on-disk `Info.plist` digest key to the SHA-256 of an edited record and put that record in place | startup fails (S1–S3 validation or S5); the edited key is never accepted as the signed value. Recorded as E16 evidence |

A failure in any row fails the job, and `attest` and the publication jobs do not run.

## Part B — manual clean-machine and quarantine matrix

### Machines

| Machine | Purpose |
| --- | --- |
| **M1** | Apple-silicon Mac on **macOS 11.0–11.2**, the declared floor (`LSMinimumSystemVersion` 11.0). This exercises the dynamic-validation path **without** `noNetworkAccess` (ADR-017 5.2, E3). M7.1 never launched the app on macOS 11 (its gate 3; ADR-017 E20). Fresh user account. **No Homebrew, no Xcode, no Command Line Tools**, no previous Fido Manager. |
| **M1b** | Apple-silicon Mac on **macOS 11.3 or a later 11.x**, same clean conditions. This exercises the `noNetworkAccess` dynamic path on the floor's major version. If M1 or M1b cannot be provided, record that, keep E3 and E20 open, and do not claim macOS 11 support in the release notes. |
| **M2** | Apple-silicon Mac on the **current** macOS release, same clean conditions. |
| **M3** (if architecture support exists) | Intel Mac. Only if an x86_64 or universal artifact ships. Merged M7.1 packages arm64 only (its gate 4), so M3 is not run for the first release. |

"Clean" is checked before starting: `ls /opt/homebrew /usr/local/Cellar` gives no such directory,
`xcode-select -p` fails, `which openssl` is only the system one, and there is no
`~/Library/Application Support/eu.fidomanager.desktop`.

Authenticator: one FIDO2 key whose PIN is known. Only discovery, read-only inspection and a
cancelled or read-only PIN prompt are used.

for the Gatekeeper rows.

artifacts and are deleted afterwards.

### Publication rule

`publish-final` is approved only when B1–B14 and B23–B28 pass on M1, M1b and M2 (and M3 if
applicable), with B12 and B28 (offline) passing on both macOS 11 flag paths; B15–B17 and B20–B21
(B20 from the second release on) show fail-closed behaviour; and B2 matched the DMG digest in the
**authenticated** authorization record (Part D). The filled-in matrix is committed as
`docs/validation/M7.2-macos-release-<version>.md`.

## Part C — first-launch Gatekeeper latency vs the 3 s worker handshake

Background: `ProcessWorkerConfig::default().handshake_timeout` is 3 s. It starts **after**
`ParentHello` is written (`process_worker.rs`), so in the ADR-017 design the pre-spawn and
post-spawn signature validation happen **before** that clock starts. Two latencies can still eat
into the window:

1. the worker's own exec when its file is quarantined: does syspolicyd evaluate a nested helper
   separately on first exec (ADR-017 E15)?
2. first-run dyld and page-in costs for a freshly copied binary on a cold disk cache.

### Measurements

| ID | Condition | Measure |
| --- | --- | --- |
| C1 | M1, M1b and M2, first launch after quarantined download, online | spawn → `ChildHello` received; static + dynamic validation time |
| C2 | Same, offline (B13 conditions) | same |
| C3 | Translocated launch (B14) | same |
| C4 | Second and later launches | same (baseline) |
| C5 | Supervisor replacement spawn after `kill -9` of the worker | same |

How to measure: the M7.2 implementation should record, per worker generation, the
validation-duration and handshake-duration milliseconds in the existing local diagnostics. These
are non-sensitive timing integers that never leave the machine (Diagnostics Center, product
roadmap). The A13 test records the same in CI. In addition, `log stream --predicate 'process ==
"syspolicyd"' --style compact` running during C1–C3 shows whether a separate assessment of
`fido-worker` happens.

### Evidence threshold (proposal, for review)

- At least 10 first-launch samples per machine for C1 and C2.
- If the **maximum** spawn → `ChildHello` latency is below 1.5 s (half the timeout) on every
  machine, the 3 s timeout is kept with recorded evidence.
- If any sample is **≥ 1.5 s**, or any handshake times out, record it as a finding and open a
  separate reviewed change. The timeout is **not** changed in M7.2.
- In every case, a first-launch handshake timeout must already be self-healing through the ADR-009
  backoff (the next spawn is no longer the first exec). B4/B5 show whether the user notices.

## Part D — publication verification (publish-draft and publish-final jobs)

These rows run in the publication jobs. Those jobs have no candidate checkout and no signing
secrets. Every comparison is a hard failure: download tooling warnings never replace it.

| ID | When | Check | Pass |
| --- | --- | --- | --- |
| D0 | every publication job, before anything else | **Authenticate the authorization record:** its SHA-256 equals `D7` from `needs.verify.outputs` (never from a downloaded file); `gh attestation verify release-authorization.json` with `--repo mbzbugsy/fidomanager`, `--signer-workflow …/release-macos.yml`, `--signer-digest <workflow sha>`, `--source-digest <commit>`, `--source-ref refs/tags/<tag>` and `--deny-self-hosted-runners`; the certificate's run invocation URI equals `…/actions/runs/<run_id>/attempts/<run_attempt>` from `verify`'s outputs; `policy-check` output is `immutable_releases=true` | all hold; otherwise stop and trust nothing in the record |
| D1 | `publish-draft`, before upload | Re-download the `verify` outputs. Run D0. Recompute every asset's SHA-256 and size against the authenticated record, and `SHA256SUMS` against the record's `sha256sums` digest and then line by line. Check the tuple fields against this run (`github.repository`, tag, tag object, peeled commit, `github.workflow_sha`, run ID) and the `preflight` outputs | all equal |
| D2 | before upload | No release (draft or published) already exists for the tag; the tag still peels to the recorded commit | true |
| D3 | after upload to the draft | Download every asset from the **draft release through the API** into a fresh directory. Run D0 on the downloaded record. SHA-256 and size of each asset equal the authenticated record; the asset name set is exactly the final asset set (payload/evidence, `SHA256SUMS`, authorization record, attestation bundle) | all equal; otherwise stop, and leave the draft unpublished for deletion |
| D4 | `publish-final`, before publishing | Repeat D0–D3 against the draft as it is now | all equal |
| D5 | after publishing | Download the **published** authorization record and run D0 on it; `gh release verify <tag>` (release exists and is immutable) and the release object's `immutable` field is `true`; `gh release verify-asset <tag> <file>` for every asset; one more API download with digest comparison against the authenticated record; the tag still peels to the recorded commit | all pass; any failure starts the ADR-017 §11 incident procedure |

## Part E — signing-boundary and publication-root negatives (no credentials)

These run in the signer repository's own test suite (N1–N7) and in the credential-free rehearsal on
a fork or throwaway repository (N8–N14), before any real credential exists. Every case must fail
closed, with nothing extracted, signed, uploaded or published.

| ID | Case | Expected |
| --- | --- | --- |
| N1 | `build-output.tar` with an absolute path, a `..` component, an empty component, a `.` component, a backslash or a control character | rejected before any write (ADR-017 6.5) |
| N2 | Archive containing a symlink, a hard link, a character or block device, a FIFO, or a pax/GNU extended header | rejected before any write |
| N3 | Duplicate paths, a case-only collision (`Info.plist` and `info.plist`), a Unicode-normalization collision, and a file and directory with the same path | rejected before any write |
| N4 | Archive over 256 MiB, over 1024 entries, or whose files sum to over 256 MiB | rejected before any write |
| N5 | Entry outside `build-output/` or outside the expected layout; setuid, setgid or sticky mode | rejected before any write |
| N6 | Candidate directory pre-seeded with a symlink at a path the archive contains (simulates a non-fresh directory) | the driver refuses: it only ever extracts into a directory it just created, and `O_NOFOLLOW`/`O_EXCL` stop the write |
| N7 | Valid archive whose bundle already contains `release-worker-identity.json` or the `Info.plist` digest key | rejected at the data-only pre-checks |
| N8 | Replace the draft's authorization record **and** all assets consistently with a self-made set | D0 fails: the SHA-256 differs from `D7` in job outputs, and the attestation does not verify for this run |
| N9 | Authorization record attested by a different run, a different attempt, a different workflow file or SHA, or a different commit | D0 fails on the certificate constraints |
| N10 | `SHA256SUMS` edited to match a tampered asset | the record's `sha256sums` digest no longer matches; stop |
| N11 | `policy-check` with immutable releases disabled (`404`), with the App key missing, and with a token lacking Administration: read | the job fails; `publish-draft` does not run |
| N12 | Tag whose commit has a failed, missing or pending `CI` run (`validation`, `macos-native-auth` or `macos-packaging`) | `preflight` stops the run |
| N13 | Lightweight tag; tag on a commit not on `main`; tag version ≠ version files; a release already existing for the tag | `preflight` stops the run |
| N14 | Workflow with an unpinned `uses:` or a checkout without `persist-credentials: false` | `preflight` stops the run |

## What is out of scope here

- Windows and Linux packaging.
- Any updater.
- Universal or x86_64 builds, unless they ship (M7.1 packages arm64 only).
- Licence notices for Rust crates and frontend packages. The packaged notices file covers the
  native libraries only (M7.1 gate 5); this plan checks that file, not wider coverage.
- Hardware mutation of any kind, and M6/Reset.
- Protection against deliberately installing an older **complete** release (B22 documents the
  behaviour only).
