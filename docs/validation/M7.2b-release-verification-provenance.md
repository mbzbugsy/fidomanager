## Candidate checker contract

Run only in unprivileged Build/Verify, with a stable, privately staged bundle and trusted Apple
OS tools on PATH. **Never run this candidate script in the credential-bearing signing job**,
even with `--no-execute-worker`: the separate, pinned driver must perform its own data checks.
The default worker startup and hostile-OpenSSL probe still execute in Build/Verify, only after
release metadata/signature/staple/DMG checks succeed.

Example for the future secret-free Verify job (values must come from trusted release context):

```sh
python3 scripts/check-macos-bundle.py '/absolute/staging/Fido Manager.app' \
  --signature developer-id \
  --expected-team-id "$EXPECTED_TEAM_ID" \
  --expected-commit "$PEELED_COMMIT" \
  --stapled --pre-staple-cdhashes /absolute/evidence/pre-staple-cdhashes.json \
  --dmg /absolute/assets/FidoManager-X.Y.Z-arm64.dmg \
  --frontend-dist /absolute/build/dist
```

`--expected-team-id` is required, ten uppercase letters/digits; `--expected-commit` is required,
40 lowercase hex. Neither is inferred from the candidate. Version comes from the reviewed
checkout's Tauri configuration. The pre-staple evidence is a local input adapter for the pinned
driver's observations, not a new release asset/protocol:

```json
{
  "fidomanager-app": { "arm64": "<40 lowercase hex>" },
  "fido-worker": { "arm64": "<40 lowercase hex>" },
  "dmg": "<40 lowercase hex>"
}
```

Omit `dmg` only when no DMG is being checked. All keys are exact. Both executable cdhashes and,
when supplied, the DMG cdhash must be unchanged from these pre-staple observations. Missing
evidence fails `--stapled`. Do not derive these values anew from the stapled candidate.

The Developer ID mode enforces:

- Exact signing identifiers, expected Team ID, Developer ID Application leaf bearing that Team ID,
  Developer ID Certification Authority, Apple Root CA, zero entitlements, and exactly the reviewed
  Hardened Runtime flags on both executables. Apple tools verify the signatures; text fields alone
  are not a signature verifier.
- Secure `Timestamp=` evidence, nonempty and parseable in the supported English codesign date
  forms. A `Signed Time=` field is never a trusted timestamp. Commands request the C locale.
- Explicit Apple-anchored Developer ID publisher requirements for app and worker, and the exact
  worker cdhash requirement. Default designated requirements are parsed as boolean expressions;
  substring matching cannot allow an attacker to append a weakening OR clause. Only ADR-017's
  Developer ID clauses, and its documented optional default Mac App Store alternative, are
  accepted. The separate explicit requirement always excludes Store-signed code.
- Deep strict bundle verification and evidence that Info.plist and resources are signature-bound.
  Duplicate plist dictionary keys fail. The checker statically verifies the on-disk bundle;
  it does **not** prove M7.2a's runtime secured-plist API semantics (E16).
- One ≤4 KiB UTF-8 identity-record buffer, authenticated by its **exact byte** SHA-256 against
  `FidoManagerReleaseWorkerIdentitySHA256` before parsing. Duplicate/unknown/missing fields,
  non-finite JSON, wrong release/Team ID/path/identifier/build ID, malformed hashes, unsupported
  slices and multiple architectures fail. The worker's whole-file SHA-256, CDHash and full SHA-256
  code-directory hash must agree with the record; the short hash must be the full hash's prefix.
- Exactly one complete enforcing marker with the expected Team ID/version/commit. The worker
  embeds the matching version-plus-commit build identity. Byte markers are consistency checks,
  not proof that arbitrary code implements the enforcement policy.
- Original M7.1 floor, symbols, private OpenSSL directory, exact worker system dependencies,
  no Frameworks, exact two-Mach-O set, reviewed icon and notices, and frontend checks. The Mach-O
  magic check also recognizes 32-bit and fat64 headers so extra code cannot hide as a resource.
- No bundle symlinks, hardlinked files, special files, unexpected directories or files. The identity
  record is allowed only in Developer ID mode. `Contents/CodeResources` is allowed **and required**
  only with `--stapled`; the ticket never replaces `_CodeSignature/CodeResources`.
- Stapled app/DMG: `stapler validate`, Gatekeeper accepted with `Notarized Developer ID`, plus
  the app's expected publisher origin. Unstapled mode makes no notarization assertion.
- Optional Developer ID DMG: expected `.dmg` signing identifier, Team ID/chain/timestamp and
  requirement, no entitlements, UDZO format, `hdiutil verify`, read-only/no-auto-open mounting,
  exact root `{Fido Manager.app, Applications}`, exact `/Applications` symlink target, bundle
  tree checks, and byte/mode equality with the checked standalone app. Detach runs on failure.
  Hidden extra files are not silently ignored.

Ad-hoc mode requires neither Team ID nor commit. It rejects the release record, RID plist key,
ticket and release-only staple/DMG options. Existing unsigned DMG packaging still uses its
established ad-hoc path. No validation is relaxed to accept signed release fixtures.

The checker summary's `code_evidence` object is the provenance input below (null for ad-hoc).
It contains Team ID, record binding, both file digests and cdhashes, system dependencies, and DMG
cdhash. A release provenance invocation requires the complete evidence including DMG.

## Provenance inputs and trust boundary

`release-provenance.py` is standard-library Python. It runs no candidate executable in
`generate`/`verify`, makes no network request, signs nothing, and creates no attestations.
`collect-sbom` runs Cargo commands in the unprivileged Build job only.

The caller must authenticate Build/signing handoffs against trusted `D0`/`D0s`/driver outputs
before using them. Use canonical absolute paths and fresh private staging directories: evidence
reads reject symlinks, including path ancestors, hardlinks, non-regular files and oversized input.
The tools assume no concurrent mutation of that staging directory; they are not a filesystem
snapshot or sandbox against a concurrent same-user attacker.

| Input | Origin and contents |
| --- | --- |
| `--context` | Trusted preflight/run outputs; exactly the §7.6 authorization fields `repository`, `tag`, `tag_object_sha`, `commit_sha`, `version`, `arch`, `deployment_target`, `eligibility`, `workflow`, `signer`. Never populate from a downloaded authorization record. |
| `--manifest-input` (generation only) | §9.1 manifest fields except `native`, `artifacts`, `sbom`, which the tool derives. Build tool observations and signing/notarization/digest-chain facts come from authenticated build/driver evidence. No success values are filled in by default. |
| `--sbom-inputs` | Output of `collect-sbom`; authenticate this Build handoff before Verify. |
| `--build-identity` | Exact native `build-identity.json` from the verified private archives. |
| `--package-summary` | Exact unsigned Build `package-summary.json`, not a summary rewritten after signing. |
| `--code-evidence` | `code_evidence` from successful candidate checker verification, including the DMG; keep outside the asset directory. |
| `--assets` | Initially exactly final stapled DMG, final stapled app ZIP, `notary-app.json`, `notary-dmg.json`, named as in ADR-017. Payload creation and credentialed verification are separate gates. |

The authorization context is validated for repository/workflow/signer pins, tag-version agreement,
commit/workflow SHA agreement, exact three successful CI check names and positive distinct IDs,
positive run/attempt, on-main and enabled immutable-release policy. These are **consistency checks
on trusted input**, not API queries proving those assertions.

The native manifest is derived from source locks and build identity; package-summary values must
agree. It binds exact input-file digests, archive hashes, versions/commits, source/patch hashes,
licenses, compiler/SDK, native-only notices, deterministic controls, static OpenSSL policy and
libcbor LTO policy. Manifest Node/pnpm/Tauri values must match repository pins; native/app SDK
observations must agree. Native license files are hashed, with OpenSSL/libcbor compared to locks.

Code evidence must agree with manifest Team ID, both cdhashes and exact worker/RID binding.
`D1` is the worker file SHA-256; final app ZIP/DMG bytes bind `D3`/`D5`. Notary logs must identify
the expected submissions, report Accepted and no issues (warnings fail), match `D2`/`D4`, and
include all expected code identities, including DMG identity. This implementation fails closed
if the empirical `sha256`/ticket fields are missing; it does not guess the ADR's alternate
submission-ID evidence. D0/D2/D4 are authenticated upstream observations, not hashes independently
recomputed here from unavailable intermediate payloads. Logs supplied as JSON do not themselves
prove Apple issued a ticket.

### SBOM collection and generation

After the production frontend build:

```sh
python3 scripts/release-provenance.py collect-sbom \
  --target aarch64-apple-darwin \
  --frontend target/macos-package/frontend-sbom-inputs.json \
  --output target/macos-package/sbom-inputs.json
```

The Vite plugin records only packages contributing rendered modules to emitted chunks and hashes
all final output files after HTML emission. It writes to `target/macos-package`, not `dist` or the
bundle. A development dependency such as Svelte is included when its runtime code is shipped;
CLI/build-only packages are not included merely because they are installed. Package versions are
cross-checked against the pinned pnpm v9 lock's package entries. Cargo metadata plus the locked,
normal-only target closure for each executable supplies Rust components and reported licenses;
identities/source checksums are cross-checked against Cargo.lock. Ambiguous duplicate-source
package identities fail rather than being guessed. Unknown lock formats require a reviewed parser
update.

The output is [CycloneDX 1.6](https://cyclonedx.org/schema/bom-1.6.schema.json), deterministic
without a wall-clock timestamp or random UUID. Per-executable closure membership is explicit;
this does not invent individual transitive dependency edges. App and worker have final file hashes;
the worker additionally has native components with source/archive/patch/license evidence.
System libraries/frameworks are external, unversioned components (`scope: excluded`). Legacy
slash-separated Cargo license declarations are preserved as license names, not invalid SPDX
expressions. License inventory does not close the Rust/npm redistribution-notices gate.

### Acyclic generation and independent verification

```sh
python3 scripts/release-provenance.py generate \
  --assets /absolute/assets --context /absolute/evidence/context.json \
  --manifest-input /absolute/evidence/manifest-input.json \
  --sbom-inputs /absolute/evidence/sbom-inputs.json \
  --build-identity /absolute/evidence/build-identity.json \
  --package-summary /absolute/evidence/package-summary.json \
  --code-evidence /absolute/evidence/code-evidence.json
```

All inputs and consistency checks pass before writing. Outputs use deterministic sorted-key UTF-8
JSON with a final newline. Exclusive creation prevents overwriting an existing output. Partial
I/O failure requires a fresh staging directory; it never produces a success/D7 report.

1. SBOM, then manifest (which names the SBOM digest).
2. `SHA256SUMS` over exactly six payload/evidence assets: DMG, app ZIP, SBOM, manifest, two logs.
3. Authorization schema `fidomanager.release-authorization/2`, written last, binds those six
   assets' SHA-256 and size plus the exact `SHA256SUMS` bytes.
4. Print `D7=<SHA-256 of authorization bytes>` for the future Verify job output.

Neither digest file hashes itself; `SHA256SUMS` never lists the authorization record. The later
attestation bundle is outside both digest files, exactly as ADR-017 §7.6 requires.

```sh
python3 scripts/release-provenance.py verify \
  --expected-d7 "$D7_FROM_TRUSTED_VERIFY_JOB_OUTPUT" \
  --assets /absolute/downloaded-assets --context /absolute/evidence/context.json \
  --sbom-inputs /absolute/evidence/sbom-inputs.json \
  --build-identity /absolute/evidence/build-identity.json \
  --package-summary /absolute/evidence/package-summary.json \
  --code-evidence /absolute/evidence/code-evidence.json
```

Verification first compares authorization bytes with externally supplied D7, then compares its
context with the independent preflight/run context, checks the exact asset set, and reconstructs
the expected SBOM/manifest/checksums/authorization from evidence and actual assets. Every generated
file must match exactly. Replacing assets, checksums and authorization together cannot supply its
own trusted D7. Recomputing hashes also cannot excuse inconsistent native/SBOM/code evidence.

Use `--with-attestation` only for the final nine-file asset set; it requires exactly the additional
`release-attestations.sigstore.jsonl`. **That flag does not authenticate the attestation.** The
future independent publisher must still perform ADR-017 §7.6 root-of-trust steps 2–3: verify
Sigstore/GitHub provenance constrained to workflow, commit, source ref and hosted runner, and check
the verified certificate's exact run-invocation URI/attempt. The JSON field path remains a rehearsal
gate. These candidate tools are not the trusted signing driver or a checkout-free publication job.

app/worker build plus packaged-worker test cover the affected integration.

## Negative coverage

- Wrong/missing Team ID and chain; wrong leaf/signing identifier; malformed/missing/duplicate
  Timestamp and Signed-Time-only output; bad runtime flags; entitlements; failed explicit or deep
  verification; altered/weakened/unbalanced/ambiguous designated requirements.
- Missing, oversized, malformed, non-UTF-8, duplicate-key, unknown-field or altered identity record;
  wrong release/build ID, worker whole-file or either code-directory hash; RID missing/malformed/
  wrong digest; duplicate plist key; missing/malformed/conflicting/wrong-team/version/commit marker.
- Extra resources/directories, symlinked records, missing or directory-shaped staple, ticket in
  unstapled/ad-hoc bundles, changed pre-staple cdhash; failed stapler/Gatekeeper; substituted DMG
  app, extra root entry or wrong Applications link, with detach checked on failure. Invalid
  release evidence cannot reach worker execution.
- Each provenance asset tampered independently; incorrect/absent D7; wholesale record replacement;
  record schema/tuple/asset-set/size/hash/worker/submission mismatch; modified checksums; a forged
  SBOM with consistently rewritten manifest/checksums/authorization; symlink/hardlink inputs;
  missing/extra assets; false eligibility; wrong source/native/lock/tool pins; inconsistent code
  evidence; warnings/rejected/missing/incorrect notary-log bindings; refusal to overwrite outputs.
- Existing M7.1 ad-hoc tree, linkage, permissions, deployment-floor, symbols, notices, entitlements,
  seal and runtime checks remain covered by the real package suite.

## Open gates and remaining M7.2b work

1. **Separate signing driver/repository** (ADR-017 §12 step 6): protected full-SHA pin, safe handoff
   extraction, no candidate execution, data prechecks, ephemeral keychain, inside-out signing,
   canonical identity record/plist insertion, real notarization/stapling, D0–D6 and driver report.
   None is created or claimed here.
2. **Release packaging flavor and protected workflow integration**: M7.2a's optimized enforcing
   build still cannot compile until the real reviewed Team ID is provisioned. Add the packager's
   release mode, release-macos workflow, policy-check/preflight, authenticated D0/D0s handoffs,
   exact tagged build/features, independent publication checks and trusted D7 propagation.
   Input adapters above must be wired to actual driver/build outputs, not handwritten claims.
3. **Attestations/publication**: genuine GitHub attestations and exact certificate run binding,
   immutable policy API evidence, exact `draft_release_id` handling, release re-downloads,
   fork/throwaway fail-closed rehearsal, clean-machine approval and final immutable publication.
   Local `verify` alone authorizes none of these actions.
4. **Real Apple empirical gates**: E1 (actual DR/chain/timestamp wording), E11 (log/ticket schema),
   E12 (exact staple layout and cdhash preservation), E13 (DMG/Gatekeeper output and strict mounted
   tree), E16/E17 (runtime secured plist and static-code object), E19 (remove-signature comparison
   proving signed worker equals Build's linked worker). Failures require reviewed changes, never
   bypasses. The current missing-log-field policy is terminal until actual evidence resolves it.
5. **Runtime/platform and release gates**: real enforcing app/worker and negative identities,
   online/offline/translocated macOS 11.0–11.2 and ≥11.3 runs, E3/E4/E7/E14/E15/E20, clean Macs,
   actual previous-release worker rejection, Intel qualification, native/Rust/npm licensing
   decisions and OpenSSL signature review. No runtime or product floor is changed by this slice.
6. Independent security review of this implementation and the final integrated release evidence.

No release gate is closed by synthetic credentials, signed-looking text, local digest agreement
alone, or the presence of an unauthenticated attestation file.
