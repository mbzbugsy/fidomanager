# M7.1 — Pinned private static macOS native dependencies

Status: **packaging hardening only.** The worker now links libfido2, OpenSSL (libcrypto) and
libcbor as private static archives, all built from checksum-pinned upstream source. The packaged
`Fido Manager.app` contains no third-party dylibs and no `Contents/Frameworks`. The artifact is
still **not** a release: it is ad-hoc sealed only, not Developer ID signed, not notarized and not
stapled.

Base: `main` at `d32dcd60fd37cd0bae4702a92447251b709d91dc` (PR #31 / M7.0 merged). M6 Reset is
untouched. No Apple credentials were used, and no authenticator was touched.

The pins live in `native/openssl/source.lock.json` and `native/libcbor/source.lock.json`. The

**Why these versions.**

- **OpenSSL 3.5.9.** The latest 3.5 LTS patch release (29 Sep 2026), supported until 2030-04-08.
  The other series do not fit:
  - 3.6 reaches end of life on 2026-11-01.
  - 3.4 reaches end of life on 2026-10-22.
  - 4.x is a new major series. Its API/ABI changes (engine removal and others) have not been
    reviewed against libfido2 1.17.0, which builds with `OPENSSL_API_COMPAT=0x10100000L`.

  The archive SHA-256 equals the upstream-published `openssl-3.5.9.tar.gz.sha256`. The release
  tarball's pax comment names commit `45e844fa…`, which is the peeled `openssl-3.5.9` tag. The PGP
  signature was not verified locally (no `gpg`); the pinned SHA-256 is the enforced gate.
- **libcbor 0.14.0.** The latest stable release, and the version libfido2 1.17.0 was already built
  and tested against in M3/M7.0 (Homebrew 0.14.0). It also contains upstream overflow and NULL
  fixes (`cbor_copy_definite`, `cbor_array_get` bounds, streaming `claim_bytes`). The codeload
  archive is addressed by commit, not by the mutable tag, and is checksum-pinned.

Nothing resolves "latest" at build time. Upgrading means editing a lock, its SHA-256 and the
reviewed `LICENSE.upstream`, followed by review.

## 2. Fetch and extraction policy (`scripts/build-native-deps.py`)

- `python3 scripts/build-libfido2.py fetch` fetches libfido2 (unchanged path), then OpenSSL and
  libcbor.
- Downloads are HTTPS only. A redirect handler refuses non-HTTPS redirects (GitHub release assets
  redirect once). The `Content-Length` and the streamed byte count are both bounded.
- A download lands in a private temporary file. It is published to `target/native-sources/` only
  after the SHA-256 matches. A cached archive is re-verified (size and digest) before every use.
  Homebrew source caches are never consulted.
- The strict extractor accepts only regular files and directories under exactly the pinned root.
  It rejects, before writing anything outside the destination:
  - a wrong or extra root, or a root that is a file
  - absolute paths, `..`, `.`, empty components and backslashes
  - symlinks, hard links, character and block devices, and FIFOs (link targets are never followed)
  - duplicate entries (files are created with `O_EXCL`)
  - entry-count, total-size and download-size overruns
  - missing required files and unexpected version markers (`VERSION.dat`, the
    `project(libcbor VERSION 0.14.0 …)` line)
  - a license that differs from the reviewed `LICENSE.upstream`
- The libfido2 source extractor, checksum, reviewed patch checksum, upstream/patched `credman.c`
  digests and `git apply` exactness are **unchanged**.

## 3. Private build configuration

All three builds share an **explicit environment allowlist**: `PATH HOME TMPDIR USER LOGNAME
SHELL LANG SDKROOT DEVELOPER_DIR`, plus `ZERO_AR_DATE=1`, `SOURCE_DATE_EPOCH`, `LC_ALL=C`,
`MACOSX_DEPLOYMENT_TARGET=11.0` and `SDKROOT=$(xcrun --sdk macosx --show-sdk-path)`. This replaces
the M3 denylist. `CC`, `CFLAGS`, `CPATH`, `LIBRARY_PATH`, `PKG_CONFIG_*`, `OPENSSL_*`, `CMAKE_*`,
`MAKEFLAGS`, `CROSS_COMPILE`, `DYLD_*` and similar variables never reach a native build. Each
Cargo build-script invocation builds all three libraries fresh from verified source; there is no
dependency cache. A full private native build takes about 25 s on an M-series Mac.

Targets: `aarch64-apple-darwin` (`arm64`) and `x86_64-apple-darwin` (`x86_64`), with deployment
target **macOS 11.0** for both.

### OpenSSL 3.5.9 (`libfidomanager_crypto.a`)

```text
perl Configure darwin64-arm64|darwin64-x86_64 CC=<xcrun clang>
  --prefix=/var/empty/fidomanager-openssl --openssldir=/var/empty/fidomanager-openssl --libdir=lib
  no-shared no-module no-engine no-dso no-autoload-config
  no-legacy no-apps no-tests no-docs no-ui-console
  -mmacosx-version-min=11.0
make build_generated libcrypto.a
```

- All five policy switches were checked against the 3.5.9 `Configure` disablables before use.
  After configuring, the builder reads `configdata.pm` and requires `shared`, `module`, `engine`,
  `dso` and `autoload-config` to be disabled. It also requires `OPENSSL_NO_AUTOLOAD_CONFIG`,
  `OPENSSL_NO_DSO` and `OPENSSL_NO_ENGINE` in the generated `configuration.h`.
- The extra switches only drop products the worker never uses. Deprecated APIs stay enabled
  because libfido2 needs them.
- `OPENSSLDIR`, `ENGINESDIR` and `MODULESDIR` compile to `/var/empty/fidomanager-openssl…`.
  `/var/empty` is root-owned, and a user cannot create anything under it. The archive must contain
  that exact `OPENSSLDIR` and must not contain `/usr/local/ssl`, `/opt/homebrew` or the build path.
- **No implicit configuration and no loadable modules (runtime proof from the archive itself).**
  The builder links a probe against the fresh archive. It also builds a hostile would-be provider
  dylib whose constructor creates a marker file. The probe runs with all of the following:
  - `OPENSSL_CONF` pointing at a config that sets `default_properties = fips=yes` and activates
    that dylib as a provider
  - `OPENSSL_MODULES`, `OPENSSL_ENGINES` and `OPENSSL_CONF_INCLUDE` pointing at a hostile
    directory
  - a working directory containing `openssl.cnf`, `legacy.dylib`, `fips.dylib` and
    `default.dylib`

  Required results:
  - Default init fetches SHA-256 and reports `OpenSSL 3.5.9 …` and
    `OPENSSLDIR: "/var/empty/fidomanager-openssl"`, so nothing was loaded.
  - The positive control explicitly calls `OPENSSL_init_crypto(OPENSSL_INIT_LOAD_CONFIG)` with the
    same file, and that call or the fetch fails. This proves the config would have mattered.
  - An explicit `OSSL_PROVIDER_load(NULL, "hostile")` fails.
  - The marker never appears.

  **Sensitivity check (one-off, local):** the same probe and fixtures linked against Homebrew's
  module-capable OpenSSL autoloaded the hostile config and `dlopen`ed the dylib (marker created),
  and its fetch failed. So the probe detects exactly the behavior the private build excludes.

  The property comes from the build, not from runtime environment handling. (The probe is skipped,
  and recorded as skipped, for cross-architecture builds.) Neither libfido2 nor the Rust worker
  calls any config-loading API.
- The **Configure target is verified after configuring**. The `$config{target}` in `configdata.pm`
  must equal the target derived from the Rust target. `./config` and host inference are never
  used. The pinned `Configurations/10-main.conf` defines `darwin64-arm64-cc` and
  `darwin64-x86_64-cc` as pure "historic aliases" (`inherit_from => [ "darwin64-arm64" ]`, and
  the same for x86_64). The canonical names are passed, and `test-native-deps.py` asserts the
  alias equivalence in the pinned source.
- **Embedded build identity.** OpenSSL embeds `built on: <SOURCE_DATE_EPOCH as UTC>`, which the
  builder verifies (`Wed Jun 17 00:00:00 2026 UTC`). It also embeds `compiler: $(CC)
  $(LIB_CFLAGS) $(CPPFLAGS)`. For that reason **no `-ffile-prefix-map` is passed to OpenSSL**: the
  in-tree build compiles relative source paths, so there is nothing to map, and an absolute
  mapping would itself put the build path into libcrypto. The archive check instead fails if the
  build directory appears anywhere in the archive. libcbor and libfido2 (CMake, absolute paths) use
  `-ffile-prefix-map` for their source and build directories.
- The built archive contains 988 objects. Every member must be a real Mach-O object of the target
  architecture with `minos 11.0`.

## 4. Private libfido2 integration

- `build-libfido2.py build` first builds the private OpenSSL and libcbor into the same output
  directory. It then configures libfido2 with `PKG_CONFIG_LIBDIR=<private .pc dir>`; the
  environment allowlist drops `PKG_CONFIG_PATH`, `PKG_CONFIG_SYSROOT_DIR` and `CMAKE_PREFIX_PATH`.
  CMake also gets `-DCMAKE_FIND_USE_CMAKE_SYSTEM_PATH=OFF` and
  `-DPKG_CONFIG_USE_CMAKE_PREFIX_PATH=OFF`. The upstream CMake's `pkg_search_module` therefore
  sees **only** the generated `libcrypto.pc` (3.5.9), `libcbor.pc` (0.14.0) and a `zlib.pc` for
  the macOS SDK's system zlib. No Homebrew/system `.pc` file is visible.
- Before configuring, the builder runs pkg-config exactly as CMake will. Every file-backed package
  must be one of those three files in the private directory. Only pkgconf's two built-in,
  file-less virtual entries (`pkg-config`, `pkgconf`) are tolerated. Each package's `--cflags`
  and `--libs` must not mention `/opt/homebrew`, `/usr/local` or `/opt/local`.
- **OpenSSL API compatibility (proven, not assumed).** libfido2 1.17.0's `CMakeLists.txt` adds
  `-Werror` and, only `if(CRYPTO_VERSION VERSION_GREATER_EQUAL 3.0)`,
  `-DOPENSSL_API_COMPAT=0x10100000L`. The private `.pc` supplies `Version: 3.5.9`. The builder
  requires every libfido2 compile command to carry `-DOPENSSL_API_COMPAT=0x10100000L`, `-Werror`
  and `-I<private include>`, and none to mention an external prefix. A permanent regression control
  in `test-libfido2.py` presents the same private OpenSSL as `1.1.1`. The define then disappears and
  libfido2's own build fails (locally: 42 `[-Werror,-Wdeprecated-declarations]` errors), so the
  version knowledge is load-bearing.
- After compiling, the builder checks the outcome:
  - `CMakeCache.txt` must show `CRYPTO_VERSION=3.5.9` and `CBOR_VERSION=0.14.0`, the private
    include directory, the private library directory, and the `fidomanager_crypto` /
    `fidomanager_cbor` library names.
  - Every compiler dependency file (`*.o.d`) of the `fido2` target must reference headers only from
    the libfido2 source, the build tree, the private include directory, the SDK or the clang
    resource directory.
  - `openssl/opensslv.h` and `cbor.h` must resolve to the private include directory.

  Any `/opt/homebrew` or `/usr/local` header fails the build.
- The libfido2 archive is now also checked for Mach-O objects at `minos 11.0`.
- Unchanged:
  - source and patch checksums
  - the bounded credential-management patch and its upstream/patched digests
  - the production `FIDO_FUZZ` check
  - the `fidomanager_libfido2_1_17_0_credman_limit` identity symbol
  - the `LIBFIDO2_LIB_DIR` refusal

Cargo (`crates/fido-libfido2/build.rs`):

- No `pkg-config` at all on macOS. The only native search path is the private output directory.
- Links `static:-bundle=` `fidomanager_fido2_bounded`, `fidomanager_cbor` and `fidomanager_crypto`,
  plus system `z`, CoreFoundation and IOKit. Because the archive names are project-unique, no
  Homebrew/system `libcrypto`/`libcbor` can satisfy these requests.
- The M3 `validated_pkg_config_libdir` helper and its unit test were removed with the pkg-config
  lookup they guarded.

`crates/fido-h0-timing/build.rs` links the same private libfido2 archive. It received the same
**linkage-only** change: private libcrypto/libcbor archives instead of pkg-config. Its
measurement code, reset-object exclusion and link-map test are unchanged and still pass.

Linux keeps its discovery-only system-library policy.

## 5. Link-map provenance (`scripts/verify-libfido2-linkage.py`)

The existing libfido2 checks stay: the identity symbol, 16 credman symbols, `fido_dev_set_pin`
and `fido_credman_del_dev_rk` attributed to the exact private archive objects. The verifier now
also proves:

1. **Exact linker input allowlist.** Every input in the ld64 map is one of:
   - Cargo output under the profile's `deps/`
   - Rust's own `lib/rustlib` rlibs
   - an SDK `.tbd` stub from the reviewed set (`libz`, `libiconv`, `libSystem` and its
     `usr/lib/system/*` re-exports, `libc`, `libm`, CoreFoundation, IOKit)
   - one of the three private archives

   Any other archive, dylib or stub fails, including a Homebrew `libcrypto.3.dylib`, a Homebrew
   `libcbor.a`, a stray `libcrypto.a` in `target/` or an SDK `libcrypto.tbd`. All three private
   archives must contribute objects.
2. **Symbol attribution.** Every live symbol whose name the private OpenSSL or libcbor archive
   defines must be attributed to an object of that archive, and the worker must import none of
   them. This addresses "the linker could have chosen another static archive": a same-named
   definition from anywhere else fails. Release worker evidence:

   | Archive | Objects linked | Live symbols attributed |
   | --- | --- | --- |
   | libfido2 | 33 | 200 |
   | libcbor | 19 | 176 |
   | libcrypto | 794 | 8950 |
3. `build-identity.json` dependency entries must match the locks and the actual archive SHA-256s.
   The OpenSSL entry must record the policy switches, the private `OPENSSLDIR`, the Configure
   target matching the worker architecture and the runtime-independence probe result. The
   libfido2 entry must record `openssl_api_compat = 0x10100000L`.

`scripts/test-credman-linkage.py` adds 12 synthetic negative controls for these rules: Homebrew
dylib/archive, stray archive, SDK libcrypto stub, stub outside the SDK, foreign rlib, missing
libcbor objects, OpenSSL symbols from another object, libcbor symbols from the libfido2 archive,
dynamically resolved OpenSSL/libcbor, and dead-stripped-only objects.

## 6. Packaging (`scripts/package-macos.py`)

The M7.0 relocation is removed entirely: no dylib discovery, no copy into `Contents/Frameworks`,
no `install_name_tool`, and no Homebrew bottle provenance. The packager now:

1. Refuses signing, notarization and override variables (unchanged).
2. Builds a clean release worker with `MACOSX_DEPLOYMENT_TARGET=11.0`.
3. Runs the full link-map verification above on the **release** worker.
4. Fails if the worker has any non-system dependency, or a `minos` above 11.0. It **never raises
   the floor to fit a dependency**.
5. Runs `tauri build` with `minimumSystemVersion` fixed to 11.0.
6. Checks that the bundled worker is byte-identical to the verified one, and that Tauri created no
   `Frameworks`.
7. Copies `THIRD_PARTY_NOTICES.md` into `Contents/Resources/`.
8. Signs ad-hoc, inside-out. The signer now refuses any `Contents/Frameworks` or nested code
   outside `Contents/MacOS`.
9. Runs the structural checks, then builds and re-checks the DMG.
10. Records the native dependency provenance in `package-summary.json`.

Bundle (local and CI):

```text
Fido Manager.app/
  Contents/
    Info.plist                       LSMinimumSystemVersion 11.0
    MacOS/
      fidomanager-app                minos 11.0, system frameworks only
      fido-worker                    minos 11.0, static libfido2 + OpenSSL + libcbor
    Resources/
      icon.icns
      THIRD_PARTY_NOTICES.md         byte-identical to the repository copy
    _CodeSignature/CodeResources     ad-hoc seal
```

`Contents/Frameworks` does not exist.

Final worker (`otool -L "…/Contents/MacOS/fido-worker"`):

```text
/usr/lib/libz.1.dylib
/System/Library/Frameworks/CoreFoundation.framework/Versions/A/CoreFoundation
/System/Library/Frameworks/IOKit.framework/Versions/A/IOKit
/usr/lib/libiconv.2.dylib
/usr/lib/libSystem.B.dylib
```

Non-system dependencies: **none**. There is no dynamic libfido2, libcrypto or libcbor, and no
Homebrew, `/usr/local`, `@rpath`, `@loader_path` or `@executable_path` load. The worker has no
`LC_RPATH` and no `LC_DYLD_ENVIRONMENT`, and its dynamic loader is `/usr/lib/dyld`. OpenSSL
obtains entropy through the system `CCRandomGenerateBytes` (libSystem/libcommonCrypto).

## 7. Structural checker (`scripts/check-macos-bundle.py`)

New or strengthened for M7.1:

- `Contents/Frameworks` must not exist. The Mach-O set is exactly `fidomanager-app` and
  `fido-worker`.
- Every dependency of both executables is a system path. Forbidden anywhere: `/opt/homebrew`,
  `/usr/local`, `/opt/local`, `libfido2`, `libcrypto`, `libssl`, `libcbor`, `@rpath`,
  `@loader_path`, `@executable_path`.
- No `LC_RPATH` or `LC_DYLD_ENVIRONMENT`, and the dynamic loader must be exactly `/usr/lib/dyld`.
  The worker's system set stays the explicit five-entry allowlist.
- **Worker symbols:**
  - No undefined `fido_`, `fidomanager_`, `cbor_`, `EVP_`, `OPENSSL_`, `OSSL_`, `CRYPTO_`, `ERR_`,
    `BN_`, `EC_`, `ECDSA_`, `ECDH_`, `RSA_`, `HMAC` or `RAND_` symbols.
  - Static definitions of the libfido2 identity symbol, `fido_init`, `fido_dev_get_puat`,
    `cbor_load`, `cbor_serialize_alloc`, `EVP_sha256` and `OPENSSL_init_crypto`.
  - No Homebrew or default OpenSSL directory strings. Any embedded `OPENSSLDIR`, `ENGINESDIR` or
    `MODULESDIR` must be the private `/var/empty/fidomanager-openssl`.
- **Deployment floor:** every `minos` must be at most `LSMinimumSystemVersion`, and
  `LSMinimumSystemVersion` must equal the declared 11.0.
- **Notices:** `Contents/Resources/THIRD_PARTY_NOTICES.md` must exist and match the repository copy
  byte for byte.
- **Worker under hostile OpenSSL inputs:** the bundled worker is started with `OPENSSL_CONF`,
  `OPENSSL_MODULES`, `OPENSSL_ENGINES` and `OPENSSL_CONF_INCLUDE` pointing at a hostile fixture.
  Its working directory contains an `openssl.cnf` that activates a marker-writing provider dylib,
  plus `legacy.dylib`, `fips.dylib` and `default.dylib` copies. It must exit orderly (0) and the
  marker must not exist. This runs on the app and again on the mounted DMG.

  Limit: the credential-free worker does not initialize OpenSSL before a protocol request, and
  reaching OpenSSL without an authenticator would require device discovery. So this check proves
  **startup** independence. libcrypto's own independence is proved by the archive probe (section
  3) on the exact archive that the link map attributes into this worker (section 5).

  `DYLD_*` injection is out of scope for M7.1. Hardened Runtime under Developer ID (M7.2) blocks
  it, and the app already spawns the worker with a cleared environment.

The bundle bytes alone cannot show which static archive the linker used. That provenance is the
link-map verification of the exact release worker (section 5), which the packager runs before
bundling and CI re-runs explicitly.

`scripts/test-macos-bundle-check.py` now mutates 33 copies of the real bundle and requires each to
be rejected for its intended reason. The M7.1 additions are:

- an empty `Frameworks` directory, and a dylib in `Frameworks`
- Homebrew `libcrypto`, `/usr/local` `libcbor`, `@rpath` `libcbor`, `@loader_path` `libfido2` and
  M7.0-style `@executable_path/../Frameworks/libcrypto` load commands
- a non-system absolute dependency
- `LC_DYLD_ENVIRONMENT` injection
- a dynamically resolved libcbor symbol
- a worker without static OpenSSL
- a Homebrew `OPENSSLDIR` compiled in
- a worker `minos` raised to 12.0, and `LSMinimumSystemVersion` raised to 12.0
- missing or altered notices
- a tampered worker after sealing

The signer is also shown to refuse a reintroduced `Frameworks` directory.

reviewed notice. The file is excluded from Prettier so that it stays byte-stable. Scope: native
libraries linked into the worker. Rust crate and frontend package notices are not covered (see
section 12).

## 9. CI

- `macos-packaging` no longer installs `openssl@3` or `libcbor`; it runs `brew install cmake
  pkg-config` for build tools only. Steps:
  1. Fetch the pinned sources.
  2. `test-native-deps.py`.
  3. `package-macos.py --dmg`, which builds the private OpenSSL, libcbor and libfido2, the release
     worker, link-map provenance, the app, the ad-hoc seal, the checks and the DMG.
  4. An explicit step: `verify-libfido2-linkage.py` on the release worker, `otool -L` on the
     packaged worker, and an assertion that `Frameworks` is absent.
  5. The checker regression tests.
  6. The packaged-worker handshake.
  7. A clean tree: `git diff --exit-code`, plus an empty `git status --porcelain
     --untracked-files=all` (offending paths are printed). Python bytecode (`__pycache__/`) is now
     gitignored. Newer Pythons write it beside the importlib-loaded scripts, which the old
     diff-only check could not see.
- `macos-native-auth`: minimal change. It installs `cmake pkg-config libfido2`. Homebrew libfido2
  is kept only for the negative linkage control, and the `openssl@3`/`libcbor` it pulls in stay on
  the runner as an adversarial environment that the private build must ignore.
- `validation` (Linux): unchanged YAML. Its existing `fetch` now also verifies the two new pins.
- Still `permissions: contents: read` and `persist-credentials: false`. No secrets, no artifact
  upload, no publication.

## 12. Remaining gates (M7.2 and later)

1. Developer ID signing with Hardened Runtime in a protected release workflow, `--signature
   developer-id` checks on real output, then notarization and stapling of the app and DMG. Until
   Hardened Runtime is on, `DYLD_*` variables are honored for the ad-hoc worker; the app spawns it
   with a cleared environment.
2. A per-spawn worker code-requirement / Team ID check, or an explicit reviewed decision to rely on
   the seal.
3. Clean-machine (no Homebrew, no Xcode) and quarantined-download validation, Gatekeeper
   first-launch latency, TCC/HID attribution, and actual launch on macOS 11.
4. Universal or x86_64 packaging and CI. The x86_64 native chain builds, but no x86_64 worker is
   linked or packaged.
5. Attribution for Rust crates and frontend packages compiled into the app, if required for
   distribution.
6. PGP verification of the OpenSSL release signature as an additional review step (the SHA-256
   pin remains the gate).
7. M6/reset and hardware-validation gates for M7 proper.
