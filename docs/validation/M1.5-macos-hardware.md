# M1.5 production worker: macOS + Thetis validation

This is the real-hardware gate from issue #5. Everything software can prove is already covered by
`cargo test --workspace --all-targets --locked` (hang, crash, orphan, framing, handshake and
descriptor-hygiene fault injection against real child processes, with a fixture standing in for
libfido2). What those tests cannot show, and this checklist does, is how the **real** libfido2,
macOS HID, and a physical authenticator behave behind the kill boundary.

Run it on a Mac with the Thetis key plugged in. Replace `<WT>` with the checkout you are testing.
Each section says what to expect; record what you actually saw in the table at the end.

## 0. Build and sanity checks

```bash
cd <WT> && git status -sb && cargo build --workspace --locked
```

Expect a clean branch and a successful build that produces both `target/debug/fido-worker` (the
worker) and `target/debug/fidomanager-app` (the app).

```bash
cd <WT> && otool -L target/debug/fido-worker | grep fido2; otool -L target/debug/fidomanager-app | grep fido2
```

Expect exactly one line, from `fido-worker`. The application binary must **not** link libfido2: the
trusted authority never loads native FIDO code.

## 1. Child worker enumerates and reads GetInfo through real libfido2

```bash
cd <WT> && cargo run -p fido-service --example discover
```

Expect `1 device(s)` with `status=Ready`, the Thetis `vendor:product`, a non-empty `aaguid`,
`versions` including `FIDO_2_1` or `FIDO_2_0`, and `transports` containing `usb`. Then:

```bash
pgrep -lx fido-worker || echo "no worker left behind"
```

Expect `no worker left behind`: the example's supervisor kills and reaps its worker on exit.

## 2. Hot unplug/replug invalidates stale handles

```bash
cd <WT> && cargo run -p fido-service --example discover -- --watch
```

Note the `handle=` and `generation=` of the device. Unplug the key, wait two refreshes, plug it back
in. Expect: `0 device(s)` while unplugged (the old handle no longer appears); after replug a
**different** `handle` that has never been seen before. The device `generation` may stay at 1: macOS
gives every plug a new HID path, which the worker treats as a new device identity (a new worker-local
id), so the old handle cannot retarget either way. A replug that reuses the same path (Linux, or a
fast reseat) bumps the device `generation` instead. Leave `--watch` running for step 3.

## 3. Killing or wedging the worker does not wedge discovery

With `--watch` still running, in a second terminal:

```bash
pgrep -lx fido-worker
```

Note the pid, then simulate a crash:

```bash
kill -9 "$(pgrep -x fido-worker)"
```

Expect one `refresh failed: ...` line, then within about a second a `[supervisor]` line with
`generation=2` and a larger `launches`, and the device back with a new `handle`. Now simulate a worker
frozen mid-operation:

```bash
kill -STOP "$(pgrep -x fido-worker)"
```

Expect a `refresh failed: ...` line within about 2.1 s (the 2 s list budget plus the 100 ms transport
margin), then recovery with `generation=3`. The frozen pid must be gone and not left as a zombie:

```bash
ps -axo pid,stat,command | grep '[f]ido-worker'
```

Expect exactly one `fido-worker` line, with a different pid than the one you stopped and no `Z` in
its `STAT` column.

### 3b. Crash-loop breaker (optional)

With `--watch` running, hammer the worker for about ten seconds:

```bash
for i in $(seq 1 30); do pkill -9 -x fido-worker; sleep 0.3; done
```

Expect `state=CrashLoop` and `launches` to stop growing (at most 5 launches inside the window), with
`refresh failed: the native worker keeps failing; automatic restarts are paused`. It resumes by
itself after the 60 s cooldown (one probe launch, then normal operation if you stopped killing it).

## 4. The app does not leave an orphaned worker

```bash
cd <WT> && pnpm install --frozen-lockfile && pnpm tauri dev
```

Wait for the key to appear in the window, then in another terminal:

```bash
pgrep -lx fido-worker
```

Expect exactly one worker. Now quit the app normally with Cmd+Q, then:

```bash
pgrep -lx fido-worker || echo "no worker left behind"
```

Expect `no worker left behind` within a second. Start the app again, wait for the key to appear, then
kill the app with no chance to clean up:

```bash
kill -9 "$(pgrep -x fidomanager-app)"
```

```bash
sleep 1; pgrep -lx fido-worker || echo "no worker left behind"
```

Expect `no worker left behind`: the worker sees its stdin close and its parent change, and exits.

## 5. HID / TCC / Input Monitoring attribution

The aim is to *observe and write down* how macOS attributes HID access from the child worker. Before
steps 1 to 4, open System Settings, Privacy & Security, Input Monitoring, and note which entries
exist. While running steps 1, 2 and 4, note any permission dialog (its exact wording and the name it
shows), and afterwards note which entries were added. Do the same for System Settings, Privacy &
Security, Security, and for any "Allow accessory to connect" prompt.

Two launch contexts are covered: the example run from your terminal (step 1) and the app run via
`pnpm tauri dev` (step 4). Both are *development* launches from a terminal, so macOS will most likely
attribute to the terminal application rather than to FidoManager. A packaged, signed `.app` with a
sidecar is not buildable yet (bundling is out of scope for this milestone) and remains an open item.

Optional, only if you are happy to change your own privacy settings: resetting the terminal's
Input Monitoring grant first gives a clean observation.

```bash
tccutil reset ListenEvent com.apple.Terminal
```

## 6. No renderer or UI regression

```bash
cd <WT> && pnpm security:renderer-boundary && pnpm lint && pnpm typecheck && pnpm test && pnpm build
```

Expect all green: no frontend or Tauri-command code changed. In the running app (step 4) expect the
same device card fields as on `main`, the device appearing within about a second of plugging it in,
disappearing on unplug, and the Refresh button working. Also kill the worker while the app is open:

```bash
kill -9 "$(pgrep -x fido-worker)"
```

Expect the window to show a brief discovery error at most once and then recover on its own, without
restarting the app.
