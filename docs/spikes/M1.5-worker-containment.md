# M1.5 spike: worker killability and native-call containment

Status: spike result, 2026-10-02. Branch `spike/m1.5-worker-containment`, based on `main` at `6bc883f`.
Issue: #3. Scope: read-only discovery only; no M2 functionality was built.

> **Outcome (issue #5).** The recommendation below was adopted and productionized: native FIDO work
> now runs in the `fido-worker` child process, M1 discovery moved onto it, the thread endpoint and
> the `fido-spike-worker` crate were removed, and the open questions in section 10 that software can
> answer are resolved in code (see ADR-009, "Milestone 1.5 decision"). The code references in this
> report describe the tree at commit `0c51ec2` and are kept as historical evidence. Hardware
> questions (TCC attribution, real `open`/`get_cbor_info` timings, post-kill device behaviour) are
> tracked in `docs/validation/M1.5-macos-hardware.md`.

**Question:** can the worker stay thread-backed for future sensitive operations, or must native work
move into a killable child process before mutation-capable milestones?

**Answer in one line:** keep the thread worker for the current read-only M1 behaviour (it fails
closed), but do **not** put any mutation, PIN, credential, or user-presence operation on it. Those
need a killable child-process worker, and the existing protocol/`WorkerEndpoint` trait carried
across a process boundary without any change.

All evidence below comes from tests in `crates/fido-spike-worker` (a throwaway workspace member;
see "What was added"). Nothing in the merged M1 crates was modified except the workspace member list
and `Cargo.lock`.

## 1. Current in-process behaviour

Read from the code, then confirmed by the experiment in section 3.

- `InProcessWorkerEndpoint::exchange` sends a `WorkItem` over an unbounded `mpsc` channel to one
  dedicated thread and waits `recv_timeout(budget_ms + 250)`. On timeout it returns
  `TransportFailure`; on a dropped channel, `Unavailable`
  ([in_process_worker.rs:70-93](../../crates/fido-service/src/in_process_worker.rs)).
- The worker thread processes items strictly in order. It is never interrupted. If the service has
  given up, the response `send` simply fails and the thread moves on to the next queued item
  (lines 52-59).
- The `JoinHandle` is stored in a private `_worker_thread` field and never joined or signalled.
  Dropping the endpoint detaches the thread.
- `DiscoveryCoordinator` quarantines the worker on any `Endpoint(_)` error
  ([discovery.rs:108-122](../../crates/fido-service/src/discovery.rs)) and refuses further `refresh()`
  until `replace_worker`. `replace_worker` documents "the caller must ensure the previous worker can
  no longer execute native calls" but has no way to check it.
- The Tauri app never calls `replace_worker`
  ([src-tauri/src/lib.rs](../../src-tauri/src/lib.rs)). After one transport failure, discovery stays
  `WorkerQuarantined` until the app is restarted.
- `refresh()` runs under a `Mutex` held for the whole transaction
  ([commands/mod.rs](../../src-tauri/src/commands/mod.rs)); a slow refresh blocks every other caller.

## 2. Fault-injection experiment

`tests/in_process_fault_injection.rs` drives the real, unmodified `InProcessWorkerEndpoint` and
`DiscoveryCoordinator` with a `GateBackend`: a `NativeDiscoveryBackend` whose calls block (ignoring
their budget) until the test releases a gate. Shared atomic counters (`entered`, `completed`,
`in_native`, `max_concurrent`) observe what the worker thread is really doing, independent of what
the service was told. No real libfido2 or device is involved, so it is deterministic.

Tests:

1. `service_timeout_is_not_quiescence`: steps A to G from the brief, in order.
2. `abandoned_queued_request_executes_after_release`.
3. `in_process_replacement_overlaps_stuck_native_call`.
4. `dropping_endpoint_leaves_stuck_thread_running`.
5. `service_has_no_transaction_deadline_and_slack_hides_overrun`.

## 3. Observed results

Output of `cargo test -p fido-spike-worker --test in_process_fault_injection -- --nocapture`:

```
A. native call entered: 1
B/C. refresh -> Err(Endpoint(TransportFailure)) after 304ms        (budget 50 + slack 250)
D. native still in flight: in_native=1, completed=0
F. quarantined: second refresh rejected with no new native entry
G. released: native completed, coordinator still quarantined
abandoned request #2 executed natively after release: entered=2
max concurrent native calls observed: 2
refresh with 100 ms budgets took 1.21s for 4 devices
```

Answers to the brief's questions 1 and 2:

| Question | Result |
|---|---|
| Native op hangs forever | Service gets `TransportFailure` at budget + 250 ms and fails closed. The thread stays blocked indefinitely. |
| Service responsive afterwards | Yes. `refresh()` returned in ~304 ms, and later calls return `WorkerQuarantined` immediately. |
| Worker thread alive | Yes (`in_native == 1`), and it is unobservable by the service. |
| Worker safely replaceable | **No.** `replace_worker` accepted a new in-process worker while the old thread was still in native code; the test observed 2 concurrent native calls against the same stack. The type system does not stop this. |
| Another native op can run safely | Not on that worker: a new request queues behind the stuck call. On a replacement worker it runs, but overlapping the old call (above). |
| Clean shutdown | Dropping the endpoint returns instantly and leaves the thread running (`in_native` stays 1). The thread can only be released cooperatively; the service has no handle to stop or join it. Process exit will not wait for it, but nothing cleans up native state either. |

Three things the brief asked to be told apart, as observed:

- **Service request timeout** happened at ~304 ms: the service's view.
- **Worker/native-call completion** happened only after the test released the gate: the native
  call's view.
- **Execution quiescence** was never established. No evidence exists unless a response arrives
  (`WorkerResponseEvidence`), and none did. During the whole window the honest value was "unknown,
  assume `Active`". The in-process endpoint cannot ever upgrade that without the call returning on
  its own.

Failure modes found beyond the brief's list:

- **Abandoned work still runs.** A request that timed out while *queued* behind the stuck call is
  executed natively after release (`entered` went from 1 to 2) with nobody waiting for its result.
  For read-only discovery that is harmless. For a mutation it means "the service reported timeout
  and the operation later happened anyway" with no outcome record. This alone rules the thread
  endpoint out for mutations.
- **The 250 ms slack hides budget overruns.** Native calls that took 3x their 100 ms budget (300 ms,
  inside budget + slack = 350 ms) were accepted as success. The slack was intended as transport
  margin but acts as a silent extension of the native deadline.
- **No transaction deadline.** One `refresh()` is `ListDevices` plus one `GetInfo` per uncached
  device, each with its own full budget. With 4 devices it took 1.21 s on 100 ms budgets, and the
  bound is `(1 + N) x (budget + slack)` with N up to `MAX_DISCOVERED_DEVICES = 64`.
- **Single-failure lockout in the app.** Because the app never replaces the worker, one transient
  hang disables discovery until restart.

### Verdict on the in-process boundary (question 4)

The in-process architecture provides a trustworthy **fail-closed** boundary but not a trustworthy
**kill/recovery** boundary. It can stop trusting a worker; it cannot stop a worker.

## 4. Child-process prototype result

`crates/fido-spike-worker` adds `ProcessWorkerEndpoint` (about 150 lines, `std` only) and a
`fido-spike-worker` child binary. The child runs the **real** `WorkerEngine` (through
`InProcessWorkerEndpoint`) over a scripted fake native backend (`ok`, `hang`, `crash`). Transport is
`u32` big-endian length prefix plus the existing serde JSON envelopes over the child's stdin/stdout,
with `MAX_WORKER_FRAME_BYTES` enforced before allocation. `ProcessWorkerEndpoint` implements the
unchanged `fido_service::WorkerEndpoint`, and the tests drive the unchanged `DiscoveryCoordinator`.

**Is the protocol process-transparent in practice? Yes.** No change was needed to
`fido-worker-protocol`, `WorkerEndpoint`, `DiscoveryCoordinator`, or the request/response
validation. Quarantine, generation checks, handle invalidation and `replace_worker` worked as
written. Observed (`tests/child_process.rs`, all passing):

```
round trip:   ListDevices + GetDeviceInfo over a real child -> 1 Ready device
hung child:   refresh -> Err(Endpoint(TransportFailure)) after 305 ms; pid gone (kill -0 fails);
              next refresh -> WorkerQuarantined; replace_worker(gen 2) -> refresh OK, new pid
crash:        refresh -> Err(Endpoint(Unavailable)) after 246 ms on a 5 000 ms budget
idle death:   kill -9 while idle -> next refresh Err(Unavailable); old handle no longer resolves;
              replacement gen 2 works; old handle stays dead
oversize:     4-byte header claiming MAX+1 bytes -> FrameError::TooLarge before any allocation
orphan:       closing the child's stdin makes an idle child exit 0
```

The decisive difference: on timeout the endpoint does `kill()` then `wait()`. When that returns, the
process is gone, so quiescence is **proven**, not assumed. That is the missing precondition for
`replace_worker`.

Limits of the prototype (deliberately not hardened):

- Backend is fake. Real libfido2 and real hardware were not exercised.
- Observed ~246 ms to detect `abort()` on macOS rather than near-zero. Plausibly the system crash
  reporter delaying exit; not investigated. Still far inside the budget.
- A child wedged in native code cannot notice its parent died, because the same thread that reads
  stdin is blocked in the call (the prototype's main loop is). The idle-orphan case is tested; the
  **hung-and-orphaned** case is not, and would leak a stuck process if the app were SIGKILLed.
  The fix is a separate watchdog thread in the child (stdin EOF, or `getppid()` polling, or
  `kqueue` `NOTE_EXIT` on the parent). Not built.
- No restart policy, backoff, health checks, or crash-loop limits.

## 5. Timeout analysis

Current values:

| Layer | Value | Where |
|---|---|---|
| `DiscoveryPolicy.list_devices_budget_ms` | 2 000 ms | discovery.rs `Default` |
| `DiscoveryPolicy.get_device_info_budget_ms` | 2 000 ms | discovery.rs `Default` |
| Service exchange deadline | budget + `HARD_DEADLINE_SLACK_MS` (250) = 2 250 ms | in_process_worker.rs |
| `fido_dev_info_manifest` | **no timeout, `_budget_ms` ignored** | libfido2 adapter |
| `fido_dev_set_timeout` | set to budget before open | libfido2 adapter |
| `fido_dev_open` | uses whatever libfido2 does internally with that timeout (not verified here) | libfido2 adapter |
| `fido_dev_get_cbor_info` | same `set_timeout` value, applied again, separately | libfido2 adapter |
| Transaction | **none** | n/a |

Inconsistencies:

1. `manifest` ignores its budget entirely, so the service budget is the only bound on it, and the
   service bound does not stop it (section 3).
2. `get_info` makes two native calls (`open`, then `get_cbor_info`) that each get the **full**
   budget. The worst case is about `2 x budget`, which already exceeds `budget + 250` at the
   default 2 000 ms (4 000 ms vs 2 250 ms). A slow-but-live device is therefore reported as a
   transport failure and quarantines the worker, not as a clean `DeadlineExpired`.
3. Native timeout equals service budget, and the slack is 250 ms, so there is no ordering guarantee
   native < exchange: they race. The code does `elapsed >= budget` to classify `TimedOut`, which
   only works if libfido2 returns just before the service gives up.
4. Whether `fido_dev_open` honours `fido_dev_set_timeout` was **not** verified in this spike (no
   libfido2 source/hardware exercised). It must be, because `open` is the likeliest call to block on
   macOS HID.
5. No overall transaction bound (section 3, `(1 + N) x (budget + slack)`).

Proposed model. Strict nesting; each layer owns exactly one deadline and is shorter than the layer
above it:

```
T_txn      service transaction deadline            owner: DiscoveryCoordinator
  └─ T_exch   per-exchange hard deadline           owner: WorkerEndpoint
       └─ T_native   per-operation native deadline owner: worker / native adapter

T_native(op) = min(op_budget, T_exch - margin)       sums over all native sub-calls in the op
T_exch       = T_native(op) + margin_transport       margin is transport only (framing, scheduling)
T_exch       <= remaining(T_txn)                     later exchanges get what is left, not a fresh budget
on T_exch expiry: endpoint terminates the worker, then reports TransportFailure + proven quiescence
```

Rules:

- The worker computes **one** deadline per request and passes the *remaining* time to each native
  sub-call (`open`, then `get_cbor_info`). It never hands the full budget to each.
- `manifest` gets a real bound: either run it where it can be killed (child process) or treat its
  unbounded nature as a documented reason it must live behind the kill boundary.
- Transport margin should be small and named for what it is (for example 100 ms), not a hidden
  extension of native time. For the child endpoint the margin only covers framing and wakeup.
- The coordinator gets a transaction deadline (suggested order of magnitude: 5 s for discovery;
  to be tuned against real devices) and derives each exchange budget from what remains. Exceeding it
  fails the whole refresh closed.
- Do not simply raise numbers. The fix is the ordering and ownership above; the absolute values
  need real-device measurements.

## 6. Recovery analysis (read-only)

| Scenario | In-process thread | Child process |
|---|---|---|
| 1. Normal response | Works. | Works (tested). |
| 2. Service timeout, worker eventually returns | Late response dropped; worker stays quarantined; but abandoned queued requests still execute natively. Cannot be made safe. | Does not arise: the process is killed at the deadline, so nothing can return late. A late frame from a killed process cannot be delivered; generation check is the second line of defence. |
| 3. Crash before response | Native crash (segfault in libfido2) takes down the **whole app**; the service cannot recover. | Detected by EOF/exit (`Unavailable`, tested, ~246 ms on abort); quarantine, handles cleared, spawn gen N+1, rediscover (tested). |
| 4. Crash after response dispatched | Same: app dies. | Detected on next exchange (`Unavailable`, tested); old handle stops resolving, replacement works (tested). Optionally detect sooner with a reader-thread death event. |
| 5. Service restart | Worker dies with the process; fresh enumeration; generation restarts at 1. | Child must also die: tested for the idle case via stdin EOF; **hung-orphan case needs a child watchdog (open)**. New process starts with a new generation and new device IDs; no state to reconcile for read-only. |
| 6. Device disconnect while worker is blocked | Thread stays blocked until the OS/native layer errors out; service times out and quarantines; nothing else can run. | Kill at deadline; replacement worker enumerates the post-disconnect truth; the old generation's device handles are already invalid. Not tested with real hardware. |

Generation bookkeeping already supports this: `replace_worker` requires a strictly increasing
`WorkerGeneration`, clears the registry and info cache, and `validate_response` rejects any response
whose `worker_generation` differs. Those held unchanged across the process boundary.

Suggested addition (not built): `WorkerEndpoint` gains a `contain()` operation returning
`ExecutionQuiescence`; the thread endpoint can only ever return `Active`; the process endpoint
returns `Quiescent` after kill + wait. `replace_worker` would then require that proof instead of
documenting it.

## 7. macOS considerations

Tested in this spike: process spawn, SIGKILL, reap, crash detection, stdin-EOF self-exit, all on the
local macOS machine. Everything else below is **analysis, not verified here**, and must be checked
with a packaged build and real hardware.

- **Executable location.** Dev: `target/debug/<bin>` (Cargo exposes `CARGO_BIN_EXE_*` to tests).
  Packaged: ship as a Tauri sidecar (`bundle.externalBin`, target-triple suffix) which lands in
  `Contents/MacOS/` next to the app executable. Resolve it from `std::env::current_exe()`'s
  directory, never from `PATH` or any renderer-influenced value.
- **Signing and notarization.** The sidecar must be signed with the same Developer ID and hardened
  runtime as the app, and is covered by the app's notarization. Unsigned or ad-hoc-signed helpers
  fail notarization. Entitlements for the helper need to be decided deliberately.
- **HID / TCC.** Whether macOS attributes HID device access (Input Monitoring) to the app bundle or
  to the sidecar, and whether the child triggers a second permission prompt, is not known. This is
  the highest-risk unknown for the child-process route and needs a real-device check early.
- **Inherited descriptors.** Rust's `Command` sets close-on-exec only on fds it opens. Descriptors
  from other libraries (Tauri/WebKit, IOKit ports, hidapi) may leak into the child unless they are
  CLOEXEC. The prototype only passes stdio but did not audit leaks. Spawn the worker before other
  initialisation, or spawn through `posix_spawn` with `POSIX_SPAWN_CLOEXEC_DEFAULT`.
- **Termination.** `Child::kill` is SIGKILL; `wait` reaps. There is no `PR_SET_PDEATHSIG` on macOS,
  so parent-death cleanup needs the child-side watchdog described in section 4.
- **App shutdown.** `ProcessWorkerEndpoint::drop` kills and reaps, which gives deterministic
  cleanup that the thread endpoint cannot offer. A hard crash of the app relies on the watchdog.
- **Cross-platform.** Linux should behave the same way but was not run here (CI will exercise the
  tests on Ubuntu; they shell out to `kill`). Windows is out of scope here; the brokered/elevated model in the plan would use the
  same protocol.

## 8. Decision / recommendation

> **Can we safely keep the worker in-process for future sensitive operations, or should
> sensitive/native operations use a killable child-process worker?**

**Sensitive and mutating native operations must use a killable child-process worker.** The
in-process thread must not host them.

Evidence:

1. A hung native call cannot be stopped, joined or proven quiescent in-process; `replace_worker` can
   silently produce overlapping native execution (2 concurrent calls observed).
2. A request the service already reported as timed out can still execute later (queued request ran
   after release). That is unacceptable for anything with side effects or user-presence semantics.
3. A native crash in-process kills the whole application, including the trusted authority.
4. The child-process prototype reused the existing protocol, trait and coordinator with **zero
   semantic changes** and gave proven quiescence, crash detection, handle invalidation and clean
   generation replacement.

The thread worker remains acceptable for the current M1 read-only discovery because it fails closed
and never mutates, with two caveats that should be tracked rather than ignored: one hang disables
discovery until restart (no `replace_worker` path in the app), and the timeout model above is
inconsistent.

If the project would rather have one placement everywhere, the cheapest consistent choice is to move
discovery behind the same child worker now and delete the thread endpoint from the production path.

## 9. Consequences for M2

- Treat the child-process worker as an M2 prerequisite, not a follow-on, for anything beyond
  idempotent reads. M2 should not start with PIN entry or any mutation on the thread endpoint.
- Productionise `ProcessWorkerEndpoint`: restart/backoff and crash-loop limit, child watchdog for
  parent death, fd hygiene, sidecar packaging and signing, and a fixed frame/handshake format with
  protocol version negotiation.
- Implement the timeout model in section 5 before M2 (single per-request deadline split across
  sub-calls, small transport margin, coordinator transaction deadline).
- Add `contain()` / quiescence proof to `WorkerEndpoint` so `replace_worker` cannot be called
  without it. Wire an actual replacement path into the Tauri app.
- Keep mutation recovery (`MutationOutcome::OutcomeUnknown`, reset/recovery admission) out of scope
  here; this spike only shows that a kill boundary is the precondition for designing it.
- Keep the spike crate out of the release build; either delete it or promote the parts above.

## 10. Open questions

1. Does macOS attribute HID access to the sidecar or the app, and does a child worker cause an extra
   permission prompt? (Needs a packaged, signed build and a real authenticator.)
2. Does `fido_dev_open` honour `fido_dev_set_timeout`, and what is its real worst case on macOS HID?
   Can `fido_dev_info_manifest` block, and for how long?
3. What are real-device P99 times for `open` and `get_cbor_info`, to choose the budgets and the
   transaction deadline?
4. Is killing a child mid-HID-transaction ever harmful to the authenticator (stuck channel, CTAPHID
   state)? Read-only GetInfo should be safe; confirm on hardware, then decide the post-kill re-init
   delay.
5. One child per app, or one per device? ADR-009 says per-device worker; the prototype is one
   process per endpoint.
6. Parent-death watchdog mechanism on macOS (`getppid` polling vs `kqueue NOTE_EXIT` vs
   stdin-reader thread) and whether it must also work while the child is wedged in native code.
7. Should discovery move to the child now (one placement) or stay in-process until M2?
