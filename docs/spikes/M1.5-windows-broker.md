## Deliverable and evidence limits

[SOURCE] `tools/windows-broker-spike/` is an isolated, Debug-only .NET 10 console/Win32 experiment. It is outside the Cargo/Tauri build graph, has no packages beyond the SDK framework, and is never launched by FidoManager. Runtime modes require `--ack-nonshipping`; `self-test` is portable. Release builds are rejected. This language/runtime choice lets the available Mac SDK compile the Win32 declarations and exercise the protocol model without changing the shipping Rust platform boundary. It is not the selected implementation language for a production broker.

[SOURCE] The executable provides an unelevated client, a UAC-launched broker, broker-owned non-secret native UI, read-only child probing, and hung-child fixtures. Only `placeholder` and `probe` are admitted wire request kinds. There are no PIN fields, approval inputs, CTAP payloads, native handles, device paths, library paths, executable paths, arbitrary filesystem/network requests, token acquisition, credential enumeration, mutation, or recovery-journal APIs. The negative-test `Approved` field is deliberately rejected JSON, not an approval API.

[UNRESOLVED] No interactive Windows machine or physical authenticator was available. All Windows API calls, UAC flows, security descriptors, native ABI calls, focus behavior, job teardown, and hardware observations below are **implemented probes and planned checks**, not observed results. Windows CI alone would not close this gate either. No final ADR-013 is added.

## Direct access and Windows Hello

[SOURCE] [Microsoft WebAuthn APIs](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/webauthn-apis) separate ordinary WebAuthn use from direct transport access. [Yubico's Windows management guidance](https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-apps-fido.html) says administrator execution is needed for direct FIDO management. [libfido2 maintainer guidance](https://github.com/Yubico/libfido2/discussions/669) explains that the Windows Hello backend does not expose the credential-management functionality used by `fido2-token`. These are source findings; they do not replace the required physical-device comparison.

[SOURCE] Reviewed baseline: libfido2 **1.17.0**, matching the previous fit spikes. Its [Windows Hello implementation](https://github.com/Yubico/libfido2/blob/1.17.0/src/winhello.c) manifests `windows://hello`, implements ordinary WebAuthn credential/assertion calls, and synthesizes GetInfo options. That pseudo-device's successful open/GetInfo is not evidence of opening a physical authenticator. The [credential-management implementation](https://github.com/Yubico/libfido2/blob/1.17.0/src/credman.c) uses the CTAP management commands. This harness never imports/calls those management functions.

[DIRECT-ACCESS][SOURCE] `ReadOnlyProbe.cs` loads only fixed sibling `libfido2/fido2.dll` in the short-lived worker. It manifests at most 16 entries and opens/GetInfo-probes at most eight, with 1500 ms native timeouts and a 12 s enclosing process budget. It records manifest/open/GetInfo return codes, VID/PID, `fido_dev_supports_credman`, DLL SHA-256, and a path hash. `windows-hello`, direct HID paths (`\\?\hid#...`), and other transports are distinguished. Native paths stay inside the worker; the client cannot choose a path or target. Path hashes are comparison metadata, not cryptographic device identity. Enumeration failure or an incomplete bounded sample cannot establish absence of manageable devices.

| Required comparison | Current result | Required evidence |
| --- | --- | --- |
| Unelevated: no device / physical device attached | [DIRECT-ACCESS][UNRESOLVED] not run | Manifest results and backend labels, open/GetInfo codes, medium token |
| Elevated: same physical device | [DIRECT-ACCESS][UNRESOLVED] not run | Direct HID entry, successful open/GetInfo, high token |
| Hello enabled vs `USE_WINHELLO=OFF` | [DIRECT-ACCESS][UNRESOLVED] not run | Two independently identified 1.17.0 builds; pseudo-device must not become a management target |
| Unplug/reinsert, replacement, browser/Windows contention | [DIRECT-ACCESS][UNRESOLVED] not run | Path-hash/VID/PID changes and error codes; no automatic identity continuity |
| Credential-management capability | [DIRECT-ACCESS][UNRESOLVED] not run | Direct GetInfo capability flag only; no PIN, PUAT, credential list or mutation |

[INFERENCE] Direct access is the candidate for management, and elevation is plausible from upstream guidance. Elevation is **not empirically established here**. Hello must be excluded from a future canonical management registry. The prototype makes a fresh worker-local enumeration each time and does not implement that production registry/session generation policy.

## Authority, IPC and singleton candidate

[SOURCE] Candidate placement is **unelevated bounded client → elevated policy/UI broker → elevated killable native child**. The broker chooses the only admitted workflows, owns the launch/connection generation, one-request admission, native prompt identity, deadline and completion. The worker owns native paths and handles; only bounded observation data returns. The broker never loads libfido2. The client cannot approve the placeholder window or choose a native call. No state is transferred on reconnect.

[UNRESOLVED] This is a one-shot feasibility authority, not a port of `fido-service`. Production policy, canonical sessions, admission cooldown, permits, sealed approval, PUATs, outcomes/recovery state and journaling are absent. Before M2, those must reside in/enforce policy within the broker, not be asserted by Tauri. The existing Rust service/worker/native-UI contracts remain unchanged, including their Windows fail-closed stubs.

[IPC][SOURCE] Candidate transport: byte-mode overlapped named pipe, maximum one instance, `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, no inheritance. Frames are 4-byte big-endian length followed by strict JSON, maximum **4096 bytes**, depth eight. Empty, truncated, oversized, malformed, missing/duplicate/unknown fields and unknown kinds fail closed. Version 1, fresh broker/client GUID generations and nonzero request ID correlate the reply. The challenge is sent only after OS peer validation. One connection gets one request and then closes; additional bytes/EOF revoke active work. After a terminal reply, the broker waits at most two seconds for client close; the client checks retained-server liveness before consuming that reply. There is no request queue or reconnect/adoption operation. Generations are correlation/replay boundaries, not authentication secrets.

[IPC][SOURCE] Requested descriptor: `D:P(A;;GA;;;SY)(A;;0x00120003;;;<same-user SID>)S:(ML;;NW;;;ME)`. It grants SYSTEM full control and the initiating/elevating same user's individual read/write/synchronize/read-control rights, omitting `FILE_CREATE_PIPE_INSTANCE`. The medium label deliberately permits the intended medium client. The harness retrieves and logs the **effective** owner/group/DACL/mandatory-label descriptor and rejects unexpected DACL principals/masks. It uses exact access rights and identification SQOS when connecting, rather than generic write. [Microsoft's pipe security documentation](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights) explains both unsafe default ACLs and generic-write's pipe-instance right. Descriptor creation/query/access-check behavior still needs runtime validation; failure ends the experiment rather than falling back to default security.

[IPC][SOURCE] The client retains the process handle returned by `ShellExecuteExW(runas)` and validates [OS-derived server PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid), creation time, live process and elevated token. The broker retains a handle to the launching client, compares [OS-derived pipe client PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid) and creation time, then reads SID, logon SID, authentication LUID, session, elevation and integrity from process tokens. It additionally checks the pipe's impersonated SID after the first request and immediately reverts. [Impersonation failure](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-impersonatenamedpipeclient) aborts; no work runs in an accidentally privileged fallback context. CLI PID/time are launch hints checked against the connection and retained OS object, not trusted renderer fields or secrets.

[IPC][UNRESOLVED] The SID DACL deliberately allows same-user connections at the transport layer. Unrelated same-user processes should then fail the retained-process/session checks; they may still squat on the name or deny service. A SID, PID or pipe name does not prove that the process is genuine FidoManager. Matching a retained launch is not executable attestation. Signed/protected binary validation, bootstrap trust and effective ACL/session behavior remain unresolved. Do not use this debug design as production IPC authentication.

[SOURCE] Provisional singleton scope is **one initiating user/logon/interactive session**, with the pipe name derived from SID + logon SID + authentication LUID + session ID. First-instance creation and one instance prevent concurrent brokers within that namespace. A second client launches a new broker that must fail rather than adopt an existing authority. A replacement client must complete a new UAC launch and generation. Other sessions/administrators and external FIDO clients are not excluded machine-wide. ADR-012's Tauri singleton is untouched.

[WINDOWS][UNRESOLVED] Same-user split-token UAC must demonstrate that the SID/logon SID/LUID/session checks succeed. If Windows produces a different linked-token logon identity, this prototype rejects it; record that failure and review the OS-linked-token model rather than weakening the comparison silently. Alternate-account UAC is intentionally unsupported and must reject before creating the pipe/UI/native worker. It is not decided whether MVP should support it. Machine-wide registry/recovery coordination across multiple logons is also unresolved.

## Native UI candidate and security limits

[UI][SOURCE] `PlaceholderWindow.cs` creates a broker-owned Win32 top-level window with fixed text, two non-secret buttons and initially focused Cancel. It captures broker-minted workflow/prompt GUIDs and one immutable request binding; client nonce/request ID are correlation data only. It runs the broker main thread's ordinary message pump, destroys the window before returning a terminal placeholder result, and checks deadline/client cancellation again after destruction. No client HWND is accepted; owner HWND is zero. It registers session notifications and revokes on session transitions, suspend, shutdown, client loss or 30 s expiry. Native loss/failure cannot authorize a FIDO operation.

[UI][SOURCE] The client logs `AllowSetForegroundWindow(broker PID)`; the broker logs `SetForegroundWindow`, actual foreground HWND immediately and after its first timer event, owning thread, prompt/request identities, client process identity and destruction. [Microsoft foreground rules](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow) restrict activation and can deny it even when documented conditions appear satisfied. No synthetic focus/input workaround is attempted.

[UI][UNRESOLVED] This proves no association with the real Tauri main window yet: the requester here is a console harness. Independent top-level UI is only a candidate, not a proven substitute for supported native modality/association. Cross-integrity HWND ownership, actual application visibility/minimization, secure-desktop transitions, focus transfer reliability, accessibility and signed/installed presentation require interactive Windows experiments. No renderer-command integration is introduced just to drive them.

[INFERENCE] The legitimate prototype interaction stays outside WebView JavaScript, which cannot answer it through application IPC. That does not authenticate genuine human action or protect against same-user malware, Accessibility/Input Monitoring/keylogging, synthetic input or a compromised OS. Renderer content could visually imitate the native window. UIPI/elevation is not a PIN-confidentiality guarantee. A placeholder acceptance is diagnostic data only: it cannot mint an `OperationPermit`, invoke a mutation, or reuse the macOS spike's publicly constructible `Approved` as production authority. Sealed consume-once completion, immutable intent/session/target binding and live admission remain separate M2 gates.

## Worker containment and teardown matrix

[SOURCE] `ChildWorker.cs` creates an unnamed, non-inheritable job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, creates the fixed sibling apphost **suspended and already assigned to the job** using `PROC_THREAD_ATTRIBUTE_JOB_LIST`, then validates job membership and child token/session before resuming. This Windows 10+ attribute avoids the parent-death gap of create-then-assign; there is no fallback to that gap. No breakaway flags are set. `STARTUPINFOEX`'s explicit inherited-handle list contains only the output pipe (stdout/stderr); stdin is null. Pipe read end, IPC handles, job and token handles are not inherited. Child environment contains only SystemRoot. Attribute/identity/launch failure never resumes native work. [Microsoft job semantics](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [handle-list requirements](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) support this candidate; Microsoft also documents [atomic job assignment](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812). Nested-job restrictions, actual inherited handles and orphan behavior need Windows testing.

[SOURCE] The parent bounds worker framing/output, uses a retained process handle, and proves root exit by waiting on that handle, terminates remaining job members, and checks job accounting reports zero active processes before returning probe data. Failure/timeout terminates the job/child and waits up to two seconds. No proof means an error/quarantine and no replacement or workflow release. The parent-death candidate is last-job-handle close; broker/client connection watchers are outside native calls. The hung fixture sleeps indefinitely without libfido2, so native-call containment can be exercised without a real device/PIN.

| Event | Implemented/modelled behavior | Empirical Windows status |
| --- | --- | --- |
| Launch / UAC cancel / launch timeout | Retained launch identity or abort; connect/hello budget 10 s | [WINDOWS][UNRESOLVED] |
| Second client / existing broker | First-instance/one-instance candidate; no adoption or queue | [WINDOWS][UNRESOLVED] |
| Client EOF, process death or extra request | Revoke; close window or kill/wait worker; suppress successful reply | [IPC][UI][UNRESOLVED] |
| Broker death | Client fails; old response slot cannot reactivate; job-close orphan cleanup candidate | [WINDOWS][UNRESOLVED] |
| Reconnect/restart/recycled PID | New retained process/generations required; old correlation fails | [TEST] model passes; OS identity queries [UNRESOLVED] |
| Worker death/bad frame/hang | Kill/wait before result; uncertain teardown never allows successor | [TEST] proof requirement model passes; job runtime [UNRESOLVED] |
| Native cancel/close/deadline/session/shutdown | Bound failure, destroyed HWND before release; post-close cancellation veto | [UI][UNRESOLVED] |
| Late/duplicate completion or response | Exactly one model terminal response; reject stale/consumed slot | [TEST] model passes |

[INFERENCE] Placement B preserves ADR-009's reason for containment: a hung/crashed parser must not block or corrupt broker policy/UI memory. Placement A (long-lived broker directly linking native code) loses that protection and has no evidence justifying it. A Windows child/job model is preferred provisionally. This is containment of hangs/crashes, not a sandbox against arbitrary malicious native code with the broker's OS privileges. Production `fido-worker-protocol` already has owned/versioned messages and no Unix pointers; its semantic boundary appears reusable, but Unix process hygiene/parent monitoring and native Windows loading are not implemented in the production worker. This experimental codec is not a production worker-protocol revision.

## Packaging dependency

[SOURCE] The DLL is resolved from an absolute sibling directory and loaded with `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32`; no PATH/current-directory lookup. [libfido2 deployment guidance](https://github.com/Yubico/libfido2/tree/1.17.0) requires trusted, non-writable artifacts. [YSA-2026-01](https://www.yubico.com/support/security-advisories/ysa-2026-01/) identifies the Windows DLL search issue fixed in 1.17.0; do not use an earlier build for this validation. The DLL hash records the tested file, not a verified trust root.

[UNRESOLVED] Debug directories, managed assemblies, apphost/runtime resolution and dependencies are user-writable. They are unsuitable for a production elevated boundary. Before shipping: administrator-protected signed broker/worker/private libraries, verified version compatibility, reparse/path/replace resistance, reviewed static-vs-bundled linkage, elevation manifest/launch, SDK/runtime dependency and install ACLs, architecture (x64/ARM64), SmartScreen/Smart App Control/WDAC and post-update identity all need validation and #8 hardening. Diagnostic logs in `%LOCALAPPDATA%\FidoManager-M15-Evidence` are user-writable evidence only, never read as authority/journal data. No packaged/signed broad Windows support claim follows from development probes.
