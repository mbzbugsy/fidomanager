# M1.5 spike: RP-hash credential enumeration

Issue: #12. Status: **source analysis, the identity-contract prototype and its automated tests are
complete, and the read-only Thetis hardware step has been run (section 9). The hardware run
confirms the verified-text path on one key and does **not** exercise hash-only enumeration; that
conclusion remains [SOURCE]/[SPEC]-based.

Hardware results below were supplied by Nima from running `fido-puat-spike rp-inventory` on the
Thetis; the PIN was typed only into the no-echo harness and never entered this conversation. The
terminal output was relayed as text, so entries labelled [HARDWARE] are as reported, not
re-observed by the author of this report.

This is a feasibility spike, not M3. It adds no production behaviour: no credential inspection, no
renderer data, no deletion, no PIN set/change, no reset, no native UI, no PIN IPC, no raw CTAP or
CBOR, and no change to the worker protocol. Code lives in `crates/fido-puat-spike`
(`publish = false`, depended on by nothing).

## Answer

> **Can FidoManager, using the pinned libfido2 1.17.0 public API, enumerate the credentials of an
> RP when the only trustworthy RP identity is the authoritative 32-byte RP ID hash?**
>
> **No.** The pinned public API exposes the authoritative hash but has no entry point that
> accepts one. It accepts RP ID *text* and hashes it itself. Hash-only credential enumeration is
> therefore an **UNSUPPORTED PRODUCT LIMITATION** for the MVP and **REQUIRES UPSTREAM WORK** to
> lift. This is not hypothetical: the CTAP specification lets authenticators truncate or omit the
> RP ID text (section 3), so hash-only RPs are a normal case on some keys.
>
> For an RP whose text verifies against the hash, enumeration **is** supported by the pinned
> public API, and is exactly equivalent to enumerating by the hash.
>
> No safe lower-level path exists that avoids custom CTAP/CBOR (section 4), so none is proposed.

## 2. libfido2 behaviour

### 2.1 RP enumeration returns the hash

- **[SOURCE] credman.c `credman_parse_rp`**: reply key 3 (`rp`) is decoded into `rp_entity`
  (`id`, `name`); reply key 4 (`rpIDHash`) is copied with `fido_blob_decode` into
  `single_rp.rp_id_hash`. Unknown keys are ignored.
- **[SOURCE] credman.h / export.gnu**: the hash is public API:
  `fido_credman_rp_id_hash_ptr(rp, idx)` and `fido_credman_rp_id_hash_len(rp, idx)`, exported on
  both linker scripts. `tools/credman.c` (upstream's own tool) uses them.
- **Answer to "does public libfido2 expose the authoritative hash?"**: yes. **SUPPORTED BY PINNED
  UPSTREAM API.**

| Field | Accessor | Type / nullability | Validation by libfido2 | Ownership |
| --- | --- | --- | --- | --- |
| RP ID text | `fido_credman_rp_id` | `const char *`; `NULL` if the device omitted `id` or `idx >= n_alloc` | CBOR text string type only (`cbor_string_copy`); **no UTF-8 check**; copied with a terminating NUL, so an embedded NUL truncates what C callers see | owned by the `fido_credman_rp_t`; valid until `fido_credman_rp_free` or the next `fido_credman_get_dev_rp` on the same object (it resets the list first) |
| RP name | `fido_credman_rp_name` | `const char *`, may be `NULL` | same | same |
| RP ID hash | `fido_credman_rp_id_hash_ptr` | `const unsigned char *`; `NULL` if the device omitted key 4 | CBOR byte string type only; **length is not checked** (any length is accepted, including 0) | same |
| Hash length | `fido_credman_rp_id_hash_len` | `size_t`; 0 when absent | n/a | n/a |
| Count | `fido_credman_rp_count` | `size_t` = entries actually received (`n_rx`) | n/a | n/a |

- **[SOURCE]** the accessors bound-check `idx` against `n_alloc` (entries allocated from
  `totalRPs`), while `fido_credman_rp_count` returns `n_rx`. Iterating `0..rp_count` is safe.
- **[SOURCE]** a duplicated key inside the `rp` map (`cbor_string_copy`: "dup") or a wrongly typed
  field fails the *whole* enumeration with `FIDO_ERR_RX_INVALID_CBOR`; there is no partial list.
- **[INFERENCE]** consequence: libfido2 itself rejects structurally broken replies, but it passes
  through *well-typed but semantically wrong* ones (wrong hash length, hash that does not match the
  text, truncated text). The identity contract must check those; libfido2 will not.

### 2.2 Empty and short results are silent

- **[SOURCE] `credman_rx_rp`**: `totalRPs` (key 5) sizes the list. If the key is absent,
  `n_alloc == 0` and the call returns **`FIDO_OK` with `fido_credman_rp_count == 0`**. The same
  applies to `credman_rx_rk` and `totalCredentials` (key 9): `FIDO_OK`, count 0.
- **[SPEC] §6.8.3 / §6.8.4**: a device with no discoverable credentials (or none for the RP hash)
  answers `CTAP2_ERR_NO_CREDENTIALS`, an error, not an empty success.
- **[INFERENCE]** so `FIDO_OK` + zero entries is a malformed-reply signature, not a legitimate
  empty result. A listed RP always has at least one credential, and the device's own
  `existingResidentCredentialsCount` is available to check against. Both are enforced by
  `assess` ([TEST] section 7).

### 2.3 What `fido_credman_get_dev_rk` accepts

- **[SOURCE] credman.c `credman_get_rk_wait`**:

  ```c
  SHA256((const unsigned char *)rp_id, strlen(rp_id), dgst);   // libfido2 hashes the text
  rp_dgst.ptr = dgst; rp_dgst.len = sizeof(dgst);
  credman_tx(dev, CMD_RK_BEGIN, &rp_dgst, pin, rp_id, FIDO_OPT_TRUE, ms)
  ```

  The public input is `const char *rp_id` (NUL-terminated text). The hash sent on the wire
  (`subCommandParams.rpIDHash`) is computed inside the function from `strlen(rp_id)` bytes.
  - there is no `rp_id_hash`/`len` parameter anywhere in the public header;
  - **[SOURCE]** `credman_tx`, `credman_get_rk_wait`, `credman_prepare_hmac` and `CMD_RK_BEGIN`
    are `static`: not exported (`src/export.gnu`), not callable;
  - `rp_id` is also passed to `cbor_add_uv_params`, but only used when libfido2 has to acquire
    its own token; with an attached PUAT (the spike's contract, which always passes `pin = NULL`)
    it plays no part in authorization. **[INFERENCE]** the hash is the only RP-dependent input
    that reaches the wire.
- **[INFERENCE]** if text `t` satisfies `SHA-256(t) == authoritative hash`, calling
  `fido_credman_get_dev_rk(dev, t, ...)` sends exactly the authoritative hash. This is what makes
  verified text a sound bridge, and what the contract enforces (section 5).
- Finding a `t` for an unknown hash is a SHA-256 preimage problem: not a workaround.

## 3. CTAP specification

- **[SPEC] §6.8.4**: `enumerateCredentialsBegin` takes **`rpIDHash` (0x01)** in
  `subCommandParams`. The protocol does not need RP text; **only the libfido2 API surface does.**
- **[SPEC] §6.8.3**: in `enumerateRPsBegin`/`GetNextRP`, `rp` is a `PublicKeyCredentialRpEntity`
  "where the id field SHOULD be included and other fields MAY be included"; `rpIDHash` (0x04) is
  the SHA-256 hash.
- **[SPEC] §6.8.7**: authenticators "MAY store relying party identifiers" and "MAY truncate
  them" to a stored form of at least 32 bytes (long IDs become an optional `scheme:` prefix, a
  U+2026 ellipsis, and the final bytes). "Authenticators MUST NOT use truncated relying party
  identifiers for comparisons", i.e. the **hash stays authoritative** and the text is advisory.
- **[INFERENCE]** hash-only RPs are therefore expected, not exceptional: any RP ID longer than 32
  bytes on a truncating authenticator, and any authenticator that does not store RP IDs. A
  truncated string hashes to a different value, so it is a hash mismatch by construction and can
  never be "repaired" into the real RP ID.
- **[SPEC] §6.8.2**: `existingResidentCredentialsCount` (0x01) is "total number of discoverable
  credentials existing on the authenticator", the reconciliation anchor.

## 4. Classification of every path considered

| # | Question | Classification | Evidence |
| --- | --- | --- | --- |
| 1 | RP enumeration returns RP ID text, name and hash | **SUPPORTED BY PINNED UPSTREAM API** | 2.1 |
| 2 | Public API exposes the authoritative hash (`ptr`/`len`) | **SUPPORTED BY PINNED UPSTREAM API** | 2.1 |
| 3 | Public API validates hash length, text/hash agreement or UTF-8 | **UNSUPPORTED**: the adapter must (contract in section 5) | 2.1 |
| 4 | `fido_credman_get_dev_rk` accepts RP ID **text** | **SUPPORTED BY PINNED UPSTREAM API** | 2.3 |
| 5 | Credential enumeration for an RP whose text verifies against the hash | **SUPPORTED BY PINNED UPSTREAM API** (equivalent to hash enumeration) | 2.3 |
| 6 | Any public API taking a raw 32-byte RP hash for `enumerateCredentialsBegin` | **REQUIRES UPSTREAM WORK**; for the MVP an **UNSUPPORTED PRODUCT LIMITATION** | 2.3; unchanged on upstream `main` |
| 7 | libfido2 computes SHA-256 of the text itself | confirmed (so hash-only input is impossible without a different function) | 2.3 |
| 8 | Lower-level reviewed path accepting the hash | **none exists** (below) | |

Lower-level possibilities, none adopted (and none permitted by the architecture plan):

- the internal `credman_tx` / `credman_get_rk_wait` are `static` and unexported. Linking
  against private symbols or patching the vendored library is "upstream work", not a reviewed
  path;
- `fido_dev_set_io_functions` / `fido_dev_set_transport_functions` are public, and would let a
  shim rewrite the outgoing frame. That requires custom CBOR *and* recomputing `pinUvAuthParam`
  (an HMAC over `subCommand || subCommandParams` keyed by the PUAT), whose bytes the contract
  deliberately never reads. It is the "ad-hoc raw-CBOR implementation" the plan forbids, plus a
  token-exposure regression, so it is **rejected**;
- **[INFERENCE]** the upstream change that would lift the limitation is small: one new function
  taking `(const unsigned char *rp_id_hash, size_t len)` that fills `rp_dgst` directly and
  otherwise reuses `credman_get_rk_wait`. That is a proposal to be pursued separately
  (architecture plan section 21), not part of this spike.

## 5. RP identity contract (prototype)

`crates/fido-puat-spike/src/rp_identity.rs`. Minimal, not an M3 DTO or renderer schema.

- `RpIdHash`: only constructible from exactly 32 bytes; `Absent` / `WrongLength { len }` otherwise.
  Never padded, truncated or defaulted. `Debug` redacts.
- `RpTextState`: `VerifiedText(VerifiedRpId)`, `TextUnavailable`, `TextHashMismatch`,
  `TextMalformed`. Unverified text is **discarded**, not retained as a display fallback, so the
  type system cannot misuse it as an identity.
- Verification requires, in order: valid UTF-8, a usable RP ID (reusing the PUAT spike's
  `RpId`: non-empty, at most 253 bytes, no NUL), and then `SHA-256(exact bytes) == hash`.
  Case is part of the bytes (`Example.com` does not verify against the hash of `example.com`).
- Absent text (`NULL`) is `TextUnavailable`; present-but-empty text is `TextMalformed`: absent
  never becomes an empty string, and empty never reads as absent.
- `Continuation`: `ViaVerifiedText(&VerifiedRpId)` is the only path that yields a value that may
  be passed to `fido_credman_get_dev_rk`. Every other state is `Blocked(reason)`.
- `RpList::from_raw` keeps every entry in device order, including malformed ones, and records
  `MalformedHash { index }` and `DuplicateHash { first, duplicate }`. **No deduplication.**
- `assess(list, per-RP results, reported_existing)` returns `Complete`, `Incomplete` or
  `Inconsistent`, and a `CredentialTotal` whose claim follows the verdict:

  | Verdict | `CredentialTotal` | Why |
  | --- | --- | --- |
  | `Complete` | `Exact(n)` | every listed RP enumerated and the sum equals the authenticator's own count |
  | `Incomplete`, nothing contradictory | `AtLeast(n)` | a genuine lower bound: only successfully enumerated RPs with distinct hashes contribute, so their credential sets are disjoint |
  | `Inconsistent` | `Unknown` | the observations contradict each other or the authenticator, so a sum may double-count (duplicate RP hash), exceed the authenticator's own count (surplus) or have overflowed; no numeric bound is trustworthy |

  `Inconsistent` takes precedence: an inspection that is both incomplete and contradictory is
  `Unknown`. The raw sum is kept as `observed_enumerated`, documented as diagnostics only
  (never a bound), and is what the harness prints as `credential_count`. There is no way to
  obtain a bare "0" for an incomplete or inconsistent inspection.

Reasons:

| Class | Reasons |
| --- | --- |
| Incomplete | `MalformedRpHash`, `ContinuationUnsupported { blocker }`, `EnumerationFailed { code }`, `EnumerationNotAttempted`, `ResultsMisaligned`, `MetadataUnavailable`, `Shortfall { enumerated, reported }` |
| Inconsistent | `DuplicateRpHash`, `ListedRpWithoutCredentials`, `Surplus { enumerated, reported }`, `TotalOverflow` |

Decisions in the prototype that M3 should keep or consciously change:

1. `Complete` requires **every listed RP enumerated** and `enumerated == existingResidentCredentialsCount`.
   A blocked RP keeps the inspection `Incomplete` even if the counts coincide.
2. An unreadable `getCredsMetadata` is `Incomplete`, never "complete against nothing". CTAP
   always provides the count when credential management is supported.
3. A listed RP with a zero credential count is `Inconsistent` (section 2.2).
4. Enumerated more than reported is `Inconsistent`, not "complete with extras".

## 6. Hash-only product limitation (MVP)

- **Classification:** hash-only RP credential enumeration: **UNSUPPORTED PRODUCT LIMITATION**.
- No raw CBOR workaround was implemented, per the brief and the plan.
- Consequences for M3 (unchanged from, and now confirmed against, the plan's section 21 and
  security model section 22):
  - preserve the authoritative hash for every RP; show it (for example a short prefix) where a
    native confirmation needs an RP label and the text is unverified;
  - mark credential inspection `Incomplete` for each such RP; present the credential total as a
    lower bound (`AtLeast`), never as a count, and drop even the lower bound if the inspection is
    also `Inconsistent`;
  - never report zero credentials for an RP whose enumeration could not continue;
  - credentials of such RPs are never listed, so **they can never be deleted individually**
    (deletion requires a listed exact credential ID in the current epoch). The reset warning must
    keep saying reset destroys credentials the app cannot enumerate;
  - upstream support is a separate effort (section 4).

## 8. Native harness extension

`fido-puat-spike rp-inventory --mode ro|cm` (feature `native-puat`; a few FFI accessors and
`LibFido2Device::credman_rp_list` / `credman_rk_count_for` were added to `native.rs`).

- uses the existing reviewed acquisition path (`plan`, `DeviceSession::acquire`,
  `PuatGuard::use_token`, cleanup on every path); one acquisition, PIN sent once, no retry,
  retry-count gate, typed `yes` confirmation, no-echo `/dev/tty` prompt, watchdog on each call;
- issues only read requests: `getCredsMetadata`, `enumerateRPsBegin/GetNextRP`,
  `enumerateCredentialsBegin/GetNextCredential` (the last only for RPs with verified text; for
  hash-only RPs nothing is sent);
- copies each RP's hash and text out of libfido2 *before* `fido_credman_rp_free` (bounded: at
  most 512 RPs, 65 hash bytes, 257 text bytes), compares in memory, and never prints them;
- prints only structure: counts, lengths and booleans (example in section 9);
- no delete, no PIN set/change, no reset, no write, no new mutation entry point;
- does not touch the production worker or protocol.

## 9. Hardware evidence

**[HARDWARE]** Thetis Security Key, VID:PID `1ea8:f829`, firmware `0x100`, macOS, libfido2 1.17.0,
exactly one key attached. Single-device evidence only.

What the command sent: `authenticatorGetInfo`, `getPinRetries`, one PIN-protocol key agreement and
one PIN submission to obtain a `cm` token (the Thetis has no `perCredMgmtRO`, so a read-only token
cannot be obtained, and this grants credential-management authority, including delete, though the
harness issues no write), then read-only `getCredsMetadata`, `enumerateRPs` and per-RP
`enumerateCredentials`. The token was cleared at the end. No RP ID text, RP name, user name,
credential ID, hash, PIN or token byte is printed by the command.

### 9.1 Wrong-PIN observation

An intentionally wrong PIN was submitted once, to see what the harness reports (reported output):

```text
pin_retries=8                      (before submission)
RESULT step=acquire outcome=failed error=Native { failure: WrongPin, code: 49 }
RESULT step=acquire name=FIDO_ERR_PIN_INVALID retry_effect=Consumed blocks_further_attempts=false
RESULT step=pin_retries_after_failure pin_retries=7
```

Observed, no more:

- one wrong PIN consumed exactly one retry on this Thetis (8 to 7);
- the harness classified `FIDO_ERR_PIN_INVALID` (code 49) as `WrongPin` with `retry_effect=Consumed`,
  and the observed decrement matched that classification;
- no automatic retry occurred; the command stopped after the failure.

This is one observation on one device. It is not evidence of how any other authenticator or
firmware counts retries or handles this error.

### 9.2 Successful RP inventory

A fresh session (retry count 7 before submission), then a correct PIN (reported output):

```text
RESULT step=fresh_object token_len=0 token_ptr_null=true
RESULT step=pin_retries_before pin_retries=7
RESULT step=acquire outcome=ok grant=ScopedCredMan { rp_scoped: false } token_len=32
RESULT step=metadata code=0 metadata_existing=1 rk_remaining=199
RESULT step=enumerate_rps code=0 rp_count=1 rp_hash_len=[Some(32)] rp_hash_absent=0 rp_hash_wrong_len=0 duplicate_hashes=0 rp_text_present=1 rp_text_hash_matches=1 rp_text_hash_mismatch=0 rp_text_malformed=0 rp_text_unavailable=0
RESULT step=enumerate_rks rp_index=0 code=0 credential_count=1
RESULT step=reconcile metadata_existing=Some(1) credential_count=1 counts_reconcile=true completeness=Complete credentials=Exact(1) incomplete=[] inconsistent=[]
RESULT step=release cleared=true
RESULT step=after_release token_len_and_ptr_null=Ok((0, true))
```

Conclusions, kept to what the output shows:

1. On this Thetis, the one enumerated RP exposed an authoritative RP hash of exactly 32 bytes.
2. RP ID text was present, and its exact bytes hashed to the authoritative RP hash
   (`rp_text_hash_matches=1`).
3. Credential enumeration through public libfido2 succeeded for that verified RP text
   (`enumerate_rks ... credential_count=1`), the path classified in section 4 as supported.
4. Device metadata reported one existing credential and enumeration found exactly one.
5. Count reconciliation therefore classified the inspection `Complete` / `Exact(1)`.
6. On this key no duplicate hash, malformed or missing hash, mismatching text, malformed text or
   unavailable text was observed.
7. Explicit PUAT cleanup succeeded and left no host-attached token (`release cleared=true`,
   token length 0 and pointer `NULL` afterwards).
8. The grant was a full `cm` token (`ScopedCredMan`, not RP-scoped), as expected without
   `perCredMgmtRO`; read-only behaviour here is the harness's policy, not authenticator
   enforcement.

A later review change to the contract (the `Inconsistent` total became `Unknown` instead of
`AtLeast`, section 5) only affects non-`Complete` verdicts, so it does not change this run's
`Complete` / `Exact(1)` result and no hardware rerun is needed.

### 9.3 What this run does not show

- It does **not** verify hash-only credential enumeration. Every RP on this key had verified text,
  so the hash-only paths were never reached. The hash-only
  **UNSUPPORTED PRODUCT LIMITATION** conclusion rests on [SOURCE] (section 2.3) and [SPEC]
  (section 3), not on hardware.
- It does not show that authenticators in general return RP text, or that returned text matches
  the authoritative hash. Those remain what the contract checks, not what hardware has been seen
  to guarantee.
- It does not show how any other authenticator handles a wrong PIN or counts retries.
- The negative paths (`TextHashMismatch`, `TextUnavailable`, malformed hash, duplicates, count
  shortfall) are covered only by the synthetic tests in section 7.
- No further hardware step is required for this gate.

## 10. M3 implications

1. The adapter copies `fido_credman_rp_id_hash_ptr/len` for every RP and builds the
   authoritative hash itself; it never trusts `fido_credman_rp_id` as an identity.
2. Text is verified in Rust (UTF-8, `RpId` rules, SHA-256 equality) before it can reach
   `fido_credman_get_dev_rk`; only `VerifiedRpId` converts to the C string.
3. A mutation or confirmation that names an RP binds the authoritative hash, not the text.
4. The per-RP and aggregate completeness rules (section 5) apply to every inspection result:
   `Exact` only on `Complete`, `AtLeast` only on a non-contradictory `Incomplete`, and no
   numeric claim (`Unknown`) on `Inconsistent`. The raw per-RP sum is diagnostics, never UI.
5. `FIDO_OK` with zero RPs or zero credentials must never be published as "empty" without the
   metadata count agreeing (section 2.2).
6. A hostile or buggy authenticator can fabricate any of these; they produce
   `Incomplete`/`Inconsistent`, never a confident wrong answer.
7. M3 user-facing text must distinguish "key reports N credentials; M could not be read" and
   "the key's data is inconsistent, no count can be trusted" from a clean list, and must not
   offer deletion for blocked RPs.
8. RP name (`fido_credman_rp_name`) is untrusted display text; it is not read by this spike.
9. Open upstream proposal: hash-taking enumeration entry point (section 4).

## 11. Remaining unknowns

- **[UNRESOLVED]** hardware evidence for the negative paths: a key that returns truncated,
  absent or mismatching RP text, or a malformed or duplicate hash. Section 9 observed only the
  all-verified case on one Thetis.
- **[UNRESOLVED]** which authenticators truncate or omit RP IDs in practice; the Thetis did not
  for its one RP.
  The product limitation is justified by the spec permitting it, not by a measured prevalence.
- **[UNRESOLVED]** behaviour on libfido2 builds other than 1.17.0. M2 already requires 1.17.0
  on every platform that runs the token path; this spike inspected only that tag and upstream
  `main` as of 2026-07-09.
- **[UNRESOLVED]** whether upstream will accept a hash-taking enumeration function.
