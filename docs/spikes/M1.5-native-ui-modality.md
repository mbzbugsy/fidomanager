# M1.5 native sensitive-UI threading and modality

Status: macOS **development-window feasibility passed**. Linux runtime validation and the Windows broker/access spike remain open. This is not production M2 authentication or packaged-platform clearance.

Specification: [issue #17](https://github.com/mbzbugsy/fidomanager/issues/17). Implementation and validation used the existing local Mac checkout on `spike/m1.5-native-ui-modality`, starting at current `origin/main` (`b9314bc`). No merge, real PIN, authentication transaction, operation permit, or authenticator mutation is part of this spike.

## Selected contract

[SOURCE] `crates/fido-native-ui/src/lib.rs` exposes the following backend-only, non-Serde types:

- `PromptController::request(WorkflowId, Instant, Duration)` returns an owned `PromptRequest` and a Rust `Receiver<PromptOutcome>`.
- The authority supplies its minted workflow generation. The controller allocates a monotonically increasing `PromptInstanceId`, checks exhaustion, and never reuses an instance during its lifetime. Exactly one controller belongs to an authority for its entire lifetime; replacing a controller while callbacks exist is prohibited. Local callbacks cannot survive process restart, so these process-local identities are not IPC bootstrap tokens or cryptographic nonces.
- `PromptRequest` has private fields, read-only binding/deadline accessors, no `Clone`, and no renderer deserializer. Platform handles never occur in the neutral contract.
- `resolve(outcome, now)` accepts only the currently registered workflow **and** prompt. Duplicate or stale decisions are rejected. Approval at/after the monotonic deadline becomes `TimedOut`, independently of event-loop timer scheduling.
- `revoke(outcome)` records backend failure/cancellation before dismissal; it can veto an approval still awaiting teardown. `shutdown()` vetoes pending approval and permanently closes admission.
- `did_teardown(binding, now)` is the native host's acknowledgement that the UI is detached and hidden. Only then is one result sent and the prompt reservation released. Approval is checked against the deadline again. Teardown without a decision yields `TornDown`.
- `OwnerLost` is the conservative Drop result if controller ownership disappears without teardown acknowledgement. It never permits workflow release or native reuse. Losing the receiver does not release the native reservation.

[SOURCE] Outcomes are `Approved`, `Cancelled`, `TimedOut`, `ParentLost`, `Shutdown`, `TornDown`, `OwnerLost`, and `PresentationFailed`, each containing the exact `PromptBinding`. None is a production operation permit. Private native callbacks supply the captured binding; there is no renderer approval callback.

[SOURCE] The service spike uses the existing `SensitiveWorkflowGate`, including its minted `WorkflowAdmission`, zero queue, and interruption/cooldown policy. A concurrent admission is rejected immediately with `OperationInProgress`; no automatic successor prompt is scheduled. The harness uses the credential-inspection admission category only as a gate fixture and starts no inspection transaction. The workflow is released after the native result, with worker quiescence/recovery evidence valid because **no FIDO execution or recovery incident was started**. Production must combine UI teardown with actual worker/recovery evidence, never copy this fixture's unconditional evidence.

[TEST] Nine deterministic contract tests cover wrong workflow/prompt identity, stale callbacks against a successor, duplicate and competing callback rejection, cancellation/all failure variants, expiry at callback and teardown, revocation/shutdown overriding pending approval, reservation held until teardown, receiver/owner loss, and identity/lifetime exhaustion. A tenth macOS-feature test rejects presentation on a background thread before touching even a null native parent. Neutral tests need no display server.

## macOS implementation and observed results

[SOURCE] `macos_spike.rs` uses the pinned `objc2` 0.6.4, `objc2-app-kit` / `objc2-foundation` 0.3.2 and `block2` 0.6.2 already present in the lockfile. AppKit objects stay in main-thread-local storage. Presentation checks `MainThreadMarker`; native completions, notification handlers, timers, and teardown assert it again. No AppKit object is transferred to the Rust authority's receiver thread.

[SOURCE] The Tauri adapter obtains `get_webview_window("main").ns_window()` **inside** `run_on_main_thread`, and the host immediately retains that exact live `NSWindow`. There is no renderer-supplied window identifier, native pointer, prompt text, or binding. The window must be visible, unminimized, and the application foreground. An already attached sheet is rejected before calling AppKit, preventing AppKit's own sheet queue.

[SOURCE] `NSAlert::beginSheetModalForWindow_completionHandler` presents asynchronously and returns to Tauri's ordinary event loop. Both `parent.attachedSheet == alert.window` and `alert.window.sheetParent == parent` are checked by native object identity after presentation. No `runModal`, modal-session runner, or custom/nested event loop is used. The pinned AppKit bindings document this as the NSWindow sheet mechanism; see also Apple's [asynchronous sheet API](https://developer.apple.com/documentation/appkit/nswindow/beginsheet(_:completionhandler:)).

[SOURCE] The fixed native text explicitly identifies the non-secret spike. Cancel is added first with Return as its key equivalent; Continue has no key equivalent, and Cancel is requested as first responder. After presentation the native default button cell must be Cancel and Continue must not be first responder, or presentation fails closed. No input widget exists, so even accidental real PIN entry cannot become a Rust/renderer payload. Production untrusted device/RP/user text will require native-boundary bounded sanitization; fixed text here proves no such sanitizer yet.

[MACOS] Empirically run on this development Mac: Apple Silicon `aarch64`, macOS **26.5.2 (25F84)**, Rust **1.98.1**, Tauri **2.12.0**, embedded built frontend (`tauri/custom-protocol`). The runner launched the actual local Tauri binary and exercised its actual `main` application window. All eight scenarios passed:

| Scenario | Native / Rust result | Observed teardown |
| --- | --- | --- |
| `native-cancel` | Native Cancel button → `Cancelled` | detached and hidden |
| `native-continue` | Native Continue button → `Approved` | detached and hidden |
| `cancel` | Backend cancellation → `Cancelled` | detached and hidden |
| `timeout` | 2-second monotonic expiry → `TimedOut` | detached and hidden |
| `teardown` | Explicit backend teardown → `TornDown` | detached and hidden |
| `parent-close` | Destroy original Tauri main window → `ParentLost` | detached and hidden |
| `replace-parent` | Create another Tauri window, destroy original → `ParentLost` | no sheet/result transferred |
| `shutdown` | Tauri application exit → `Shutdown` | detached before exit |

[MACOS] Each scenario logged `main=true attached=true sheet_parent=true default_cancel=true approval_focused=false`, a main-run-loop timer progressing with the sheet open, exactly one `Rust authority result=...`, `workflow_released=true`, and `second_result=Err(Disconnected)`. Mechanical native-button fixtures invoke NSAlert's actual native button action and completion handler. They prove callback plumbing; they are **not human authorization evidence**. No fixture is renderer-callable or available in a default/release build.

[MACOS] The parent-loss cases keep an independent Tauri observer window alive so parent loss is distinguishable from application exit. The observer/replacement has a different native identity and no selected renderer capability. An old parent is never replaced inside a live request. Its retained native object is held only through teardown.

## Lifecycle and teardown

[SOURCE] Cancellation/expiry/parent loss record a failure **before** `endSheet(returnCode: Cancel)`, so a late completion cannot resurrect approval. Parent `NSWindowWillCloseNotification` uses an exact object filter. A 50 ms timer in common run-loop modes also detects parent disappearance or lost sheet association and checks a trusted monotonic deadline. The normal fixture lifetime is 30 seconds; timeout mode is 2 seconds. These are spike constants, not selected M2 prompt/permit lifetimes.

[SOURCE] Completion calls `orderOut`, checks that the sheet is hidden, has no `sheetParent`, and is no longer the parent's attached sheet. It invalidates the timer and removes notification tokens before acknowledging teardown/delivering to Rust. If detachment cannot be proven, the reservation and timer stay alive; no queued prompt or guessed quiescence is permitted. The callback, dismissal fallback, and timer may race logically, but all native operations occur on one thread and exact binding checks plus controller state accept at most one result.

[SOURCE] Tauri `ExitRequested` and `Exit` and AppKit application termination revoke approval and detach the prompt. After native teardown, Tauri shutdown waits up to 500 ms on a condition variable solely for the Rust receiver acknowledgement; it does not wait for AppKit work or run a modal/event loop. Missing acknowledgement keeps the reservation fail-closed. Abrupt process death cannot leave an approving Rust authority alive; it is not a guarantee of a callback after process death. Production authority shutdown must retire its controllers permanently. No native cancellation implies cancellation of a worker; this spike has no worker-sensitive transaction.

[INFERENCE] Destructive activation delay belongs in backend request policy and the trusted native host: service defines operation kind/not-before policy; the native host disables the destructive control until that deadline and rechecks it in the native callback, with the service also validating before permit issuance. No mutation control or production delay constant is introduced here. Prompt evidence alone cannot authorize an operation; immutable intent/target/session binding and single-use permits remain M2+ gates.

## Renderer isolation and build separation

[SOURCE] `src-tauri` still depends only on `fido-service` among project trust crates. The service's native-UI dependency is optional, and all spike features default to empty. The adapter startup module and service implementation are compiled only for macOS with `native-ui-spike`; startup additionally requires an explicit local `--native-ui-spike=<scenario>` argument. Second-launch arguments remain ignored by the existing singleton plugin. The native crate deliberately fails compilation if `modality-spike` is enabled without debug assertions, preventing an ordinary release build from accidentally including this prototype.

[TEST] `scripts/check-renderer-boundary.mjs` passes against resolved Tauri ACLs. Its discovery parameter check now requires exactly the authority-owned `State` parameter rather than allowing extra parameters beside it. The allowed commands remain exactly `foundation_status` and `list_authenticators`; the permissions, selected capability, manifest, invoke handler and frontend invoke surface are unchanged. No prompt/PIN/secret/approval DTO, event, channel, plugin permission, or renderer command was added. Default app dependency inspection shows no `fido-native-ui` dependency. Release-feature rejection is checked separately.

[SOURCE] Spike diagnostics contain only static text, lifecycle booleans, internal identities and result classifications. No input content, real PIN, token, authenticator credential, or user text is collected, stored, logged or serialized. Neither the neutral crate nor the prototype adds production PIN transport, PUAT acquisition, enumeration UI, mutation dispatch, journal, broker, or provider integration.

## Linux association model and validation plan

[LINUX][SOURCE] Pinned Tauri 2.12.0's `WebviewWindow::gtk_window()` returns its actual **GTK 3 `ApplicationWindow`**, explicitly restricted to the main thread. Use that backend-owned object on Tauri's GTK UI thread/main context. A raw XID, `wl_surface`, renderer window label or a separately initialized GTK 4 toolkit is not needed for in-process GTK 3 transient parenting. If a future authority is out of process, this direct GTK object model no longer applies; reviewed compositor-specific exported-parent support would be another gate.

[LINUX][SOURCE] The candidate host sets [transient-for](https://docs.gtk.org/gtk3/method.Window.set_transient_for.html), [modal](https://docs.gtk.org/gtk3/method.Window.set_modal.html), and [destroy-with-parent](https://docs.gtk.org/gtk3/method.Window.set_destroy_with_parent.html) on a GTK 3 dialog using that same parent, connects response/destroy signals, and attaches timeout/cancellation to the owning [GLib main context](https://docs.gtk.org/glib/main-loop.html). Use asynchronous signals and `show`/`present`; avoid [`gtk_dialog_run`](https://docs.gtk.org/gtk3/method.Dialog.run.html), which uses a recursive main loop. GTK modal prevents interactions with other application windows; transient parenting establishes the window-manager relationship. Those properties do not prove compositor enforcement on their own.

[LINUX][UNRESOLVED] No Linux GUI host or supported runtime combination is claimed by this macOS spike. The headless contract remains portable; existing Linux CI runs its tests without opening prompts. Runtime acceptance matrix:

| Candidate configuration | Required evidence before support | Current status |
| --- | --- | --- |
| Ubuntu LTS / GNOME, native X11 GTK 3 | Same GTK parent; transient/modal properties; WM transient hint/stacking; blocked parent input; all lifecycle scenarios | planned, unsupported until proven |
| Fedora / GNOME Mutter, native Wayland GTK 3 | Same mapped parent/display; compositor transient relationship; blocked parent input, focus and all lifecycle scenarios | planned, unsupported until proven |
| Fedora / KDE KWin, native Wayland GTK 3 | Independent compositor validation of the same relationship, focus, teardown and no fallback window | planned, unsupported until proven |
| XWayland GTK 3 under Mutter/KWin | Validate separately from native Wayland; ensure both windows use the same backend/display and transient/modal behavior survives focus changes | planned, unsupported until proven |
| Mixed displays/backends, missing parent, remote/headless session, untested compositor/toolkit | No reliable same-parent relationship established | reject sensitive presentation; no floating-dialog fallback |

[LINUX] For each candidate record distro/GTK/WebKitGTK/Tauri/WM or compositor versions and `GDK_BACKEND`/session type; run the eight equivalent scenarios plus Return/Escape, competing parent input, repeated presentation, multiple windows, parent minimize/destroy/replace, shutdown, and focus/workspace changes. Check transient parent identity and modal state programmatically and confirm effective input blocking manually. A compositor that fails association/focus/lifecycle checks remains unsupported. Neither X11 nor Wayland parenting implies protection from all same-user input observation/injection.

## Windows dependency handed to the access/broker spike

[WINDOWS-DEPENDENCY] If the trusted authority is elevated, **the broker owns the prompt and its workflow/prompt controller**. The unelevated Tauri client requests a workflow only; it never returns approval or PIN material. Cross-integrity HWND ownership/parenting is not an accepted design assumption. Source context: Microsoft's [owned-window relationships](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features) and [foreground activation restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow).

[WINDOWS-DEPENDENCY] The later spike must empirically answer:

1. Which initiating/elevating user, integrity level, desktop/session and alternate-credential combinations are supported?
2. What broker-owned top-level/owner-window model genuinely associates the prompt with the requesting application without trusting a client-supplied HWND or cross-integrity parenting?
3. How is foreground/focus admission established under UAC, foreground-lock restrictions, desktop changes and client minimize/focus loss? Is presentation refused when reliable association cannot be achieved?
4. Do timeout, cancel, client death, owner close/replacement, broker exit, lock/suspend/session switch and delayed native callbacks revoke approval, close the dialog and preserve reservations until teardown/quiescence?
5. How do broker/client launch identity, exact workflow generation/prompt identity and replay protection ensure a result cannot approve a different request or survive client/broker replacement?
6. Does the model work on each intended architecture and user/elevation configuration, including multiple application windows? How do broker singleton and recovery namespace follow the initiating/elevating user decision?

[WINDOWS-DEPENDENCY] UAC approval is not consent to a FIDO operation. UIPI/input integrity is not a PIN-confidentiality guarantee against same-user malware or keylogging. No Windows implementation or unsupported safety claim is introduced here.

## Reproduction, checks, and decisions

[SOURCE] From this existing local checkout, with other FidoManager instances closed and an active foreground Mac GUI session:

```sh
pnpm build
cargo build -p fido-worker --locked
cargo build -p fidomanager-app --features native-ui-spike,tauri/custom-protocol --locked
python3 scripts/check-native-ui-spike-macos.py
# Optional human exploration (30-second expiry):
./target/debug/fidomanager-app --native-ui-spike=manual
```

[MACOS] The runner checks each subprocess exit, real parent/default/focus assertions, event-loop progress, exactly one terminal result, correct outcome and workflow release after detachment. It saves non-secret logs to ignored `target/native-ui-spike/validation.log`. Native-button scenarios are explicitly mechanical fixtures. The runner launches only the existing local build; it never edits or launches another checkout and never supplies a PIN.

[TEST] Validation commands:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo clippy -p fidomanager-app -p fido-native-ui -p fido-service --all-targets --features fidomanager-app/native-ui-spike --locked -- -D warnings

node scripts/check-renderer-boundary.mjs

pnpm test --exclude '**/.claude/**'
```

[TEST] The local commands used cached dependencies (`--offline`) and disabled pnpm's automatic dependency verification (`--config.verify-deps-before-run=false`). Formatting excludes generated Tauri schemas and unrelated local `.claude/` checkouts. The frontend test run reports no test files. A pre-existing worker process-count test failed inside the sandbox; the full suite passed when allowed to observe child processes outside it. This is an environment limitation, not a modification of completed worker containment.

[INFERENCE] The established decision matches existing architecture sections 9/26 and Security Model section 6: main-thread asynchronous window-modal sheets are feasible against the real macOS Tauri window, with backend-bound identity and explicit teardown. A small evidence link in the release plan is sufficient; no architecture redesign or new ADR is necessary. ADR-007 is still a future production authentication decision, and ADR-013 remains the separate Windows gate.

[UNRESOLVED] Issue #17's independent pre-merge review remains required. This spike does not grant permission to merge or start production M2. Before M2, settle production lifetime/admission constants, destructive activation policy, sanitizer/immutable-intent/permit integration, lock/suspend/session revocation and secret-memory/transport design.
