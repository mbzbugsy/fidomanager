# M1.5 spike: libfido2 PUAT and credential-management fit

Issue: #9. Status: **source inspection, prototype contract, automated tests and the Thetis hardware
gate are complete for every capability the Thetis advertises.** `perCredMgmtRO` and built-in UV are
not advertised by this key and are recorded as not applicable, not as untested. Remaining
unverified items (CTAP 2.0 legacy hardware, other authenticators) are listed in section 13.

Hardware results below were supplied by Nima from running `fido-puat-spike` on the Thetis; the
PIN was typed only into the no-echo harness and never entered this conversation. The raw terminal
output was relayed as a summary, so entries labelled [HARDWARE] are as reported, not re-observed
by the author of this report.

This is a feasibility spike. It adds no production behaviour: no renderer-callable PIN path, no
native PIN dialog, no credential listing, no deletion, no PIN set/change, no reset, and no change to
the worker protocol. The code lives in `crates/fido-puat-spike` (`publish = false`, depended on by
nothing) and its native part only builds with `--features native-puat`.

## 3. Source-level findings

### 3.1 `fido_dev_get_puat(dev, perm, rpid, pin)`

- **[SOURCE] pin.c `fido_dev_get_puat`** first calls `fido_blob_reset(&dev->puat)`, so any
  previously attached token is wiped *before* the attempt; then ECDH, then `uv_token_wait`, which
  writes the decrypted token straight into `dev->puat`. The token never passes through an
  application buffer.
- **[SOURCE] pin.c `uv_token_wait`**: if `fido_dev_supports_permissions(dev)` (GetInfo option
  `pinUvAuthToken`) it sends subcommand 0x09 (PIN) or 0x06 (built-in UV) with `perm` and `rpid`;
  **otherwise it sends CTAP 2.0 `getPinToken` (0x05) and silently ignores `perm` and `rpid`**,
  returning `FIDO_OK` with an unscoped token. A request for `FIDO_PUAT_CREDMAN_RO` on a CTAP 2.0
  authenticator therefore *succeeds* and yields full, unscoped authority.
- **[SOURCE]** with `pin == NULL`: the 2.1 path uses built-in UV only if `fido_dev_has_uv` (option
  `uv` true), else `FIDO_ERR_PIN_REQUIRED` before transmitting; the 2.0 path returns
  `FIDO_ERR_PIN_REQUIRED` before transmitting. Legacy is PIN-only.
- **[SOURCE]** the man page says the RP ID is ignored for `CREDMAN_RO`, but `ctap21_uv_token_tx`
  transmits `rpid` whenever it is non-NULL, regardless of `perm`.
- **[SOURCE]** libfido2 performs no host-side check of `perCredMgmtRO` before sending 0x40.
- **[SOURCE] `tools/token.c ppuat_get`**: upstream's own `fido2-token -G -t` writes the persistent
  read-only token to a file. FidoManager must not do that (persistence is forbidden).

### 3.2 Attached-token semantics

- **[SOURCE] dev.c**: the token lives in `dev->puat`. `fido_dev_set_puat(dev, NULL, 0)` and
  `fido_dev_free` call `fido_blob_reset`, which is `freezero` + `explicit_bzero` (**blob.c**).
- **[SOURCE] dev.c `fido_dev_close`** closes the transport and resets the CID only; it **does not
  touch `dev->puat`**. `fido_dev_open_rx` resets `dev->flags` but not the token. A token survives
  close/reopen of the same object.
- **[SOURCE] pin.c `cbor_add_uv_params`**: if a token is attached it is used *instead of* the PIN
  for every token-aware call; the PIN argument is not even consulted. If no token is attached it
  acquires a one-shot token per call with `cmd_to_perm`, which maps both credential-management
  commands to **`FIDO_PUAT_CREDMAN` (full `cm`)**, never read-only.
- **[SOURCE] man page**: "An invalid token is not automatically cleared from dev."
- **[SOURCE] credman.c `credman_tx`**: with no token and `pin == NULL` the call still runs ECDH and
  then `fido_dev_get_uv_token(pin = NULL)`. On an authenticator with `uv` configured that **starts
  built-in UV** (and can consume UV attempts); without UV it returns `FIDO_ERR_PIN_REQUIRED`
  before sending anything that authenticates.

### 3.3 Credential management

- **[SOURCE]** `credman_get_cmd` uses 0x0A (`credMgmt`) or 0x41 (`credentialMgmtPreview`).
- **[SOURCE]** `fido_credman_get_dev_rk(dev, rp_id, ...)` takes RP ID **text** and hashes it
  (`credman_get_rk_wait`); there is no hash-only enumeration entry point (ADR-014 input, M3).
- **[SOURCE]** enumeration continuation (`*_NEXT`) is sent with no authentication, as CTAP specifies.

### 3.4 Retry APIs

- **[SOURCE] pin.c**: `fido_dev_get_retry_count` sends clientPin 0x01 and parses only response key
  0x03 (`pinRetries`); `fido_dev_get_uv_retry_count` sends 0x07 and parses only key 0x05.
  **`powerCycleState` (key 0x04) is discarded.** Neither sends a PIN or starts UV.

### 3.5 Timeouts

- **[SOURCE]** `fido_dev_new` initialises `timeout_ms = -1`. `fido_dev_get_puat` copies
  `dev->timeout_ms` into one `ms` budget that `fido_time_delta` decrements across ECDH, the token
  request and the reply, including the keepalive loop in `io.c rx_preamble`. With a finite timeout
  the whole acquisition is bounded; with `-1` the keepalive loop never ends while the authenticator
  keeps sending keepalives (for example while waiting for UV).
- **[SOURCE] hid_osx.c `schedule_io_loop`**: on macOS a `-1` timeout becomes 5 s *per read*, so it
  is not infinite per frame but is unbounded across keepalives.
- **[SOURCE]** no path in `io.c` sends `CTAPHID_CANCEL` on timeout; `fido_dev_cancel` exists but is
  only called explicitly. A host timeout leaves any UV/user-presence wait running on the device.
- **[SOURCE] hid_osx.c `fido_hid_open`**: `IOHIDDeviceOpen(..., kIOHIDOptionsTypeSeizeDevice)`.
  On macOS only one `fido_dev_t` can have a key open at a time.

## 4. CTAP 2.2 text relevant to the contract

- **[SPEC] §6.5.5.7 permissions table**: `pcmr` = 0x40, "Persistent Credential Management Read
  Only"; "the persistentPinUvAuthToken can only be used for Read Credential Management operations".
  RP ID ignored.
- **[SPEC] §6.4 GetInfo**: option `perCredMgmtRO` true means requesting `pcmr` is supported.
- **[SPEC] §6.5.5.7.2/.3**: permission checks come **before** the `pinRetries` decrement; `pcmr`
  returns `CTAP2_ERR_UNAUTHORIZED_PERMISSION` if `perCredMgmtRO` is false/absent **or any other
  permission is requested with it**; "Undefined permissions present in the permissions parameter
  are ignored." A pre-2.2 authenticator that does not know 0x40 may therefore *ignore* it and issue
  an ordinary token with no permissions, which libfido2 reports as `FIDO_OK`.
- **[SPEC]** a `pcmr` request returns the *persistent* token and does not call
  `resetPinUvAuthToken`; every other successful request regenerates the ordinary token ("all
  existing pinUvAuthTokens are invalidated"). The ordinary token is "generated afresh at power-on";
  the persistent token is reset on PIN change (setPIN/changePIN steps: "all persistent permissions
  are cleared on pin change").
- **[SPEC] §6.8.2–6.8.4**: getCredsMetadata / enumerateRPsBegin / enumerateCredentialsBegin accept
  either the persistent token with `pcmr` or the ordinary token with `cm`; getCredsMetadata and
  enumerateRPs require **no permissions RP ID**.
- **[SPEC] §6.8.5 deleteCredential**: verified only against the ordinary `pinUvAuthToken` and checks
  `cm` (and the RP ID) **before** looking the credential up, returning `CTAP2_ERR_PIN_AUTH_INVALID`.
  `CTAP2_ERR_NO_CREDENTIALS` comes after.
- **[SPEC] §6.5.2.3/§6.5.5.7.2**: wrong PIN decrements and regenerates the key agreement; three
  consecutive mismatches give `PIN_AUTH_BLOCKED` (power cycle needed); zero retries give
  `PIN_BLOCKED`. `powerCycleState` exists in the getPinRetries response but is optional.

## 7. Retry-state evidence

- **Before submission [SOURCE]**: `fido_dev_get_retry_count` (pinRetries) and
  `fido_dev_get_uv_retry_count` (uvRetries, new in 1.17.0). Both non-consuming. That is everything.
- **Cannot be known before an attempt [SOURCE]**: `powerCycleState` (discarded by the parser), so
  "3 wrong PINs this power cycle" (`PIN_AUTH_BLOCKED`) cannot be predicted; whether the key will
  accept the requested permissions; whether a display-equipped key will ask for consent.
- **After an attempt** (prototype `retry::classify_acquisition_error`, **[TEST]** sweep over every
  code from -64 to 0xff): only `FIDO_ERR_PIN_INVALID` and `FIDO_ERR_PIN_AUTH_BLOCKED` count as proof
  a retry was consumed; only `FIDO_ERR_INVALID_ARGUMENT` (rejected inside libfido2 before any
  transmission, [SOURCE] `fido_dev_get_puat`) counts as not submitted; everything else, including
  `TX`/`RX`/timeout and `INTERNAL` (which `uv_token_rx` can return after the PIN was sent), is
  "unknown, re-query". `PIN_AUTH_BLOCKED`, `PIN_BLOCKED` and `UV_BLOCKED` are explicit and stop
  further attempts. The spec says permission errors precede the decrement, but the prototype does
  not rely on that until hardware confirms it.
- **Pre-submission policy [TEST]**: >3 proceed; 2–3 warn; exactly 1 requires an extra typed
  acknowledgement; 0 refuses; query failure refuses (spike) and never displays a guessed number.

## 8. PUAT attachment and cleanup

- **Contract [TEST]**: `DeviceSession::open` refuses a native object that already carries a token
  (a fresh `fido_dev_t` never does), `acquire` refuses and clears an ambient token instead of using
  it, and the `PuatGuard` is armed *before* `fido_dev_get_puat` runs, so success
  (`release()` reports a failed clear), error, early return and panic/unwind all clear the token.
  A clear that leaves bytes attached is reported (`TokenStillAttached`). Calls meant to run without
  authorization (`without_token`) refuse while a token is attached.
- **Host erasure is not revocation [SPEC + SOURCE]**: clearing wipes libfido2's copy. The ordinary
  token stays valid at the authenticator until a newer token, power-off, or its own timers. The
  persistent `pcmr` token stays valid until PIN change (or reset), across power cycles; anyone who
  copied it could keep reading credential metadata. FidoManager never reads the token bytes
  (`fido_dev_puat_ptr` is used only for a NULL check) and never persists them.
- **Close/reopen [SOURCE]**: the token survives `fido_dev_close`. The contract never reopens an
  object; reconnect consumes the old session and requires a strictly newer `DeviceGeneration`
  [TEST]. The harness reproduces the forbidden pattern as a negative control.

- **[HARDWARE] lifecycle on Thetis**: acquire gave a 32-byte token; reads worked; closing and
  reopening the *same* `fido_dev_t` left the token attached and still accepted; `release()` then
  cleared it (`token_len=0`, pointer NULL); a token-less read returned `FIDO_ERR_PIN_REQUIRED`.
  Issuing a second ordinary token on a fresh object made the first object's token fail with
  `FIDO_ERR_PIN_AUTH_INVALID` while its host copy stayed at 32 bytes; a physical replug did the
  same to the old token while a fresh object after replug started at `token_len=0`. Neither
  failure changed `pinRetries` (8). So the host copy says nothing about validity, and a stale token
  fails closed at the authenticator without costing a retry *on this device*.
- **Consequence [HARDWARE + SOURCE]**: same-object reuse is forbidden by the contract not because
  it is unsafe on Thetis' first reopen (the token still worked) but because the host cannot know
  whether the token is live, and libfido2 will keep sending a dead one in preference to a PIN.

## 9. Legacy fallback

- **[SOURCE]** exists and is automatic: libfido2 picks CTAP 2.0 `getPinToken` whenever
  `pinUvAuthToken` is absent, PIN-only, ignoring permissions and RP ID, and still returns `FIDO_OK`.
- **Representation [TEST]**: the contract plans before calling. `CredManReadOnly` requires
  `pinUvAuthToken` *and* `perCredMgmtRO`; `CredMan` requires `pinUvAuthToken`; neither ever falls
  back. `LegacyUnscoped` must be requested by name, is refused where scoped tokens exist (the label
  would be false), is refused for UV, and yields `GrantKind::LegacyUnscoped`, which is never
  read-only and never "permission scoped".
- **[HARDWARE]** not applicable on Thetis (advertises `pinUvAuthToken`; the planner refused
  `LegacyUnscoped`). Real CTAP 2.0 behaviour remains NOT YET EMPIRICALLY VERIFIED and needs a
  CTAP 2.0 authenticator.

## 10. UV findings

- **[SOURCE]** built-in UV acquisition exists only on the 2.1 path and only when `uv` is configured.
- **[SOURCE]** the dangerous ambient case: a credential-management call with no token and no PIN
  starts built-in UV on a UV-capable key. The adapter must never issue a token-aware call without
  an attached token (the harness skips its "no token" check on such keys).
- **[SOURCE]** UV waits rely on keepalives; only a finite timeout ends them, and the device is not
  sent a cancel.
- **[HARDWARE]** not applicable: Thetis does not advertise `uv`, so built-in UV is unsupported on
  this key (the planner returned `BuiltInUvUnavailable`). UV waits, UV retries and UV-blocked
  behaviour are unobserved and unverified on any hardware.

## 11. Timeout and containment

- **[SOURCE]** PUAT acquisition and credential-management calls honour `fido_dev_set_timeout` as a
  single budget across their exchanges; the default is unbounded. The production adapter already
  sets a timeout before every call from one `NativeDeadline`; the M2 adapter must do the same for
  these calls.
- A timeout after the PIN was sent is `RetryEffect::Unknown`, and the device may still be waiting
  for UV/presence (no cancel).
- **Hang containment [INFERENCE from ADR-009 + SOURCE]**: if a native call blocks despite the
  timeout (as `fido_dev_info_manifest`, which takes none, can), the existing `fido-worker` kill
  boundary terminates and reaps the process; `fido_dev_free` never runs, but the token dies with the
  address space. The authenticator-side token is unaffected (section 8). The harness models the same
  boundary with a watchdog that `_exit`s the process if any native call outlives its libfido2
  timeout plus 2 s.
- **Worker placement**: the PIN-bearing harness deliberately does *not* run inside `fido-worker`.
  Doing so would have meant adding a PIN-carrying request to the production JSON protocol purely for
  a spike; per the brief that is a distortion, so the harness is a separate, non-shipping native
  process with the same "native code in a killable process" property. M2 must design how PIN bytes
  reach the worker (section 13).

## 12. Proposed M2 adapter/authorization contract

Prototyped in `crates/fido-puat-spike/src/{contract,guard,retry,secret}.rs`; types stay spike-only
until hardware evidence and review promote them.

```text
TokenCapabilities::from_options(GetInfo options)       // evidence, not vendor identity
plan(capabilities, RequestedAuthorization, VerificationMethod)
    -> AcquisitionPlan { kind: GrantKind, method, permissions, rp }   // decided before any call
       RequestedAuthorization = CredManReadOnly | CredMan { rp: Option<RpId> } | LegacyUnscoped
       GrantKind              = ScopedCredManReadOnly | ScopedCredMan { rp_scoped } | LegacyUnscoped
DeviceSession::open(fresh fido_dev_t, DeviceGeneration)  // refuses an object with a token
session.acquire(&plan, Option<&PinSecret>, timeout_ms)
    -> (PuatGuard<'_>, AuthorizationGrant { kind, method, generation })
guard.use_token(&grant, |dev| credman read)              // grant generation must match
guard.release() -> Result<(), CleanupError>              // Drop clears on every other path
session.reconnect(new fido_dev_t, newer generation)      // consumes the old session
```

Invariants and how they are enforced:

| Invariant | Mechanism | Evidence |
| --- | --- | --- |
| Acquisition is explicit | only `DeviceSession::acquire` calls `fido_dev_get_puat` | [TEST] |
| Mode is typed and decided before the call | `plan` from GetInfo | [TEST] |
| Legacy cannot pose as read-only | `ReadOnlyUnavailable`/`ScopedTokenUnavailable`, distinct `GrantKind` | [TEST] |
| Ambient token is never consent | `AmbientTokenPresent`, `without_token` refuses | [TEST] |
| Cleanup on every exit path | guard armed before the call; success/error/early return/panic tested | [TEST] |
| No token/PIN bytes cross DTO boundaries | token stays in `dev->puat`; `PinSecret` not `Clone`/`Display`, redacted `Debug`, crate has no serde | [TEST] (compile-time not-`Clone`/not-`Display` checks) |
| NUL rejected before C strings | `PinSecret`, `RpId` validate at construction | [TEST] |
| Reconnect creates a new native object | `reconnect` consumes the session; `open` refuses a token-bearing object | [TEST] |
| Authorization cannot cross `DeviceGeneration` | `use_token` checks grant generation | [TEST] |
| Approval separate from authorization | `AuthorizationGrant` carries no permit; nothing converts it into one; M2 mutation APIs must take an `OperationPermit` *and* a `ScopedCredMan` grant | design |
| Credential-management calls never take a PIN | native wrapper passes `pin = NULL` | [SOURCE]-motivated, harness |

## 13. Unsupported or unverified

- **UNSUPPORTED on Thetis (not advertised)**: `perCredMgmtRO` / `pcmr` read-only tokens and
  built-in UV. The authenticator therefore cannot enforce read-only credential management for this
  key; **this report makes no claim that any authenticator enforces `CREDMAN_RO`.**
- **[UNRESOLVED]** RP-scoped `cm` on hardware (not exercised).
- **[UNRESOLVED]** CTAP 2.0 legacy behaviour on real hardware; read-only enforcement, UV, and
  `UV_BLOCKED`/`PIN_AUTH_BLOCKED`/`PIN_BLOCKED` behaviour (blocking states were deliberately not
  provoked); other authenticators and firmware. All Thetis results are single-device evidence.
- **[UNRESOLVED]** persistent-token revocation short of PIN change (moot on Thetis).
- **[UNRESOLVED]** macOS HID seize contention with other FIDO clients.
- **UNSUPPORTED PRODUCT LIMITATION [SOURCE]**: `powerCycleState`; hash-only credential enumeration.

## 14. Implications for M2

1. Pin libfido2 **>= 1.17.0 on every platform that runs the token path**, including Linux CI and
   distro packages; Ubuntu 24.04's 1.14.0 cannot link it. Options: build the pinned tag in CI, or
   gate the token adapter behind a build feature that CI exercises against 1.17.0.
2. The adapter, not libfido2, decides scoped vs legacy from GetInfo, and requires `perCredMgmtRO`
   for read-only.
3. Never call token-aware libfido2 functions with a PIN or without an attached token: the PIN path
   acquires full `cm` per call and the no-token path can start built-in UV.
4. A guard clears the token on every path; native objects are never reopened or reused across
   generations; set an explicit timeout before every call, including acquisition.
5. Retry UX can show pinRetries/uvRetries and nothing about power-cycle state; post-attempt
   classification stays conservative until hardware confirms the spec's ordering.
6. PIN transport to the worker needs its own design (bounded, never JSON-logged, zeroized on both
   sides, never a renderer schema). This spike did not change the protocol.
7. A persistent read-only token outlives FidoManager's erasure; documentation must say so
   (the plan's section 13 already does).

## 15. Implications for M3

1. **On Thetis, inspection needs ordinary `cm` authorization.** `perCredMgmtRO` is absent, so a
   read-only token cannot be obtained. The inspection transaction's "read-only" property is
   enforced by FidoManager policy only: it must issue no mutating call, hold no application
   permit, and clear the token at the end. The authenticator would accept a delete under that
   token. UI and docs must not describe Thetis inspection as authenticator-enforced read-only.
2. Where a key does advertise `perCredMgmtRO`, prefer `pcmr`, but treat enforcement as unverified
   until probed on that model.
3. RP-scoped `cm` tokens cannot run getCredsMetadata or enumerateRPs [SPEC]; whole-key inspection
   needs an unscoped (no RP) token.
4. Enumeration by RP needs RP ID text; hash-only/mismatched RPs stay an explicit `Incomplete`
   limitation unless upstream adds a hash entry point (ADR-014).
5. Completeness can be checked against `getCredsMetadata` `existing` (observed: 1 credential, 1 RP).

## 16. Remaining risks and questions

- Other authenticators: the stale-token, replug and no-retry-cost results are Thetis-specific.
- CTAP 2.0 legacy behaviour and any `perCredMgmtRO`-advertising key are unobserved.
- Blocking and UV states were not provoked, so the post-attempt mapping for
  `PIN_AUTH_BLOCKED`/`PIN_BLOCKED`/`UV_BLOCKED` rests on source and spec only.
- How M2 delivers PIN bytes to the worker without a renderer or logging exposure.
- Browser/vendor-tool contention with the macOS HID seize (`DeviceBusy` mapping).
- Two reviewed-later items: whether to require a second typed confirmation before any `cm` grant
  on a key without `perCredMgmtRO`, and how to word the inspection prompt given point 1 of
  section 15.

## Appendix A: running the harness

Build (Mac with Homebrew libfido2 1.17.0):

```bash
cargo build -p fido-puat-spike --features native-puat
```

No-PIN steps: `target/debug/fido-puat-spike info`, `target/debug/fido-puat-spike timeout-probe`.
PIN steps each explain themselves, show the retry count, require typing `yes` (and `LAST` if one
retry remains), read the PIN from `/dev/tty` without echo, send it at most as announced, and never
retry: `acquire --mode ro` (only where `info` shows `perCredMgmtRO`), `acquire --mode cm`, `stale-token --first cm`, `stale-token --first ro`,
`replug --mode cm`, `replug --mode ro`. `probe-ro-enforcement` is opt-in, only meaningful where `perCredMgmtRO` is advertised (not run on Thetis), and additionally requires
typing `PROBE`. If the process is killed while the PIN prompt is open, run `stty sane`.
